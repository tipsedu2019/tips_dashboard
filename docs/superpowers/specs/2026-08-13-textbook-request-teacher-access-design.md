# 교재관리 요청 탭 선생님 전체 열람·등록 권한

## 목표

모든 로그인한 선생님이 교재관리의 `요청` 탭에서 전체 교재 요청을 확인하고 새 요청을 등록할 수 있게 한다. 주문·입고 이후의 운영 처리는 기존 관리자·스태프 권한을 유지한다.

## 범위

### 선생님

- `요청` 탭만 노출한다.
- 다른 선생님이 만든 요청을 포함해 전체 요청 목록과 검색 결과를 본다.
- `요청 추가`로 새 교재 요청을 등록한다.
- 새 요청의 요청자는 현재 로그인한 계정으로 자동 기록한다.
- 기존 요청의 주문·입고 전환, 삭제, 반품 등의 관리 동작은 사용할 수 없다.

### 관리자·스태프

- 기존처럼 모든 교재관리 탭과 운영 동작을 사용한다.
- 요청 탭에서 전체 요청을 확인하고 주문·입고 처리한다.

## 설계

현재 화면은 비관리자에게 데이터 로드 범위를 `request`로 지정하고, UI도 `요청` 탭으로 제한한다. 이 범위는 `textbook_purchase_orders`와 `textbook_purchase_order_lines`를 전체 조회하므로, 선생님별 필터는 추가하지 않는다.

권한은 화면에서 두 가지로 분리한다.

1. `canManageTextbookOperations`는 마스터, 주문·입고, 출고, 재고, 정산 및 기존 요청의 운영 처리를 계속 보호한다.
2. `canCreateTextbookRequest`는 `isTeacher || canManageTextbookOperations`일 때만 참이다. 요청 추가와 `request` 단계의 새 요청 등록만 허용한다.

선생님이 새 요청을 열면 요청자 선택 대신 현재 로그인한 선생님 이름을 읽기 전용으로 표시한다. 기존 요청의 상세 열기, 주문·입고 전환, 삭제, 반품과 일괄 처리는 선생님에게 노출하거나 실행하지 않는다. 주문·입고 단계로 넘어가는 제출은 관리자·스태프 권한을 계속 요구한다.

## 데이터와 보안

- 기존 요청 목록의 전체 열람은 현재 `request` 데이터 범위를 그대로 사용한다.
- 새 요청은 직접 테이블 삽입이 아니라 새 `create_textbook_request_v1` RPC로 저장한다. 이 RPC는 `auth.uid()`와 `current_dashboard_role()`을 확인해 `teacher`, `staff`, `admin`만 허용한다.
- RPC는 요청 단계를 `requested`로 고정하고, 주문·입고 수량·공급처·재고 이동 값을 받지 않는다. `created_by`는 `auth.uid()`로, `requested_by`는 현재 프로필/연결된 교사 카탈로그의 이름으로 서버에서 결정한다.
- RPC는 주문과 요청 라인을 한 트랜잭션으로 생성한다. 교재명, 수업, 위치, 학생용·교사용 요청 수량, 메모만 입력으로 받는다.
- 기존의 관리자·스태프 테이블 쓰기 정책은 유지한다. 선생님에게는 위 RPC 실행 권한만 추가하며, `update`, `delete`, 주문·입고·재고·출고에 대한 직접 쓰기 권한은 추가하지 않는다.

## 오류 처리

- 인증 세션이 없으면 현재와 같이 교재관리 데이터를 로드하거나 요청을 저장하지 않는다.
- 필수 교재명·수량 검증은 기존 요청 폼 규칙을 유지한다.
- 저장 실패 시 기존의 오류 메시지 표면을 사용하고 목록을 갱신하지 않는다.

## 검증

- 선생님 권한에서 `요청` 탭이 보이고 전체 요청을 로드하는지 확인한다.
- 선생님 권한에서 새 요청이 서버가 결정한 현재 로그인 선생님 이름과 `created_by`로 기록되는지 확인한다.
- 선생님 권한에서 주문·입고 등 관리 탭과 기존 요청의 운영 처리가 노출되지 않는지 확인한다.
- 관리자·스태프의 기존 요청·주문·입고 흐름에 회귀가 없는지 확인한다.
- RPC 권한 테스트에서 선생님은 새 `requested` 요청만 만들 수 있고, 선생님 역할의 직접 insert/update/delete와 주문·입고 데이터 입력은 거부되는지 확인한다.
