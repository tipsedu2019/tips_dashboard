# Supabase 장애 복구와 무한 로딩 방지 설계

## 목표

Supabase 프로젝트의 DB 연결 장애를 운영 재시작으로 복구하고, 같은 종류의 Auth 또는 REST 지연이 재발해도 대시보드가 무한 로딩 상태에 머물지 않게 한다.

## 확인된 원인

- Vercel Production의 HTML과 정적 JavaScript는 정상 응답했다.
- Supabase Auth, REST, SQL이 함께 522/524/504 또는 연결 시간 초과로 실패했다.
- Supabase 관리 화면은 프로젝트의 Disk IO Budget 소진 임박을 표시했다.
- 초기 `auth.getSession()`과 휴보강 작업공간의 데이터 조회에는 완료 제한시간이 없어, 공급자 요청이 끝나지 않으면 로딩 상태도 끝나지 않는다.

## 검토한 접근

1. **프로젝트 재시작만 수행**
   - 가장 빠르게 현재 장애를 복구한다.
   - 자원 압박이 반복되면 같은 무한 로딩이 재발한다.

2. **프로젝트 재시작 + 클라이언트 실패 안전장치** — 채택
   - 현재 장애를 먼저 복구한다.
   - Auth 초기화와 로그인 요청, 휴보강 데이터 조회에 유한한 제한시간을 둔다.
   - 제한시간이 지나면 사용자가 이해할 수 있는 오류와 재시도 동작을 제공한다.
   - 정상 시 데이터와 권한 흐름은 바꾸지 않는다.

3. **즉시 유료 컴퓨트 업그레이드와 광범위한 쿼리 재설계**
   - 자원 여유를 늘릴 수 있지만 비용 변경과 넓은 회귀 위험이 있다.
   - 이번 승인 범위에는 포함하지 않고, 복구 후 Observability 근거로 별도 판단한다.

## 구성

### 운영 복구

Supabase Project Settings의 Restart project를 사용한다. Pause/restore, 백업 복원, 마이그레이션, 데이터 수정은 수행하지 않는다. 재시작 후에는 관리 상태만 보지 않고 Auth health, REST 최소 조회, `select now()`, 운영 로그인과 휴보강 화면을 각각 검증한다.

### 인증 실패 안전장치

Supabase Auth Promise를 공통 제한시간 헬퍼로 감싼다. 초기 세션 확인과 명시적 로그인은 제한시간 안에 끝나지 않으면 정해진 한국어 오류를 반환하고 로딩 상태를 해제한다. 늦게 도착한 응답이 이미 해제된 UI 상태를 되돌리지 않게 Promise 경계에서만 제한시간을 적용한다.

### 휴보강 조회 실패 안전장치

작업공간 데이터 로더 전체에 제한시간을 적용한다. 조회가 멈추면 기존 `finally` 경로가 실행되어 로딩을 끝내고 오류를 표시한다. 화면에는 기존 새로고침 동작을 재시도 수단으로 유지하며, 정상 데이터 구조와 저장·승인 로직은 변경하지 않는다.

### 부하 범위

초기 복구 범위는 장애 시 무한 대기를 제거하는 데 한정했다. 재시작 뒤 운영 측정에서 초기 9개 조회가 약 6.5MB를 전송하고, 대부분이 목록 화면에서 쓰지 않는 수업 일정과 처리 전후 스냅샷임을 확인해 승인 범위를 확장한다. 목록에는 실제 소비 필드만 명시적으로 조회하고, 레거시 수업 일정은 수업 선택 시 한 행만 제한시간 안에 지연 조회한다. 정규화 수업은 기존 회차 데이터를 사용하며, 일정 로딩이 끝나기 전에는 휴강일 선택과 관련 제출을 막는다.

## 오류 처리

- 시간 초과는 일반 인증 실패나 DB 스키마 오류와 구분되는 사용자용 메시지로 표시한다.
- 비밀번호나 키, 세션 토큰은 오류 메시지와 로그에 포함하지 않는다.
- 제한시간 이후 자동 재전송하지 않아 로그인이나 운영 작업이 중복 실행되지 않게 한다.

## 검증

- 제한시간 헬퍼가 정상 완료, 거절, 시간 초과를 구분하는 단위 테스트
- 초기 인증과 로그인 시간 초과 시 로딩/제출 상태가 해제되는 회귀 테스트
- 휴보강 로더 시간 초과가 오류로 종료되는 회귀 테스트
- 관련 테스트, ESLint, `next build --webpack`
- Vercel Production `READY`, 운영 별칭 HTTP 응답, Supabase Auth/REST/SQL, 실제 로그인 후 `/admin/makeup-requests` 렌더와 재시도 동작

## 배포 경계

최신 `origin/main` 기반 격리 worktree에서 구현한다. 검증된 커밋만 `main`에 반영해 GitHub로 푸시하고, 그 커밋과 일치하는 Vercel Production 배포가 `READY`인지 확인한다. 고객 메시지 발송, 알림 워커 활성화, DB 마이그레이션은 이번 작업에 포함하지 않는다.
