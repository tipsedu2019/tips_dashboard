# 영어 단어 재시험 응시예정일시·표 가독성 설계

**작성일:** 2026-07-23
**상태:** 상세 설계 검토 요청

## 1. 배경

영어 단어 재시험 목록에는 원래 시험이 있었던 `본시험일`만 표시된다. 학생이 실제 재시험을 보기로 약속한 날짜와 시간을 별도로 기록할 수 없어 조교선생님이 사전에 준비하기 어렵다.

`본시험일`은 기간 필터, 업무 일정, 기본 재시험의 `본시험일 + 7일` 자동 미응시 판정에 연결된 운영값이다. 따라서 참고용 응시 약속을 이 값이나 업무 기한에 재사용하면 기존 자동화 의미가 깨진다.

현재 본시험일 선택기는 작은 Popover 달력과 하단 수업일정 버튼을 동시에 보여 주어 정보가 중복되고 폼을 가린다. `[퇴원]`의 퇴원일 선택기는 같은 다이얼로그 안에서 전체 폭 인라인 일정 달력을 사용한다.

메모는 추가·수정 모달에 있지만 목록에서는 확인할 수 없고, 모달에서도 `교재·시험범위·출제 개수·커트라인` 다음에 있어 데이터테이블에서 사용할 정보 순서와 맞지 않는다.

## 2. 목표

- `본시험일`과 분리된 참고용 `응시예정일시`를 저장하고 목록에서 확인한다.
- 담당선생님이 자신의 진행 중 재시험을 어느 단계에서든 찾아 응시예정일시를 수정할 수 있게 한다.
- 본시험일 달력을 `[퇴원]`과 같은 깔끔한 전체 폭 인라인 일정 달력으로 바꾼다.
- 목록에서 메모 내용을 바로 확인한다.
- 모달과 데이터테이블의 정보 순서를 맞춘다.
- 기존 재시험 상태, 점수, 미응시, 재재시험, 알림 동작을 유지한다.

## 3. 비목표

- 응시예정일시를 강제 예약, 출석 약속, 업무 기한 또는 상태 전이 조건으로 사용하지 않는다.
- 응시예정일시 기준 자동 알림이나 미응시 판정을 만들지 않는다.
- 본시험일의 기존 필터와 `+7일` 규칙을 바꾸지 않는다.
- 완료·취소 업무를 다시 편집 가능하게 만들지 않는다.
- 기존 조교·담당선생님 업무 액션 소유권을 바꾸지 않는다.
- 외부 알림 제공자 설정을 활성화하지 않는다.

## 4. 접근안 비교

### 4.1 기존 본시험일 또는 업무 기한 재사용

DB 변경은 작지만 기존 기간 필터, 자동 미응시, 일정 알림과 결합된다. `다른 구속력 없는 참고 메모`라는 요구와 충돌하므로 사용하지 않는다.

### 4.2 메모 문자열 안에 날짜·시간 저장

DB 변경은 피할 수 있지만 날짜·시간을 안정적으로 표시·수정할 수 없고 일반 메모와 섞인다. 목록 열과 날짜·시간 입력기를 만들기에도 부적합하므로 사용하지 않는다.

### 4.3 별도 nullable timestamp — 채택

`ops_word_retests`에 참고용 nullable timestamp를 추가한다. 본시험일과 자동화 계약을 분리하고 기존 생성·수정 RPC의 원자성·권한·stale-write 방어를 재사용할 수 있다.

## 5. 데이터 계약

DB와 앱 모델에 다음 필드를 추가한다.

```ts
type OpsWordRetestDetail = {
  // existing fields...
  expectedRetestAt?: string
}
```

```sql
alter table public.ops_word_retests
  add column expected_retest_at timestamptz;
```

`응시예정일시` 의미는 다음으로 고정한다.

- 학생과 협의한 예상 재시험 날짜·시간
- 선택 입력
- 언제든 지울 수 있음
- 업무 기한·상태·점수·미응시 판정과 무관
- 알림·리마인더와 무관
- 정렬·기간 필터 기준이 아님

서비스의 row mapping, 입력 payload, `buildWordRetestRow`, SQL의 `upsert_ops_task_detail_v2` INSERT·UPDATE 양쪽에서 필드를 보존한다.

적용된 기존 migration은 수정하지 않는다. 신규 migration은 컬럼을 추가하고 `dashboard_private.upsert_ops_task_detail_v2`의 word-retest INSERT·UPDATE 열만 현재 최종 정의를 기준으로 확장한다. public wrapper와 create/update/retry producer 구현은 재정의하지 않는다. 세 생산자가 이미 공통 upsert 함수를 통과하는 구조를 유지해 이전 producer 보강을 덮어쓰지 않는다.

기존 데이터는 backfill하지 않으며 `null`로 표시한다. 별도 인덱스는 만들지 않는다.

## 6. 생성·수정·재재시험

### 6.1 일반 생성

응시예정일시는 비워 둔 채 생성할 수 있다. 입력된 경우 기존 업무와 같은 트랜잭션에서 함께 저장한다.

여러 학생을 동시에 선택하면 학생별 약속 일시가 다를 수 있으므로 생성 폼의 응시예정일시는 비활성화하고 `저장 후 학생별로 입력해 주세요.`를 표시한다. 학생 한 명을 선택했을 때만 생성 시 값을 함께 저장한다.

### 6.2 수정

완료·취소 전 업무는 기존 수정 RPC와 optimistic concurrency를 사용한다. stale-write가 발생하면 최신 데이터를 다시 불러오고 사용자가 다시 저장하도록 안내한다.

응시예정일시 변경만으로 재시험 상태, `updated_at` 외의 업무 필드, 점수, 결과를 바꾸지 않는다.

기존 전체 수정 권한이 있는 단계의 일반 모달 저장은 현재 update RPC를 사용한다. 조교 진행 단계에서 담당선생님이 schedule-only 모드로 저장하거나 표의 응시예정일시 빠른 진입을 사용하는 경우에는 7장의 전용 expected-at RPC를 사용한다.

### 6.3 재재시험

본시험일은 기존 설계대로 원본 값을 기본으로 이어받는다. 응시예정일시는 각 재시험 회차마다 새로 약속하는 참고값이므로 원본 값을 복사하지 않고 빈 값으로 시작한다.

## 7. 담당선생님 화면 노출과 권한

현재 담당선생님 탭은 검토 요청 등 담당선생님 액션 단계만 보여 주므로, 조교 진행 단계에서는 담당선생님이 자신의 업무를 찾지 못할 수 있다.

실제 담당선생님 계정의 `담당선생님` 탭에서는 다음을 적용한다.

- `ops_word_retests.teacher_catalog_id → teacher_catalogs.profile_id = auth.uid()`로 연결된 본인 업무
- 완료·취소 전 모든 재시험 상태
- 현재 상태 배지와 진행 단계 표시
- 기존 상태별 액션 버튼은 그대로 유지

이름 fallback은 화면 라벨에만 사용하고 소유권 판단에는 사용하지 않는다. `teacher_catalog_id` 또는 `profile_id`가 연결되지 않은 기존 업무는 담당선생님 계정에 억지로 노출하지 않고 관리팀 점검 대상으로 표시한다.

관리자·관리팀이 보는 단계별 탭 의미와 실제 조교의 공동 큐는 현재 동작을 유지한다. 담당선생님에게 조교 단계의 시험 시작·점수·결과 액션을 새로 주지 않는다.

담당선생님이 조교 진행 단계의 업무를 열면 전체 수정 모달을 그대로 활성화하지 않는다. 읽기 전용 정보와 `응시예정일시 수정`만 가능한 schedule-only 모드로 연다. 검토 요청 등 기존 담당선생님 액션 단계에서는 현재 전체 수정 흐름을 유지한다.

참고 일시 전용 `public.update_word_retest_expected_at_v1` RPC는 task ID, nullable expected timestamp, expected `updated_at`, request ID만 받는다. 다음만 허용한다.

- admin/staff: 완료·취소 전 재시험
- assistant: 정확히 `requested`, `confirmed`, `in_progress`, `on_hold` 상태의 재시험
- 연결된 담당선생님: 본인의 완료·취소 전 재시험

RPC는 다른 업무·재시험 필드를 입력받지 않고, 연결된 담당선생님 여부와 stale-write를 서버에서 검사한다. 공통 actor 함수만으로 assistant를 통과시키지 않고 위 네 상태를 직접 검사하며 `review_requested`를 거절한다. 이 좁은 mutation으로 담당선생님 노출 범위를 넓혀도 조교 단계 데이터 편집 권한이 함께 넓어지지 않게 한다. 완료·취소 업무는 모든 역할에서 읽기 전용이다.

동시성 revision은 부모 `ops_tasks.updated_at`을 사용한다. RPC는 부모와 자식 행을 같은 트랜잭션에서 잠그고 `p_expected_updated_at`을 비교한 뒤, expected 값이 실제로 달라지면 자식 필드와 부모 `updated_at`을 함께 갱신해 새 revision을 반환한다. 같은 revision의 두 번째 저장은 `40001`로 거절한다. 값이 동일한 멱등 재요청은 request ledger의 최초 응답을 replay한다.

## 8. 본시험일 공통 일정 달력

퇴원 달력 전체를 재시험 도메인에 직접 연결하지 않고, 월 헤더와 7열 날짜 그리드를 표현하는 공통 `ClassScheduleCalendarSurface`를 추출한다.

### 8.1 공통 표면

- 이전 달·다음 달 이동
- 월 제목
- 요일 헤더
- 42개 날짜 셀
- 선택 상태
- 오늘·현재 월·다른 월 tone
- 일정이 있는 날짜의 회차·상태 표현
- 비활성 날짜와 키보드 focus ring

### 8.2 퇴원 래퍼

기존 퇴원일 선택 규칙, 휴강·보강 표시, 퇴원회차·진행률 계산과 하단 지표를 그대로 유지한다.

### 8.3 재시험 래퍼

- 모달 안에 전체 폭으로 표시한다.
- 선택한 수업의 일정이 있으면 해당 수업일만 선택할 수 있다.
- 일정 데이터가 없으면 현재 동작처럼 일반 날짜를 선택할 수 있다.
- 선택하면 `testAt`만 바꾼다.
- 기존 작은 Popover와 하단 `수업일정` 버튼 중복을 제거한다.
- 수업을 선택하지 않았으면 `수업을 먼저 선택하면 등록된 수업일정이 표시됩니다.` 상태를 보여 준다.

공통화는 시각 표면에 한정한다. 퇴원 지표 계산과 재시험 본시험일 의미를 하나의 도메인 로직으로 합치지 않는다.

## 9. 모달 정보 순서

추가·수정 모달의 재시험 입력 순서는 다음과 같다.

1. 담당선생님
2. 수업·학생
3. 전체 폭 본시험일 일정 달력
4. 응시예정일시·장소

### 범위 단계

1. 교재·시험범위
2. 메모
3. 출제 개수·커트라인

메모는 사용자 추가 요청대로 `교재·시험범위` 바로 아래, `출제 개수·커트라인` 위에 둔다. 데이터테이블에서도 같은 의미 순서를 사용한다.

응시예정일시는 기존 `DateTimePickerControl`을 재사용하되, form이 날짜 draft와 시각 draft의 완성 여부를 알 수 있도록 controlled draft 또는 `onDraftStateChange` 계약을 추가한다. 날짜·시각을 모두 선택한 경우에만 값을 만들고, 지우기 동작을 제공한다. 하나만 선택한 불완전 초안은 dirty로 취급하고 `날짜와 시간을 모두 선택해 주세요.` 오류를 표시하며 저장과 확인 없는 닫기를 막는다. 다이얼로그 안에서는 검증된 `disablePortal` 동작을 사용한다.

### 10.1 응시예정일시 열

- 본시험일 바로 오른쪽에 둔다.
- `YYYY-MM-DD HH:mm` 형식으로 정확한 날짜·시간을 표시한다.
- 기존 `dateLabel()`의 `09:00` 숨김 규칙을 사용하지 않는다.
- 값이 없으면 `미정`으로 표시한다.
- 셀 자체를 명시적 button으로 만들고 행 열기 이벤트 전파를 막는다.
- 셀을 누르면 기존 수정 모달이 `응시` 영역으로 열리고 응시예정일시 날짜 trigger에 focus한다.
- 완료·취소 업무의 셀은 수정 모달 대신 읽기 전용 상세를 연다.

테이블 셀 내부에서 즉시 DB 저장하는 편집기는 만들지 않는다. 날짜와 시각의 부분 입력, 모바일 Popover 중첩, 연속 저장의 stale 충돌을 피하면서 한 번의 클릭으로 기존 검증된 수정 흐름에 진입한다.

focus는 pending focus target을 modal state에 저장하고, 모달 mount와 해당 영역 렌더가 끝난 뒤 한 번 소비한다. `DateTimePickerControl`은 날짜 trigger ref 또는 명시적 focus API를 노출하며, focus 후 pending target을 지워 재렌더 때 포커스가 반복 이동하지 않게 한다.

### 10.2 메모 열

- 시험범위 바로 오른쪽에 둔다.
- 값은 `wordRetest.requestNote || task.memo` 순서로 읽어 기존 데이터도 빠뜨리지 않는다.
- 데스크톱은 한 줄 말줄임과 hover·focus 전체보기 툴팁을 제공한다.
- 모바일은 최대 두 줄까지 직접 표시한다.
- 빈 값은 `-`로 표시한다.

수정 모달의 초기값도 같은 fallback을 사용한다. `task.memo`에만 있는 기존 메모를 수정·저장하면 내용을 `wordRetest.requestNote`로 승격해 저장하되 기존 `task.memo`를 자동 삭제하지 않는다. 이후 표·상세·모달은 `requestNote`를 우선 표시한다.

### 10.3 열 너비

- 응시예정일시: 기본 168px, 최소 148px
- 메모: 기본 220px, 최소 160px
- 기존 resizable header 패턴을 유지한다.
- 전체 표는 기존 가로 스크롤 동작을 유지한다.

## 12. 상세 화면

상세 정보에는 다음을 함께 표시한다.

- 본시험일
- 응시예정일시
- 학생
- 교재
- 시험범위
- 메모
- 점수와 결과

응시예정일시는 `미정`도 명시해 조교선생님이 약속 기록 여부를 바로 판단할 수 있게 한다. 메모는 기존 fallback을 유지한다.

## 13. 자동화·알림 경계

`expected_retest_at`은 다음 어디에도 사용하지 않는다.

- `getWordRetestTestDateKey`
- 기간 필터
- `getWordRetestAutoAbsentDeadline`
- `shouldAutoMarkWordRetestAbsent`
- 업무 캘린더의 본시험 항목
- 완료 blocker
- `word_retest.schedule_changed`
- notification payload와 reminder 계산

값 저장으로 일반 row update 이력은 남을 수 있지만, 일정 변경 알림 이벤트나 외부 발송을 만들지 않는다. Google Chat, Web Push, SOLAPI와 notification control-plane 플래그는 변경하지 않는다.

전용 expected-at RPC는 필요하면 일반 감사 이력에 `expected_retest_at` 변경만 기록하되 notification source event는 만들지 않는다.

## 14. 오류·호환성

- 날짜와 시각 중 하나만 선택된 초안은 저장값을 만들지 않는다.
- 잘못된 timestamp는 저장 전에 거절하고 기존 값을 보존한다.
- stale-write는 기존 `40001` 흐름으로 최신 데이터 재조회 후 안내한다.
- 필드 저장 실패 시 모달을 닫지 않고 입력값과 오류를 유지한다.
- 날짜 또는 시각만 고른 초안도 dirty로 감지하고 저장·닫기 확인에서 유실시키지 않는다.
- 신규 migration이 적용되지 않은 DB에 앱을 먼저 배포하지 않는다. DB 컬럼과 producer 함수 preflight 후 앱을 반영한다.
- 기존 null 데이터, 수동 수업, 일정 데이터가 없는 수업에서도 추가·수정 모달을 열 수 있어야 한다.

## 15. 테스트 전략

### 모델·서비스

- `expectedRetestAt` row mapping과 payload 직렬화를 검증한다.
- timestamp를 서울 로컬 입력값과 DB ISO 값 사이에서 정확히 변환한다.
- 재재시험 생성 초안에서는 응시예정일시를 비운다.
- 본시험일 기반 기간 필터와 `+7일` 미응시 규칙이 그대로다.
- 실제 담당선생님은 본인의 완료 전 모든 상태를 볼 수 있다.
- 담당선생님 소유권은 profile 연결만 사용하고 이름 fallback으로 권한을 만들지 않는다.
- 관리자·관리팀의 단계별 큐와 조교 공동 큐는 그대로다.
- 여러 학생 동시 추가에서는 응시예정일시가 비어 있고 학생별 입력 안내가 보인다.

### 워크스페이스 UI

- 열 순서가 설계와 일치한다.
- 본시험일 셀 바로 다음에 응시예정일시가 있다.
- 시험범위 바로 다음에 메모가 있다.
- 모달에서 `교재·시험범위 → 메모 → 출제 개수·커트라인` 순서다.
- 응시예정일시 셀 클릭이 수정 모달의 해당 입력으로 이동한다.
- 조교 단계의 담당선생님은 schedule-only 모드에서 응시예정일시만 바꿀 수 있다.
- 셀 button은 행 열기와 이벤트가 겹치지 않고 focus target을 한 번만 소비한다.
- 완료·취소 셀은 읽기 전용 상세를 연다.
- 메모 fallback, 말줄임·전체보기, 모바일 두 줄 표시를 검증한다.
- legacy `task.memo`는 모달에도 보이고 저장 시 `requestNote`로 승격된다.
- 불완전 날짜·시각 초안은 dirty·오류 상태로 보존된다.
- 본시험일은 Popover가 아니라 공통 인라인 일정 달력을 사용한다.
- 수업 일정이 있을 때 허용일만, 없을 때 일반 날짜를 선택한다.
- 퇴원 달력의 기존 선택·지표 계산에 회귀가 없다.

### SQL

- 신규 컬럼이 nullable timestamptz다.
- create·update·retry producer가 필드를 정확히 저장한다.
- 일반 수정의 optimistic concurrency와 권한 검증이 유지된다.
- 전용 expected-at RPC가 다른 필드를 수정할 수 없고 담당 profile 연결과 역할별 허용 상태를 검증한다.
- 부모 revision을 잠금·비교·갱신해 같은 revision의 동시 저장을 한 건만 허용한다.
- 응시예정일시 변경이 `word_retest.schedule_changed` 이벤트를 만들지 않는다.
- 외부 알림 provider 호출이 0건이다.

### 브라우저

- `/admin/word-retests`의 조교선생님·담당선생님 화면에서 새 열과 메모를 확인한다.
- 담당선생님이 조교 진행 단계의 본인 업무를 찾고 수정 모달을 열 수 있는지 확인한다.
- 추가·수정 모달의 인라인 본시험일 달력, 응시예정일시 입력, 필드 순서를 확인한다.
- `/admin/withdrawal`의 퇴원일 달력 회귀를 확인한다.
- 데스크톱·모바일에서 가로 넘침, 모달 스크롤, Popover 겹침, 키보드 focus를 확인한다.
- production build를 반영한 `localhost:3000`에서 검증하되 실제 운영 업무는 저장하지 않는다.

## 16. 완료 기준

- 본시험일과 응시예정일시가 별도 값으로 저장·표시된다.
- 응시예정일시는 어떤 자동화나 구속력도 갖지 않는다.
- 담당선생님은 본인의 완료 전 재시험을 모든 단계에서 찾아 응시예정일시를 수정할 수 있다.
- 본시험일 달력이 퇴원일과 같은 전체 폭 인라인 표면을 사용한다.
- 표에서 본시험일 바로 오른쪽에 응시예정일시가 있다.
- 표와 모달 모두 `교재·시험범위 → 메모 → 출제 개수·커트라인` 순서를 사용한다.
- 메모를 목록에서 바로 읽을 수 있다.
- 기존 미응시, 점수, 재재시험, 권한, 알림에 회귀가 없다.
