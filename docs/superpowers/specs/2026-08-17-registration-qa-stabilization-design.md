# 등록 메뉴 QA 안정화 설계

## 범위

등록 메뉴의 실제 운영 QA에서 재현된 다섯 가지 문제를 코드와 자동화 테스트로 해결한다. 이 작업은 로컬 소스, 테스트, 로컬 브라우저, 그리고 읽기 전용 운영 확인까지만 포함한다. 운영 DB 변경, 배포, 외부 알림 전송은 포함하지 않는다.

## 목표

1. 목록 읽기의 부가 런타임 점검 실패가 목록 행 자체를 숨기지 않게 한다.
2. 관리자와 상담 담당자가 완료된 상담 결과를 수정할 수 있게 한다.
3. 저장된 상담 방식과 화면의 초기 선택을 일치시켜, 열자마자 잘못된 변경 상태가 생기지 않게 한다.
4. 모든 섹션을 열어 두는 편집 UX와 실제 워크플로의 현재 단계를 분리한다.
5. 기존 청강 예약과 같은 반·회차를 다시 저장할 수 없게 한다.

## 설계

### 1. 목록 읽기 부분 실패 격리

`loadOpsTaskPage`는 목록 RPC를 필수 경계로 유지한다. 등록 런타임 점검은 목록과 병렬로 수행하되, 점검이 거부되거나 시간 초과되면 목록 행을 버리지 않고 `null` 런타임 상태를 반환한다. UI는 목록을 계속 표시하고 청강 전용 기능만 기존의 fail-closed 상태를 사용한다.

목록 RPC 자체 오류는 기존처럼 목록 오류로 처리한다. 통계 RPC 실패가 목록을 막지 않는 현재 원칙과 동일하게, 독립적인 런타임 점검도 목록 가용성을 낮추지 않는다.

### 2. 상담 결과 편집 권한

상담 결과 편집기는 현재 `canCompleteConsultation` 또는 `canEditConsultationResult`만 전달받는다. 관리 권한이 있는 사용자는 결과 편집기가 보이지만 비활성화되는 불일치가 있으므로, 전달 권한을 `canManage || canCompleteConsultation || canEditConsultationResult`로 통일한다.

서버 저장 RPC의 권한 검증은 변경하지 않는다. UI는 서버 권한을 우회하지 않으며, 거절 시 기존의 안전한 오류 안내를 유지한다.

### 3. 상담 방식 초기값

상담 방식의 저장 기준은 활성 방문 예약 유무만으로 정하지 않는다. 활성 예약이 있으면 방문상담이며, 그렇지 않으면 가장 최근의 취소되지 않은 상담 기록의 `mode`를 사용한다. 기록이 없을 때만 전화상담을 기본값으로 둔다.

이 값은 드래프트의 dirty 비교 기준에도 사용한다. 완료된 방문상담을 열 때 전화상담 버튼이 선택되거나 저장 버튼이 불필요하게 활성화되지 않는다.

### 4. 열려 있는 섹션과 현재 단계 분리

관리자에게 모든 섹션을 편집 가능하게 하는 기존 UX는 유지한다. 다만 `openSectionStates`가 모든 섹션을 `current: true`로 덮어쓰는 동작을 제거한다. 각 섹션의 `current` 값은 워크플로에서 계산된 원래 상태를 보존하고, `editable`과 잠금 안내만 관리 권한에 맞게 확장한다.

따라서 스크린 리더와 상태 레이블은 정확한 현재 단계 하나만 읽고, 관리자는 필요한 이전 정보를 계속 수정할 수 있다.

### 5. 청강 예약 무변경 저장 차단

청강 편집기는 현재 예약의 `classId`와 정규화된 회차 식별자를 선택값과 비교해 `bookingDirty`를 계산한다. 저장은 새 예약이거나 선택값이 달라진 경우에만 가능하다. 같은 값이면 버튼은 `저장됨`으로 표시하고 확인 대화상자도 열지 않는다.

비교는 정규 회차의 `classLessonSessionId`와 레거시 회차의 `legacySessionKey`를 기존 `sessionValue` 함수로 정규화해 수행한다. 예약 취소와 알림 미리보기 경계는 변경하지 않는다.

## 테스트

각 변경은 구현 전에 실패 테스트를 작성한다.

- 등록 런타임 점검 거부 시에도 목록 RPC 행이 반환되는 서비스 테스트
- 관리자 권한이 완료된 상담 결과 편집을 활성화하는 편집기 계약 테스트
- 완료된 방문상담이 방문상담으로 초기화되고 clean 상태를 유지하는 모델 테스트
- 관리 편집 상태에서도 한 섹션만 현재 단계로 유지되는 모델/쉘 테스트
- 같은 청강 반·회차의 저장이 차단되고 변경된 회차만 저장 가능해지는 편집기 모델 테스트

검증은 대상 테스트, 전체 등록 테스트, 린트, `pnpm build`, 로컬 브라우저 QA 순서로 한다. 테스트 의존성 오류가 남으면 제품 회귀와 별도로 기록하고 복구한다.

## 비목표

- 목록 RPC 또는 Supabase 스키마 재설계
- 외부 알림 발송·재시도·설정 변경
- 운영 DB 마이그레이션 적용 또는 프로덕션 배포
- 실제 학생 또는 예약 데이터의 저장·취소·상태 변경
