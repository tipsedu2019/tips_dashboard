# 수업 날짜 정규화 및 저장 경계 강화 설계

## 상태

2026-08-16 사용자 승인 완료.

## 문제

운영 `classes.start_date`에는 정식 ISO 날짜가 아닌 문자열 52건이 남아 있다.

- `2024년 01월 31일`: 2건
- `20260101`: 47건
- `20260102`: 1건
- `20260301`: 2건

`classes.start_date`와 `classes.end_date`는 `text`이고, 기존 저장 경로에는 형식/달력 유효성 제약이 없었다. 2026-08-14 추가된 시간표·수업계획 RPC가 이 값을 `date`로 직접 변환하면서 PostgreSQL `22007`이 발생했다. Supabase 오류는 JavaScript `Error` 인스턴스가 아닌 구조화 객체인데 화면이 이를 무시하여 `Unknown error`만 표시했다.

## 목표

1. 확인된 52건만 명시적으로 ISO `YYYY-MM-DD`로 정규화한다.
2. 이후 잘못된 날짜가 다시 저장되지 않게 데이터베이스 경계에서 차단한다.
3. 시간표와 수업계획 RPC가 정규화된 데이터에서 정상 동작함을 회귀 테스트한다.
4. 구조화된 Supabase 오류도 실제 메시지로 표시한다.
5. 소스·테스트, 운영 마이그레이션, 운영 RPC, GitHub `main`/Vercel, 운영 UI를 별도 게이트로 검증한다.

## 데이터 마이그레이션

새 Supabase migration은 다음 정확한 변환만 수행한다.

| 기존 값 | 정규화 값 | 예상 건수 |
| --- | --- | ---: |
| `2024년 01월 31일` | `2024-01-31` | 2 |
| `20260101` | `2026-01-01` | 47 |
| `20260102` | `2026-01-02` | 1 |
| `20260301` | `2026-03-01` | 2 |

마이그레이션은 변경 전에 대상 값이 하나라도 있으면 각 값과 합계가 위 예상과 정확히 같은지 확인한다. 다르면 즉시 중단하여 새 데이터나 범위 드리프트를 임의로 고치지 않는다. 신규/테스트 DB처럼 네 값이 모두 0건이면 데이터 변경 없이 제약만 설치한다. 변경 후에는 운영 경로에서 수정 건수가 52건인지, 비어 있지 않은 모든 시작일/종료일이 유효한 정식 ISO 날짜인지 다시 확인한다.

## 저장 제약

기존 애플리케이션 호환성을 위해 이번 변경에서 컬럼 타입은 `text`로 유지한다. 대신 `dashboard_private`에 immutable 날짜 검증 함수를 두고 `classes.start_date`, `classes.end_date`에 CHECK 제약을 추가한다.

허용 값:

- `NULL`
- 공백 문자열(기존 선택값 없음 의미 유지)
- 실제 달력에서도 유효한 `YYYY-MM-DD`

거부 값:

- `YYYYMMDD`, 한글 날짜, 슬래시 날짜 등 비표준 형식
- `2026-02-30`처럼 형식만 맞고 실제로 존재하지 않는 날짜

제약은 모든 쓰기 경로에 동일하게 적용되어 UI/API/RPC 중 어느 경로에서도 다시 잘못된 값을 저장할 수 없게 한다.

## RPC 및 테스트

기존 시간표·수업계획 RPC는 정식 값이 보장되면 안전하게 변환할 수 있다. 적용된 과거 migration을 수정하지 않고 새 migration과 pgTAP 회귀 fixture로 다음을 검증한다.

- 정규화 대상 형식은 migration 이후 남지 않는다.
- 두 RPC가 정규화된 과거 시작일을 포함해 오류 없이 결과를 반환한다.
- 시작일과 종료일 모두 잘못된 형식/달력 날짜 저장을 거부한다.
- `NULL`, 공백, 유효 ISO 날짜는 계속 허용한다.

## 오류 표시

공용 오류 메시지 추출 함수를 추가한다. 우선순위는 다음과 같다.

1. `Error.message`
2. 구조화 객체의 비어 있지 않은 `message`
3. 비어 있지 않은 `details`
4. 지정된 한국어 fallback

시간표·수업계획 데이터 훅과 인접 운영 데이터 훅에서 이 함수를 사용해 `Unknown error`를 제거한다. 민감한 객체 전체나 stack은 화면에 노출하지 않는다.

## 배포 및 안전 경계

- 기존 적용 migration은 수정하지 않는다.
- 외부 메시지, SOLAPI, Google Chat 설정/발송은 변경하지 않는다.
- 로컬 변경을 검증한 뒤 운영 Supabase migration을 적용한다.
- 운영 RPC 정상화를 확인한 뒤 GitHub `main`에 반영하고 Vercel Production `READY`를 별도로 확인한다.
- 마지막으로 로그인된 운영 UI에서 시간표와 수업계획을 각각 확인한다.
- 각 게이트가 실제로 통과하기 전에는 전체 완료로 보고하지 않는다.
