# 등록 당일 고객 리마인드 및 상태 UI 설계

**작성일:** 2026-08-16

**상태:** 사용자 방향 승인 완료 · 문서 검토 대기

**대상:** 등록 예약 섹션, SOLAPI 고객 리마인드 자동화, 환경 설정의 Google Chat 알림 규칙 화면

## 1. 목표

1. 고객 예약 리마인드 알림톡은 예약 당일 오전 10시(KST)에 자동 발송한다.
2. 당일 전에 확정된 레벨테스트·방문상담 예약만 리마인드 대상으로 삼는다.
3. 당일 신규 예약과 당일 일정 변경은 예약 안내 알림톡과 중복되므로 리마인드를 발송하지 않는다.
4. 등록 화면에서 수동 `리마인드 알림톡` 버튼을 제거하고 예약별 예정·처리·결과 상태만 읽기 전용으로 표시한다.
5. 환경 설정에서 더 이상 운영하지 않는 Google Chat 예약 리마인드 규칙과 모든 규칙에 공통인 `시점` 표시를 제거한다.
6. 하루 한 번 실행하되 당일 대상 전체를 안전한 제한 배치로 처리한다.

## 2. 비목표

- 예약 저장 직후 보내는 `예약 안내 알림톡`의 미리보기·수동 확인 흐름은 변경하지 않는다.
- 고객 SOLAPI 리마인드 자체를 폐기하지 않는다.
- 실패·불명 상태를 자동으로 재발송하지 않는다.
- 과거 알림톡 메시지, 공급자 증빙, 감사 이력을 삭제하지 않는다.
- Google Chat의 즉시 업무 알림이나 연결 설정을 변경하지 않는다.

## 3. 확인된 현재 구조와 문제

- 고객 리마인드 설정은 `lead_hours`를 사용해 `예약시각 - N시간`을 도래 시각으로 계산한다.
- 기본값은 3시간이지만 운영값은 `enabled=true`, `lead_hours=48`, revision 2다.
- 운영값은 2026-08-14 20:01 KST에 관리자 저장으로 변경됐으며 저장 사유는 별도 기록되지 않았다.
- 크론은 과부하 대응으로 매일 오전 10시 한 번 실행하도록 바뀌었지만, 시간 차감 기반 생산자와 한 번에 한 건만 처리하는 worker는 그대로 남았다.
- 따라서 현재 구현은 `오전 10시에 오늘 예약 전체 확인`이라는 운영 규칙과 일치하지 않는다.
- 등록 예약 섹션의 `리마인드 알림톡` 버튼은 자동 상태를 보여 주는 것이 아니라 수동 미리보기·발송 대화상자를 연다.
- 환경 설정은 비활성 Google Chat 예약 리마인드 세 규칙을 계속 표시하고, 그 규칙 때문에 모든 업무에 `시점` 열을 노출한다.

## 4. 검토한 방식

### 4.1 채택: 고정 당일 배치 + 예약별 읽기 전용 상태

매일 오전 10시 KST에 당일 예약을 조회하고, 전날까지 현재 일정이 확정된 예약만 제한 배치로 처리한다. 등록 화면에는 수동 발송 버튼 대신 해당 예약의 자동 리마인드 상태 한 줄을 표시한다.

이 방식은 예약 안내와 리마인드의 역할을 분리하고, 사용자가 해야 할 행동이 없는 자동 기능을 버튼처럼 보이게 하지 않는다.

### 4.2 기각: `lead_hours` 값만 변경

1시간, 14시간, 24시간 등으로 바꿔도 예약 시각마다 도래 시각이 달라져 `당일 오전 10시` 계약이 되지 않는다. 하루 한 번 실행하는 worker가 한 건만 처리하는 문제도 해결하지 못한다.

### 4.3 기각: 수동 버튼 유지 + 자동 상태 병기

동일한 예약에 자동·수동 발송 진입점이 함께 남아 중복 발송 기대와 운영 혼선을 만든다. 기존 중복 잠금이 있더라도 잘못된 행동을 유도하는 UI를 유지할 이유가 없다.

### 4.4 기각: 별도 리마인드 관리 화면

예약별 상태를 확인하려고 별도 화면으로 이동해야 하며 현재 등록 흐름보다 복잡하다. 각 예약 섹션 안의 한 줄 상태로 충분하다.

## 5. 자동 발송 계약

### 5.1 실행 시각

- 크론 표현식은 `0 1 * * *` UTC, 즉 매일 오전 10시 KST를 유지한다.
- 시간 전 입력과 `lead_hours` 기반 운영 설정은 제거한다.
- 발송 예정 시각은 예약 날짜의 오전 10시 KST로 서버에서 계산한다.

### 5.2 대상 조건

오전 10시 실행 시 다음 조건을 모두 만족하는 예약만 대상으로 삼는다.

1. 예약 종류가 레벨테스트 또는 방문상담이다.
2. 예약 상태가 `scheduled`다.
3. `scheduled_at`의 KST 날짜가 실행일과 같다.
4. 현재 예약 일정의 최종 확정·변경 시각이 실행일 KST 00:00보다 이르다.
5. 같은 예약의 `appointment_reminder` 발송 기록이 없다.
6. 현재 예약 revision과 작업의 source revision이 일치한다.
7. 승인된 SOLAPI 템플릿·활성화·수신 대상 계약이 유효하다.

`ops_registration_appointments`에 `schedule_confirmed_at timestamptz not null`을 추가한다. 신규 예약에서는 생성 시각을 기록하고, 기존 예약에서는 `scheduled_at` 또는 `place`가 실제로 변경될 때만 갱신한다. 상태 변경이나 알림 처리처럼 예약 사실과 무관한 수정은 이 시각을 바꾸지 않는다. 기존 행은 보수적으로 `updated_at`으로 backfill해 당일에 수정된 이력이 불명확한 예약을 자동 발송하지 않는다.

### 5.3 당일 신규·변경 예약

- 당일 00:00 이후 새로 만든 예약은 리마인드 대상이 아니다.
- 이전에 만든 예약이라도 당일 일정 또는 장소를 변경하면 리마인드 대상이 아니다.
- 해당 변경은 기존 `예약 안내 알림톡` 흐름으로 안내한다.
- 화면에는 `리마인드 대상 아님 · 오늘 예약` 또는 `리마인드 대상 아님 · 오늘 변경`을 표시한다.

### 5.4 배치와 중복 방지

- 한 HTTP 호출에서 한 건만 처리하는 `runOnce()`를 그대로 하루 한 번 호출하지 않는다.
- 한 실행은 최대 처리 건수와 최대 실행 시간을 가진 bounded batch로 반복 claim한다.
- 대상이 상한보다 많으면 동일 세대의 후속 호출을 한 번만 예약해 남은 작업을 이어간다.
- appointment 단위 unique 작업과 기존 메시지 중복 잠금을 유지한다.
- `accepted`, `unknown`, provider attempt marker가 있는 건은 자동 재발송하지 않는다.
- 예약 취소·완료·revision 변경은 공급자 호출 직전 다시 확인한다.

## 6. 등록 예약 섹션 UI

### 6.1 동작

- `예약 안내 알림톡` 버튼은 유지한다.
- `리마인드 알림톡` 버튼과 수동 `appointment_reminder` 대화상자 진입점을 제거한다.
- 저장 버튼 아래 또는 예약 안내 버튼과 같은 결과 영역에 읽기 전용 리마인드 상태 한 줄을 표시한다.
- 상태는 별도 polling 없이 등록 상세 조회 응답에 포함한다. 저장·발송 후 사용자가 상세를 새로 불러올 때 최신 상태를 받는다.

### 6.2 표시 상태

| 서버 상태 | 화면 문구 | 사용자 동작 |
| --- | --- | --- |
| `scheduled` | `{M월 D일} 오전 10시 발송 예정` | 없음 |
| `not_applicable_same_day_created` | `리마인드 대상 아님 · 오늘 예약` | 없음 |
| `not_applicable_same_day_changed` | `리마인드 대상 아님 · 오늘 변경` | 없음 |
| `processing` | `리마인드 발송 처리 중` | 없음 |
| `sent` | `리마인드 발송 완료 · {실제 시각}` | 없음 |
| `unknown` | `리마인드 발송 결과 확인 필요` | 공급자 확인은 기존 관리자 증빙 경계에서 수행 |
| `failed_hold` | `리마인드 발송 안 됨 · 확인 필요` | 자동 재시도 없음 |
| `canceled` 또는 종료된 예약 | 표시하지 않음 | 없음 |

단순 badge나 별도 카드 설명은 만들지 않는다. 한 줄의 상태만으로 예정·결과를 이해할 수 있게 한다.

### 6.3 조회 계약

등록 상세 RPC는 각 appointment에 비밀정보 없는 `customerReminder` 요약을 추가한다.

- `state`: 위 닫힌 상태 vocabulary
- `scheduledFor`: 발송 예정 시각 또는 null
- `sentAt`: 공급자 접수 확정 시각 또는 null
- `updatedAt`: 상태가 마지막으로 바뀐 시각

전화번호, 템플릿 본문, provider message ID, 내부 claim token은 등록 상세에 포함하지 않는다. 여러 과목이 하나의 공유 appointment를 가리키면 동일한 reminder 요약을 재사용한다.

## 7. 환경 설정 UI

- `registration.appointment_reminder_due` Google Chat 규칙은 규칙 표와 모바일 카드에서 렌더하지 않는다.
- 서버의 과거 event key와 전달 이력은 감사·판독을 위해 보존하지만 신규 Google Chat 예약 리마인드는 활성화할 수 없게 유지한다.
- 데스크톱 규칙 표의 `시점` 열과 모든 `즉시` 셀을 제거한다.
- 모바일 카드의 시점 문구도 제거한다.
- 예약 시각 라벨 helper와 예약 시각 편집 UI를 제거한다.
- SOLAPI 고객 리마인드는 이 Google Chat 규칙 표에서 관리하지 않는다.
- SOLAPI 설정 화면에서는 시간 입력을 제거하고 `매일 오전 10시 · 당일 이전 예약만`을 읽기 전용 운영 계약으로 보여 준다.

## 8. 오류와 안전 경계

- 업무 예약 저장은 리마인드 worker나 provider 실패 때문에 rollback하지 않는다.
- 리마인드 작업과 예약 원본은 독립적으로 저장한다.
- provider 호출 전 source eligibility와 중복 잠금을 다시 확인한다.
- provider 결과가 불명확하면 `unknown`으로 마감하고 자동 재시도하지 않는다.
- 하루 실행 실패 시 같은 날 무제한 recovery polling을 만들지 않는다. 관리 화면의 상태와 운영 로그로 실패를 확인하고 별도 승인된 복구만 수행한다.
- 당일 예약·변경 제외 판정은 KST 달력일을 사용하고 DB/session timezone에 의존하지 않는다.

## 9. 마이그레이션과 기존 데이터

- 현재 `lead_hours=48`을 단순히 다른 숫자로 바꾸지 않는다.
- 새 당일 배치 계약을 배포하기 전까지 기존 설정을 임의 변경하거나 provider를 호출하지 않는다.
- 새 계약 적용 시 미래 `pending` 작업은 현재 예약 기준으로 다시 계산한다.
- 당일 신규·변경으로 판정되는 기존 pending 작업은 provider 호출 없이 `canceled`로 마감한다.
- 이미 `accepted`, `unknown`, `failed_hold`인 메시지와 공급자 증빙은 보존한다.
- 기존 Google Chat 예약 리마인드 규칙은 비활성 상태를 검증하고 UI에서 제외한다. 역사 행은 삭제하지 않는다.

## 10. 테스트

### 10.1 DB 계약

- KST 날짜 경계 직전·직후 예약 생성
- 전날 확정한 당일 예약은 대상
- 당일 신규 예약은 제외
- 전날 예약 후 당일 일정·장소 변경은 제외
- 전날 일정 변경은 대상
- 취소·완료·과거 예약 제외
- 동일 appointment 중복 발송 방지
- 이미 provider attempt가 시작된 건 자동 재발송 방지
- batch 상한과 후속 호출 coalescing

### 10.2 서버·worker

- 한 호출이 여러 eligible job을 상한까지 처리
- provider 이전 source revision 재검증
- 일부 건 실패가 다른 안전한 건의 처리를 무제한 막지 않음
- unknown/failed_hold 자동 재시도 없음
- 비밀정보 없는 reminder summary 직렬화

### 10.3 UI

- 수동 `리마인드 알림톡` 버튼과 appointment reminder dialog target이 없음
- 예약 안내 알림톡 버튼은 유지
- 각 상태 문구와 예정·완료 시각 표시
- 공유 appointment 상태 중복 조회 없음
- 환경 설정의 예약 알림 행·`시점` 열·모바일 시점 문구·시간 편집기 없음
- Google Chat 즉시 규칙 편집과 연결 관리는 유지

### 10.4 운영 검증

- source/tests
- Supabase migration 적용과 exact cron `0 1 * * *`
- GitHub `main`과 Vercel Production `READY`
- 인증된 등록 상세에서 버튼 제거와 상태 표시
- 인증된 환경 설정에서 예약 규칙·시점 제거
- worker 실행은 provider-zero 또는 승인된 무발송 검증부터 수행
- 실제 고객 발송·수신 확인은 별도 승인과 예약 대상이 있는 날의 독립된 최종 단계로 남긴다.

## 11. 기준선 참고

설계 작성 전 관련 테스트에서 알림 UI, 고객 리마인드 스케줄러, 고객 리마인드 worker 테스트는 통과했다. `tests/registration-track-workspace.test.mjs`에는 현재 `main`의 상담 편집기 계약과 맞지 않는 기존 실패 2건이 있으며 본 설계 구현 전에 기준선 이슈로 분리해 다룬다.
