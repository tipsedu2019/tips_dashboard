# 대시보드 실행형 일정 충돌 경고 설계

**작성일:** 2026-07-23
**상태:** 상세 설계 검토 요청

## 1. 배경

대시보드는 시험 일정 충돌 일부를 계산하지만 현재 경고는 통계 필터와 KPI 아래에 있고, 시험 충돌만 제한적으로 보여 준다. 선생님·강의실·학생 시간표 충돌 데이터는 위험 건수에만 반영되어 실제 문제와 해결 주체를 확인하기 어렵다.

경고 행에는 정적인 조치 문구만 있으며, 해결 업무를 `[할 일]`에 옮기려면 사용자가 다시 내용을 작성해야 한다. 같은 충돌을 여러 사용자가 반복 등록하는 것도 막지 못한다.

상단 과목·부서 필터는 외곽 테두리와 내부 segmented control 테두리가 중첩되어 화면을 복잡하게 만든다.

## 2. 목표

- 페이지 콘텐츠의 가장 위에서 학원 전체 일정 충돌을 놓치지 않고 확인한다.
- 시험일, 선생님, 강의실, 학생 시간표 충돌을 하나의 공통 형식으로 보여 준다.
- 각 충돌에서 `무슨 문제인지`, `누가 처리할지`, `어떻게 처리할지`를 바로 이해한다.
- 한 번의 클릭으로 충돌 해결 업무를 `[할 일]`에 등록한다.
- 같은 충돌에서는 사용자·탭·브라우저·새로고침과 관계없이 영구적으로 업무 한 건만 생성한다.
- 상단 필터의 불필요한 바깥 테두리만 제거한다.

## 3. 비목표

- 충돌을 자동으로 수정하거나 수업 일정을 자동 변경하지 않는다.
- 업무 생성과 동시에 Google Chat, Web Push, SOLAPI 등의 외부 알림을 보내지 않는다.
- 기존 시험·수업·학생 데이터를 일괄 수정하지 않는다.
- KPI, 학생 분포, 수업 운영의 집계 의미를 바꾸지 않는다.
- 공통 `Card`, `Alert`, `Button` 스타일을 전역 변경하지 않는다.

## 4. 화면 순서와 필터 관계

대시보드 본문 순서는 다음으로 고정한다.

1. 일정 충돌 경고
2. 과목·부서 필터
3. KPI 통계
4. 학생 분포·수업 운영

일정 충돌 경고는 통계 필터와 무관한 학원 전체 기준이다. 필터가 경고 아래에 있으므로 필터 변경이 경고를 숨기거나 바꾸지 않아야 한다. 영어·수학·과학과 모든 부서의 실제 수업 데이터를 포함한다.

충돌이 0건이고 모든 충돌 원천이 정상 조회된 경우에만 경고 영역 전체를 숨긴다. 선택적 시험 테이블 조회가 실패하거나 시간 초과되면 빈 배열로 바꾸지 않고 `schedule: ready | error`, `exam: loading | ready | error` 상태를 별도로 반환한다. 시간표 충돌은 먼저 보여 줄 수 있지만, 시험 원천이 실패한 경우 경고 상단에 `시험 일정 충돌을 확인하지 못했습니다.`와 재시도 동작을 남긴다.

과목·부서 필터에서는 외곽 `border`와 장식용 배경만 제거한다. 각 segmented control의 선택 상태, focus ring, 내부 경계는 유지한다.

## 5. 충돌 범위

### 5.1 시험 일정

시험 충돌 규칙은 다음과 같다.

| 상황 | 판정 |
| --- | --- |
| 수업일이 해당 과목 시험일과 같음 | 충돌 |
| 다음 날 시험 과목에 현재 수업 과목이 하나라도 포함됨 | 전날 수업 가능 |
| 다음 날 시험 과목이 모두 현재 수업과 다른 과목임 | 충돌 |

예를 들어 다음 날 영어와 수학 시험이 함께 있고 현재 수업이 영어라면 전날 영어 수업은 가능하다. 다음 날 시험이 수학과 과학뿐이고 현재 수업이 영어라면 전날 영어 수업은 충돌이다.

기존 `same-day-subject`, `day-before-other-subject` 분류를 유지하되, 같은 수업에 여러 시험·학생 충돌이 있으면 실제 충돌 단위로 평탄화한다.

시험 충돌은 오늘 이후의 수업일만 경고한다. 이미 지난 일회성 시험 충돌은 현재 해결할 수 있는 일정 경고에서 제외한다.

### 5.2 선생님 중복

동일 선생님이 겹치는 시간에 둘 이상의 수업을 담당하면 한 충돌로 표시한다. 수업 쌍의 순서가 바뀌어도 같은 충돌이어야 한다.

### 5.3 강의실 중복

동일 강의실에 겹치는 시간의 수업이 둘 이상 배정되면 한 충돌로 표시한다. 강의실이 비어 있거나 미정인 수업은 강의실 충돌에서 제외한다.

### 5.4 학생 시간표 중복

동일 학생이 겹치는 시간에 둘 이상의 수업에 등록되어 있으면 한 충돌로 표시한다. 같은 학생·시간·수업 쌍은 한 건으로 중복 제거한다.

선생님·강의실·학생 충돌은 현재 데이터처럼 요일과 시간으로 반복되는 주간 충돌이다. 안정 키에는 임의의 이번 주 날짜를 넣지 않고 `요일+겹치는 시간 구간`을 사용한다. 표시·정렬·업무 기한에는 Asia/Seoul 기준 다음 발생일을 계산해 사용한다.

## 6. 공통 충돌 행 계약

UI에 전달하는 충돌은 다음 공통 형태로 정규화한다.

```ts
type DashboardConflictRow = {
  key: string
  type: "exam" | "teacher" | "classroom" | "student"
  occurrenceKind: "dated" | "weekly"
  title: string
  nextOccurrenceAt: string
  recurrenceDay: string
  problem: string
  ownerLabel: string
  resolution: string
  classIds: string[]
  classNames: string[]
  affectedStudentIds: string[]
  subject: string
  campus: string
  primaryAssigneeProfileId: string
  secondaryAssigneeProfileId: string
  assigneeTeam: string
}
```

- 충돌 건수는 수업 개수가 아니라 정규화된 실제 충돌 행 개수다.
- 이름은 화면 설명에만 사용하며, `key`는 안정적인 수업·학생 ID와 날짜·시간을 사용한다.
- 수업 쌍과 관련 ID는 정렬한 뒤 키를 만든다.
- 선생님·강의실 표시명 변경이나 배열 순서 변경으로 같은 충돌의 키가 달라지면 안 된다.
- 충돌 날짜·시간 또는 관련 수업 자체가 바뀌면 새로운 충돌로 본다.
- 주간 충돌은 `nextOccurrenceAt`이 매주 바뀌어도 같은 키를 유지한다.
- 모든 날짜·시간 정규화와 다음 발생일 계산은 `Asia/Seoul`을 기준으로 한다.

키 예시는 다음 구조를 따른다.

```text
exam:v1:<class-id>:<date>:<rule>
teacher:v1:<weekday>:<overlap-start>:<overlap-end>:<sorted-class-ids>
classroom:v1:<weekday>:<overlap-start>:<overlap-end>:<sorted-class-ids>
student:v1:<student-id>:<weekday>:<overlap-start>:<overlap-end>:<sorted-class-ids>
```

키는 `충돌을 일으킨 운영 단위`를 식별한다. 시험은 같은 수업·날짜·규칙을 한 건으로 묶고, 선생님·강의실은 같은 수업 쌍·요일·겹침 구간을 한 건으로 묶는다. 따라서 레거시 선생님명·강의실명이 바뀌거나 시험에 영향받는 학생 집합이 조금 달라져도 같은 운영 충돌은 같은 키를 유지한다. 반대로 관련 수업 쌍이나 겹침 구간이 바뀌면 새 충돌이다.

현재 계산 단계에서 버리는 원천 ID는 키와 별개로 잠금·최신 상태 재검증을 위해 다음처럼 보존한다.

- 시험: event/detail ID가 있으면 함께 전달한다. 없으면 학교 ID·시험일·과목 원천 행을 조회해 검증한다.
- 선생님: 수업의 teacher catalog/profile ID를 우선 보존한다. 카탈로그가 없는 기존 데이터는 두 수업 행을 잠그고 정규화된 선생님명이 실제로 같은지 서버에서 다시 검증한다.
- 강의실: classroom catalog ID를 우선 보존한다. 카탈로그가 없는 기존 데이터는 두 수업 행을 잠그고 정규화된 지점·강의실명이 실제로 같은지 서버에서 다시 검증한다.
- 학생·수업: 실제 UUID를 사용한다.

표시명과 이름 fallback은 키에 직접 섞지 않으며 담당자 profile UUID 권한 판단에도 사용하지 않는다. 미연결 이름만으로 충돌을 판정한 경우에도 안정 키는 두 수업 UUID를 사용하므로 이름 수정이 영구 한 건 보장을 깨지 않는다.

## 7. 경고 UI

경고는 지속형 `Alert` 표면으로 렌더링한다. 중첩 Card나 설명용 보조 카드는 만들지 않는다.

### 7.1 요약

- 제목: `일정 충돌 N건`
- 기본 상태: 가장 임박한 3건
- 확장: `전체 보기`
- 접기: `접기`
- 정렬: 충돌 일시 오름차순, 같은 시각이면 시험 → 선생님 → 강의실 → 학생 순서

### 7.2 행 내용

각 행에는 다음 정보만 표시한다.

- 충돌 유형과 일시
- 문제: 겹친 수업·시험·사람
- 담당: 담당선생님 또는 관리팀
- 처리: 가장 직접적인 다음 행동
- 업무 버튼

권장 처리 문구는 유형별로 다음을 기본값으로 사용한다.

- 시험: 수업일 변경 또는 휴강·보강 확정 후 학생·보호자 안내
- 선생님: 한 수업의 시간 또는 대체 선생님 확정
- 강의실: 한 수업의 강의실 또는 시간 변경
- 학생: 두 담당선생님이 우선 수업과 보강 방안 확정

### 7.3 담당자

- 시험 충돌: 해당 수업 담당선생님
- 선생님 충돌: 중복 배정된 선생님
- 강의실 충돌: 관리팀
- 학생 충돌: 두 수업 담당선생님을 주·보조 담당으로 지정

`teacher_catalogs.profile_id`가 있는 경우에만 프로필 UUID를 담당자로 저장한다. 카탈로그 ID를 업무 담당자 ID로 사용하지 않는다. 담당 프로필을 찾지 못하면 `관리팀`으로 배정하고 메모에 원래 담당선생님 이름을 남긴다.

## 8. 원클릭 할 일 생성

생성되는 업무는 기존 일반 업무 생산자와 같은 계약을 사용한다.

- 유형: `general`
- 제목: `[일정 충돌] {충돌 요약}`
- 우선순위: `high`
- 담당자·담당팀: 7.3의 매핑 결과
- 수업·과목·지점: 충돌 데이터에서 가능한 값을 연결
- 기한: `nextOccurrenceAt` 전날 18:00. 이미 그 시각이 지났거나 충돌이 임박한 경우 오늘 23:59로 둔다.
- 메모: 충돌 키, 일시, 관련 수업, 문제, 담당, 권장 처리 순서

전용 충돌 생산자는 일반 업무와 같은 입력·권한 검증을 사용하지만 `task.created` notification source event를 만들지 않는 no-notify 경로를 사용한다. 업무 생성 성공은 알림 발송 성공과 결합하지 않는다. 이번 범위에서 알림 dispatch API를 호출하거나 제공자 플래그를 변경하지 않는다.

## 9. 영구 중복 방지

클라이언트 상태나 `sessionStorage`만으로는 새 탭·다른 사용자·성공 후 재클릭을 막을 수 없으므로 전용 DB 연결 레지스트리를 사용한다.

```sql
dashboard_private.dashboard_conflict_task_links (
  conflict_key text primary key,
  task_id uuid not null unique references public.ops_tasks(id) on delete restrict,
  conflict_type text not null,
  created_by uuid not null references public.profiles(id),
  created_at timestamptz not null default now()
)
```

### 9.1 생성 RPC

`public.create_dashboard_conflict_task_v1(p_conflict jsonb, p_request_id uuid)`은 다음을 한 트랜잭션에서 수행한다.

1. 인증 사용자와 입력을 검증한다.
2. 허용된 `admin`, `staff`, `teacher` 역할인지 확인한다.
3. type, occurrence kind, UUID 형식, 날짜·요일·시간 형식처럼 DB 상태와 무관한 입력 모양을 검증한다.
4. 타입·정렬된 수업/학생 ID·날짜 또는 요일/겹침 구간으로 versioned candidate key와 request fingerprint를 만든다. 요청 원장에서 같은 actor·request ID·fingerprint의 완료 응답이 있으면 원천 상태를 다시 검사하기 전에 최초 응답을 그대로 replay한다. 같은 request ID에 다른 fingerprint가 오면 거절한다.
5. 신규 요청만 candidate key의 transaction advisory lock을 획득한다.
6. 관련 원천 행을 `schema.table, primary key` 순서로 고정해 잠근다. 수업·수업일정·등록 학생 행과, 시험 충돌이면 시험 parent event 및 detail 행을 포함한다. 시험 parent 잠금은 같은 이벤트 detail의 동시 추가도 직렬화한다.
7. 잠근 원천 행에서 충돌을 다시 계산한다. 서버 canonical key가 candidate key와 다르거나 충돌 관계가 사라졌으면 `dashboard_conflict_stale`로 거절한다. 클라이언트가 임의 키를 직접 지정하지 못한다.
8. 서버가 잠근 최신 원천 데이터에서 제목·메모·담당 profile을 만들고, 업무 type=`general`, status=`requested`, priority=`high`, requestedBy=`auth.uid()`를 강제한다.
9. 기존 연결이 있으면 새 업무를 만들지 않고 호출자의 업무 열람 가능 여부까지 계산해 기존 연결 상태를 반환한다.
10. 연결이 없으면 일반 업무 input normalizer와 actor 검증을 재사용하되 notification source를 만들지 않는 private insert 경로로 업무를 만든다.
11. 연결 행을 삽입한다.
12. `{ linked, taskId, canOpen, conflictKey, alreadyExists }`를 반환한다. `taskId`는 호출자가 해당 업무를 열 수 있을 때만 제공한다.

신규 RPC가 요청 원장을 직접 소유한다. request kind는 `create_dashboard_conflict_task_v1`, fingerprint는 actor와 canonical conflict를 포함한다. 같은 request ID의 재전송은 최초 응답을 그대로 replay하고, 새 request ID에서 같은 conflict key가 들어오면 `alreadyExists: true`를 반환한다. 기존 `create_ops_task_v2`를 중첩 호출해 두 원장을 소비하지 않는다.

연결된 업무는 물리 삭제할 수 없다. DB `BEFORE DELETE` guard가 연결을 먼저 확인하고 `dashboard_conflict_task_delete_forbidden` 고유 오류를 반환한다. 기존 삭제 RPC와 UI는 이 오류를 `일정 충돌에서 생성된 할 일은 삭제 대신 완료 또는 취소해 주세요.`로 매핑한다. `[할 일]`에서는 완료 또는 취소로 처리한다. 이것이 동일 충돌에서 영구적으로 한 건만 유지하는 기준이다.

### 9.2 조회 RPC

`public.list_dashboard_conflict_task_links_v1`은 현재 화면의 canonical conflict 배열만 받아 서버가 같은 키를 계산하고 연결 상태를 반환한다. 연결 자체는 허용된 대시보드 역할에 `linked: true`로 알려 중복 등록 버튼이 다시 나타나지 않게 한다. 업무 ID는 기존 `ops_tasks` 조회 정책상 호출자가 해당 업무를 읽을 수 있을 때만 `taskId`와 `canOpen: true`로 반환한다. 읽을 수 없으면 `taskId: null`, `canOpen: false`만 반환해 비공개 업무 ID나 내용을 노출하지 않는다. 전체 비공개 레지스트리는 브라우저에 노출하지 않는다.

`create_dashboard_conflict_task_v1`도 이미 연결된 업무를 발견했을 때 같은 visibility-aware 응답을 사용한다. 따라서 다른 사용자가 먼저 만든 업무가 있더라도 새 업무를 만들지 않으며, 열람 권한이 없는 사용자에게 열 수 없는 링크를 제공하지 않는다.

두 RPC는 `SECURITY DEFINER`, 빈 `search_path`, 명시적 schema qualification을 사용한다. 함수별 역할은 다음으로 고정한다.

| RPC | 허용 역할 |
| --- | --- |
| `list_dashboard_conflict_task_links_v1` | 대시보드 접근 역할 전체: `admin`, `staff`, `teacher`, `assistant`, `viewer` |
| `create_dashboard_conflict_task_v1` | 생성 역할: `admin`, `staff`, `teacher` |

`anon`과 `public`에는 실행 권한을 주지 않는다. `assistant`와 `viewer`는 조회 RPC만 호출하며 업무 생성은 서버에서도 거절한다. 레지스트리 테이블의 직접 권한은 모든 브라우저 역할에서 회수한다.

## 10. 버튼 상태와 오류 처리

업무 버튼 상태는 행별로 관리한다.

- 초기 조회 중: 비활성 `확인 중`
- 미등록: `할 일 등록`
- 저장 중: 비활성 `등록 중`
- 신규 생성 성공: `등록됨 · 할 일 보기`
- 기존 연결 반환: `등록됨 · 할 일 보기`
- 기존 연결은 있으나 업무 열람 불가: 비활성 `등록됨 · 담당자가 처리 중`
- 실패: `등록 실패 · 다시 시도`

성공 후 `할 일 보기`는 `/admin/tasks?taskId=<id>`로 이동한다. 실패는 행 안에 짧은 오류를 남기고 toast로 한 번 알린다. 실패한 행만 다시 시도할 수 있어야 하며 다른 충돌 행의 버튼은 막지 않는다.

생성 RPC가 허용되지 않는 읽기 전용 역할에는 `할 일 등록` 버튼을 렌더링하지 않는다. 이미 연결된 행은 비활성 `등록됨 · 담당자가 처리 중`, 미연결 행은 짧은 `관리팀 등록 필요` 상태만 보여 준다.

## 11. 반응형·접근성

- 데스크톱은 문제·담당·처리를 한 행 안에서 빠르게 스캔할 수 있게 한다.
- 모바일은 같은 정보를 세로로 쌓고 업무 버튼을 전체 너비로 둔다.
- 확장 버튼은 `aria-expanded`와 연결된 영역 ID를 가진다.
- 충돌 유형은 색상만으로 구분하지 않고 텍스트를 함께 표시한다.
- 저장 상태와 오류는 `aria-live` 영역으로 전달한다.
- 키보드만으로 전체 보기, 업무 등록, 할 일 이동이 가능해야 한다.

## 12. 데이터 흐름과 갱신

- 충돌 계산은 전체 수업 데이터에서 한 번 수행하고 통계 필터별 집계와 분리한다.
- 대시보드 로더는 teacher/classroom catalog ID와 profile 연결, 시험 원천 ID를 정규화 단계까지 보존한다.
- 시험 데이터가 후속 비동기 조회로 도착하면 전체 충돌 행을 다시 정규화한다.
- 선택적 시험 조회의 loading/error 상태를 보존하고 빈 충돌 결과와 구분한다.
- 연결 상태 조회는 현재 충돌 키가 바뀔 때만 실행한다.
- 동일 충돌 키의 생성 요청이 동시에 들어와도 DB 레지스트리가 한 업무만 허용한다.
- 업무 생성 성공 후 기존 할 일 workspace cache를 무효화해 `할 일 보기`에서 즉시 새 업무를 읽는다.
- 일정이 수정되어 충돌이 사라지면 경고에서는 없어지지만 생성된 업무와 연결 이력은 유지한다.
- 동일한 충돌이 다시 나타나면 기존 업무 연결 상태를 다시 보여 준다.

## 13. 마이그레이션과 운영 안전

- 적용된 기존 migration은 수정하지 않고 신규 migration으로 테이블·RPC를 추가한다.
- 일반 업무 생산자의 input normalization과 actor 검증을 재사용하되, 신규 RPC가 자체 요청 멱등성 원장을 소유한다.
- 충돌 생산자는 notification source event를 만들지 않는다고 SQL 계약으로 고정한다.
- 외부 알림 제공자와 notification control-plane 설정은 변경하지 않는다.
- 앱 배포 전에 DB migration과 RPC 계약을 검증한다.
- 실제 운영 데이터 브라우저 QA에서는 할 일을 생성하지 않는다. fixture 또는 transaction rollback 경로에서 생산자와 중복 방지를 검증한다.

## 14. 테스트 전략

### 메트릭·모델

- 네 충돌 유형을 공통 행으로 정규화한다.
- 수업 쌍 순서가 바뀌어도 같은 키를 만든다.
- 주간 충돌의 다음 발생일이 바뀌어도 키를 유지한다.
- 원천 카탈로그 ID가 없는 기존 선생님·강의실 데이터도 수업 UUID 기반 안정 키를 만들고, 표시명 변경 후에도 같은 키를 유지한다.
- 과학 수업도 충돌 계산에 포함한다.
- 다음 날 같은 과목 시험이 있으면 전날 수업을 허용한다.
- 다음 날 시험이 모두 다른 과목이면 전날 충돌을 만든다.
- 같은 과목 시험 당일은 충돌을 만든다.

### UI

- 경고가 필터와 KPI보다 먼저 렌더링된다.
- 경고는 필터 변경과 관계없이 학원 전체 기준을 유지한다.
- 상단 필터의 바깥 테두리만 제거된다.
- 모든 원천이 ready인 0건일 때만 경고를 숨긴다.
- 시험 원천 실패를 0건으로 표시하지 않고 재시도 상태를 보여 준다.
- 기본 3건, 전체 보기·접기, 모바일 배치가 동작한다.
- 행별 저장·성공·기존 연결·실패·재시도 상태가 독립적이다.
- 다른 사용자가 만든 연결 업무를 읽을 수 없으면 재등록 버튼이나 열 수 없는 링크 대신 `등록됨 · 담당자가 처리 중`을 보여 준다.
- 생성 권한이 없는 읽기 전용 역할에는 등록 버튼을 보여 주지 않는다.

### SQL·서비스

- 서로 다른 두 DB 세션의 같은 키 동시 생성 요청이 업무 한 건만 만든다.
- 다른 사용자와 새 요청 ID에서도 기존 업무를 반환한다.
- 연결 업무를 읽을 수 없는 사용자에게는 `linked: true`만 반환하고 비공개 task ID를 노출하지 않는다.
- 같은 요청 ID replay는 최초 `alreadyExists` 응답까지 그대로 반환한다.
- 원천 일정 변경과 생성 요청을 서로 다른 두 DB 세션에서 경합시켜, 잠금 뒤 사라진 충돌이 `dashboard_conflict_stale`로 거절되는지 확인한다.
- 연결된 업무 삭제가 고유 오류로 거절되고 UI 문구로 매핑된다.
- 인증되지 않은 사용자가 RPC와 레지스트리에 접근할 수 없다.
- 허용되지 않은 역할, 잘못된 canonical conflict, 임의 type/status/priority가 거절된다.
- 일반 업무 입력 정규화와 actor 검증이 유지된다.
- task notification source event가 생성되지 않는다.
- 외부 알림 provider 호출이 0건이다.

### 브라우저

- `/admin/dashboard` 데스크톱·모바일에서 경고 순서와 필터 테두리를 확인한다.
- 네 유형의 fixture가 문제·담당·처리를 정확히 보여 주는지 확인한다.
- 운영 데이터 생성 없이 `등록됨`, 오류, 반응형 상태를 fixture로 확인한다.
- production build를 반영한 `localhost:3000`에서 검증한다.

동시성은 단일 pgTAP 트랜잭션이나 정규식 테스트로 완료 처리하지 않는다. 로컬 또는 임시 DB에서 서로 다른 두 연결을 사용하는 통합 테스트를 실행하고, fixture transaction rollback 뒤 업무·레지스트리·notification source·delivery/provider 호출 수를 확인한다.

## 15. 완료 기준

- 일정 충돌 경고가 페이지 본문의 첫 요소다.
- 통계 필터가 어떤 값이어도 학원 전체의 네 충돌 유형을 놓치지 않는다.
- 시험 전날 규칙이 사용자 확인 내용과 정확히 일치한다.
- 각 행에서 문제, 담당자, 처리 방법이 명확하다.
- 같은 충돌은 영구적으로 할 일 한 건만 연결된다.
- 이미 등록된 충돌은 열람 권한이 있으면 기존 할 일로 이동하고, 없으면 중복 등록 없이 담당자가 처리 중임을 확인할 수 있다.
- 상단 필터의 불필요한 바깥 테두리가 사라진다.
- 과학 통계와 기존 학생 명단·접힘 동작에 회귀가 없다.
