# 대시보드 첫 화면 부하 최적화 설계

## 목표

운영 대시보드의 기본 통계와 일정 충돌 기능을 유지하면서, 첫 화면 진입 시 Supabase로 동시에 퍼지는 조회를 줄이고 충돌 데이터 지연이 로그인·기본 통계 표시까지 막지 않게 한다.

## 확인된 기준선

- 현재 대시보드 훅은 기본 수업·학생·회차 3개 조회 뒤, 충돌 계산용 보조 원본 9개를 추가로 읽는다.
- 페이지 공통 권한·알림 조회와 충돌 할 일 연결 조회는 이 12개에 별도로 더해진다. 브라우저의 CORS 사전 요청까지 포함하면 한 번의 진입이 짧은 요청 묶음으로 나타난다.
- 운영 데이터 기준 전체 대시보드 원본은 약 499KiB다. 수업 기본 정보는 약 42KiB, 학생 기본 정보는 약 97KiB, 회차 날짜는 약 301KiB다.
- 회차 RPC의 현재 실행 계획은 약 33ms, 물리 디스크 읽기 0블록, 임시 파일 0블록이다. 일정 충돌 계산 자체는 브라우저에서 실행되므로 현재의 주된 잔여 위험은 쿼리 CPU보다 요청 fan-out과 실패 결합이다.
- 72개 수업 중 71개가 레거시 `schedule_plan`을 사용하며 4,816개 회차가 JSON에 들어 있다. 이 구조의 실제 정규화 전환은 별도 데이터 마이그레이션 프로젝트로 다룬다.

## 범위

### 포함

1. 대시보드 기본 요약과 일정 충돌 원본을 서로 독립적인 두 RPC로 통합한다.
2. 기본 요약을 먼저 표시하고, 충돌 원본은 첫 렌더 이후 별도 단계로 불러온다.
3. 사용자별 30초 메모리 캐시로 같은 세션의 빠른 재진입을 중복 조회하지 않는다.
4. 모든 신규 RPC와 충돌 할 일 연결 조회에 실제 취소 가능한 제한시간과 `.retry(false)`를 적용한다.
5. `academic_events.select("*")`를 없애고 충돌 계산이 소비하는 필드만 반환한다.
6. 관리자와 직원의 기존 통계·충돌 결과 및 RLS 가시성 범위를 그대로 보존한다.

### 제외

- 일정 충돌 기능 또는 통계 카드 제거
- 충돌 계산 규칙 변경
- 고객 알림, SOLAPI, Google Chat 발송
- 서비스 역할 키를 사용한 사용자 데이터 조회
- 71개 레거시 수업의 운영 데이터 정규화 및 `schedule_storage_mode` 전환
- Supabase 유료 플랜 변경

## 아키텍처

### 1. 기본 요약 RPC

`public.get_dashboard_summary_sources_v1()`는 다음 JSON 객체 한 행을 반환한다.

```json
{
  "classes": [],
  "students": []
}
```

- `classes`는 현재 대시보드가 기본 통계와 시간표 겹침 계산에 사용하는 명시적 필드만 포함한다.
- `students`는 학생 수, 재원·대기 분포, 수업 배정에 필요한 명시적 필드만 포함한다.
- 함수는 `stable`, `security invoker`, 고정된 빈 `search_path`를 사용한다.
- 실행 권한은 `authenticated`에만 주고 `public`, `anon` 권한은 제거한다.
- 클라이언트 제한시간은 8초이며 자동 재시도는 하지 않는다.

기본 요약 성공 즉시 통계 카드를 표시한다. 충돌 원본 상태는 이 시점에도 `loading`일 수 있지만 기본 통계의 연결 상태와 오류 상태를 덮어쓰지 않는다.

### 2. 일정 충돌 원본 RPC

`public.get_dashboard_conflict_sources_v1(p_date_from date, p_date_to date)`는 다음 원본을 한 JSON 객체로 반환한다.

- 기간 내 수업 회차 날짜와 상태
- 학기, 시간표 동기화 그룹과 구성원
- 선생님·강의실 카탈로그의 필요한 필드
- 학교, 시험일, 시험 상세, 학사일정의 필요한 필드

날짜 범위는 기존 계약과 동일하게 최대 400일로 제한한다. 레거시 수업은 `schedule_plan.sessions`에서 날짜와 상태만 추출하고, 정규화 수업은 `class_lesson_sessions`를 사용한다. `academic_events`는 충돌 계산이 실제 소비하는 필드만 직렬화한다.

이 함수도 `stable`, `security invoker`, authenticated 전용이며 클라이언트 제한시간은 8초, 자동 재시도는 비활성화한다.

충돌 원본 실패 시 기본 통계는 유지하고 충돌 영역에만 재시도 가능한 오류를 표시한다. 사용자가 누른 재시도는 충돌 캐시만 비우고 한 번의 명시적 RPC를 다시 실행한다.

### 3. 사용자별 단기 캐시

새 캐시 모듈은 `사용자 ID + 현재 역할 + snapshot version`을 키로 사용한다.

- 기본 요약과 충돌 원본을 서로 다른 캐시 엔트리로 저장한다.
- TTL은 30초다.
- 완료된 값과 진행 중 Promise를 함께 dedupe한다.
- 로그아웃·사용자 또는 역할 변경·명시적 재시도에서는 해당 키를 무효화한다.
- 실패 결과는 캐시하지 않는다.
- 캐시는 브라우저 메모리에만 존재하며 사용자 간 또는 CDN에 공유하지 않는다.

### 4. 충돌 할 일 연결 조회 안전성

`listDashboardConflictTaskLinks()`는 현재 대시보드 충돌 계산 뒤 한 번 실행된다. 이 RPC에도 8초 AbortSignal과 `.retry(false)`를 연결한다. 실패해도 충돌 목록 자체는 유지하고, 할 일 연결 상태만 재시도 가능한 오류로 표시한다.

## 데이터 흐름

1. 인증된 사용자 ID가 준비되면 기본 요약 캐시를 확인한다.
2. 캐시가 없으면 기본 요약 RPC 한 건을 실행한다.
3. 기본 요약으로 통계 카드를 즉시 렌더링한다.
4. 별도 effect가 충돌 원본 캐시를 확인하고 충돌 RPC 한 건을 실행한다.
5. 기존 `buildDashboardMetrics()`에 두 원본을 합쳐 동일한 통계·충돌 결과를 만든다.
6. 충돌 행이 존재할 때만 할 일 연결 RPC를 제한시간 안에서 실행한다.

대시보드 훅의 직접 데이터 요청은 12건에서 2건으로 줄어든다. 페이지 공통 인증·권한·알림 요청은 이번 범위에서 변경하지 않는다.

## 오류 및 복구 계약

- 기본 요약 실패: 전체 통계 영역에 한국어 연결 지연 안내와 재시도 동작을 제공한다.
- 충돌 원본 실패: 기본 통계는 유지하며 충돌 영역만 오류 상태로 전환한다.
- timeout, abort, 네트워크 오류, SQLSTATE `57014`: 내부 오류 문자열 대신 기존의 재시도 가능한 한국어 문구로 정규화한다.
- 사용자 전환 도중 끝난 이전 Promise는 새 사용자의 상태나 캐시에 반영하지 않는다.
- mutation과 외부 알림 전송에는 어떤 자동 재시도도 추가하지 않는다.

## 테스트 전략

1. SQL 계약 테스트
   - 두 RPC의 이름, 인자, 권한, `security invoker`, `search_path`, 날짜 범위를 검증한다.
   - `select *`가 없고 반환 필드가 명시적인지 검증한다.
2. 캐시 행동 테스트
   - 동일 사용자·동일 버전의 진행 중 요청과 30초 내 완료 값을 dedupe한다.
   - 만료, 실패, 명시적 재시도, 사용자 변경 시 새 요청을 실행한다.
   - 오래된 요청 결과가 현재 사용자 상태를 오염시키지 않는다.
3. 훅 계약 테스트
   - 기본 요약이 충돌 원본보다 먼저 렌더링된다.
   - 직접 테이블 12개 읽기가 두 RPC로 바뀐다.
   - 충돌 실패가 기본 통계의 성공 상태를 지우지 않는다.
4. 요청 안전성 테스트
   - 두 신규 RPC와 충돌 할 일 연결 RPC에 AbortSignal과 `.retry(false)`가 연결된다.
5. 회귀 테스트
   - 기존 통계와 충돌 fixture 결과가 변경 전후 동일하다.
   - 관련 Node 테스트, 전체 Node 테스트, TypeScript, ESLint, `next build --webpack`, `git diff --check`를 통과한다.
6. 운영 DB 검증
   - migration 적용 후 admin/staff 가시 행 수를 변경 전과 비교한다.
   - RPC payload, `EXPLAIN (ANALYZE, BUFFERS)`, advisor를 확인한다.

## 배포와 롤백

1. 신규 RPC migration을 먼저 운영 DB에 적용한다.
2. RPC 권한·결과·payload를 검증한 뒤 애플리케이션을 `main`에 배포한다.
3. Vercel Production SHA와 `READY`를 확인한다.
4. 대시보드·등록·휴보강·학사일정 로그인 흐름과 Supabase API/Auth/Postgres 로그를 확인한다.
5. 최소 30분 동안 5xx, statement timeout, Disk I/O 증가, 충돌 결과를 관찰한다.

코드 롤백은 이전 애플리케이션 커밋으로 되돌린다. 신규 RPC는 읽기 전용이므로 남겨도 기존 동작에 영향을 주지 않으며, 제거가 필요하면 별도 forward migration으로 권한과 함수를 제거한다. 이미 적용된 migration 파일은 수정하거나 삭제하지 않는다.

## 성공 기준

- 대시보드 훅의 직접 조회가 12건에서 정확히 2개 RPC로 감소한다.
- 기본 요약은 충돌 데이터와 독립적으로 먼저 표시된다.
- 동일 사용자 30초 내 재진입은 네트워크 요청을 반복하지 않는다.
- 전체 원본 payload는 600KiB 이하, 기본 요약 payload는 200KiB 이하를 유지한다.
- 현재 일정 충돌 개수와 상세 원인이 변경 전후 동일하다.
- admin/staff 조회 범위가 변경되지 않는다.
- 운영 배포 후 최소 30분 동안 관련 5xx와 statement timeout이 없다.
