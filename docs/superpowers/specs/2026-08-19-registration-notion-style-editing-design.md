# 등록 상세 노션식 상시 편집 설계

## 1. 목표

등록 상세창을 진행상태 중심의 잠금식 폼에서, 저장된 사실을 섹션별로 언제든 수정할 수 있는 노션식 편집 화면으로 바꾼다. 진행상태는 현재 업무 위치를 보여주는 값으로만 사용하고, 이전 단계의 입력값을 읽기 전용으로 바꾸는 근거로 사용하지 않는다.

관리 권한이 있는 사용자는 문의, 레벨테스트, 상담, 상담 책임자, 대기, 수업, 교재, 수업 시작 일정을 현재 진행상태와 관계없이 수정할 수 있어야 한다. 기술 식별자, 자동 이력, provider 영수증은 편집 대상이 아니다.

## 2. 확인된 원인

### 2.1 수업 시작 일정 저장 실패

김시현 학생의 선택 수업은 `legacy` 일정이다. 일정 원본의 `sessionKey`는 UUID지만 운영 DB의 legacy 일정 검증기는 `YYYY-MM-DD:회차번호` 형식을 정규 키로 사용한다. 화면이 UUID를 `classStartSessionKey`로 전송해 `registration_class_session_invalid`가 발생한다.

### 2.2 입력하지 않은 대기 정보 표시

운영 DB의 `waiting_kind`, `waiting_detail_kind`, `waiting_detail_class_id`, `waiting_detail_retake_decision`은 모두 `null`이다. 화면의 `RegistrationWaitingDetailsEditor`가 빈 값에 `current_term_opening`과 `not_required`를 강제로 대입하고, 변경점이 없다는 이유로 `저장됨`을 표시한다.

### 2.3 진행상태 기반 편집 잠금

상담 책임자는 표시 상태와 편집 상태가 별도 집합으로 제한되어 등록 결정 이후 읽기 전용이 된다. 다른 섹션도 현재 단계, 상담 소유자, 입학 처리 상태 등의 조건을 편집 가능 여부에 섞어 사용한다. 이 구조에서는 진행상태를 이동한 뒤 과거 사실을 정정하기 어렵다.

## 3. 승인된 원칙

### 3.1 사실 입력과 업무 진행을 분리한다

- 진행상태는 목록 분류, 현재 단계 강조, 다음 업무 안내에 사용한다.
- 진행상태는 기존 입력 필드를 숨기거나 읽기 전용으로 만드는 조건으로 사용하지 않는다.
- 각 섹션의 저장은 그 섹션의 값만 저장한다. 다른 섹션의 미입력 값 때문에 막지 않는다.
- 진행상태 변경은 명시적인 상태 선택으로만 수행한다. 과거 입력값 정정이 상태를 자동으로 되돌리거나 앞으로 이동시키지 않는다.

### 3.2 관리자는 기존 값을 언제든 수정할 수 있다

- `permissions.canManage` 사용자는 열린 건과 완료된 건 모두에서 업무 입력값을 수정할 수 있다.
- 상담 책임자는 어느 진행상태에서도 다른 활성 담당자로 변경할 수 있다.
- 상담 결과와 상담 내용은 현재 상담 책임자만 수정하도록 제한하지 않고 관리 권한 기준으로 수정한다.
- 예약 일시·장소, 대기 정보, 수업·교재·시작 일정도 진행상태와 독립적으로 수정한다.
- 동시 수정 충돌, 권한, 존재하지 않는 참조, 과목 불일치 검증은 유지한다.

### 3.3 빈 값은 빈 값으로 표현한다

- DB가 `null` 또는 빈 문자열이면 선택 컨트롤도 선택되지 않은 상태로 표시한다.
- 저장된 값이 전혀 없는 섹션은 `저장됨` 대신 `입력 없음`을 표시한다.
- 기본값은 새 입력을 시작할 때도 자동 저장값처럼 보이지 않게 한다. 사용자가 직접 선택한 뒤에만 저장 가능 상태가 된다.
- 대기 종류를 비우면 대기 반과 재응시 정보도 함께 비우는 명시적 초기화가 가능해야 한다.

### 3.4 외부 실행 결과는 자동으로 되돌리지 않는다

- 입력값 수정은 알림톡 발송, MakeEdu 등록, 청구서, 수납, roster 반영을 자동 취소하거나 재실행하지 않는다.
- 이미 외부 실행된 값과 현재 입력값이 달라지면 해당 단계에 `정정 필요`를 표시하고, 기존의 별도 운영 작업을 통해 반영한다.
- provider 발송 영수증, 입학 batch, roster 이력은 불변 이력으로 유지한다.

## 4. 데이터 및 API 설계

### 4.1 legacy 일정 정규화

`getSelectableRegistrationScheduleSessions`는 `scheduleStorageMode=legacy`일 때 원본 UUID `sessionKey`를 저장 키로 사용하지 않는다. 날짜와 양의 회차번호로 `YYYY-MM-DD:회차번호`를 만들고 lesson session ID는 전송하지 않는다. normalized 일정은 현재의 session key와 lesson session ID 계약을 유지한다.

DB의 `validate_registration_class_session` 계약은 그대로 유지한다. 화면과 서비스 테스트에서 legacy·normalized payload를 각각 검증한다.

### 4.2 섹션별 데이터 저장

- 기존 data-only RPC가 있는 문의, 대기, 수강 정보는 상태 검증을 편집 권한 검증과 분리한다.
- 대기 저장 API는 값 전체를 비우는 입력을 허용하고 세 detail 컬럼을 `null`로 저장한다.
- 상담 결과 정정은 workflow 전이를 수행하는 기존 완료 RPC와 분리된 data-only correction RPC로 저장한다.
- 상담 책임자 변경은 상태 제한 없이 기존 revision·충돌 검증을 사용한다.
- 예약 정정은 부모 예약과 자식 기록의 정합성을 한 트랜잭션에서 유지하되, 현재 pipeline 상태를 편집 금지 조건으로 사용하지 않는다.
- 수강 정보는 외부 입학 batch 또는 roster 이력을 덮어쓰지 않고, 수정 가능한 운영 입력과 이미 실행된 이력을 분리해 저장한다. 외부 실행 이후에는 자동 반영 대신 정정 필요 상태를 계산한다.

새 RPC 또는 변경된 RPC는 인증 사용자에게만 실행 권한을 주고, 함수 내부에서 현재 사용자와 관리 권한을 다시 확인한다. `SECURITY DEFINER`가 필요한 경우 공개 함수의 직접 권한을 최소화하고 내부 함수는 `public`, `anon`에서 회수한다.

## 5. UI 설계

- 모든 업무 섹션은 현재처럼 한 상세창에 계속 표시한다.
- 관리자 화면에서는 상태에 따른 `disabled`, `readOnly`, 숨김 조건을 제거하고 저장 중·충돌·데이터 로딩 실패에만 일시 잠금한다.
- 섹션마다 `입력 없음`, `수정됨`, `저장 중`, `저장됨`, `정정 필요`를 실제 저장 상태에 맞춰 표시한다.
- 저장 버튼은 해당 섹션이 수정됐을 때만 활성화한다.
- 필수값 안내는 해당 섹션을 저장하거나 외부 작업을 실행할 때만 보여준다. 다른 섹션 입력을 방해하지 않는다.
- 외부 작업 버튼은 필요한 사실이 없거나 정정이 필요한 경우 비활성화하고, 바로 옆에 부족한 항목을 한 문장으로 안내한다.

## 6. 오류 처리

- DB 오류 코드는 운영자가 이해할 수 있는 한국어 메시지로 변환하되 원래 코드는 진단 로그에 유지한다.
- 저장 성공 후 새로고침 실패는 저장 실패로 표시하지 않는다. 기존의 `저장은 완료됐지만 최신 내용을 불러오지 못했습니다` 복구 흐름을 유지한다.
- 동시 수정 충돌은 최신 값과 내 수정값을 비교한 뒤 다시 저장하도록 한다.
- 한 섹션의 실패가 다른 섹션의 임시 입력을 지우지 않는다.

## 7. 테스트 및 릴리스 게이트

1. legacy 일정이 UUID 원본 키 대신 `날짜:회차`로 직렬화되고 운영 검증을 통과하는 회귀 테스트
2. normalized 일정의 session key와 lesson session ID가 유지되는 회귀 테스트
3. DB 대기 값이 모두 비어 있을 때 빈 선택과 `입력 없음`이 표시되는 UI 테스트
4. 대기 정보 저장과 전체 비우기 RPC 테스트
5. 문의부터 완료까지 모든 상태에서 관리자 입력 컨트롤이 편집 가능한 계약 테스트
6. 상담 책임자 변경과 상담 결과 data-only 정정이 상태를 변경하지 않는 DB·service 테스트
7. 예약·수강 정정이 외부 발송, batch, roster를 자동 변경하지 않는 DB 테스트
8. 관련 등록 테스트, TypeScript, ESLint, 프로덕션 빌드
9. migration이 있으면 운영 DB 적용 후 read-only 검증과 지정된 테스트 레코드에서 저장 확인
10. `main` 반영 및 Vercel Production `READY`
11. 실제 알림톡, MakeEdu, 청구, 수납, roster 변경은 별도 승인 없이는 실행하지 않음

## 8. 완료 조건

- 김시현 학생의 과거 수업 시작 일정을 선택해 `registration_class_session_invalid` 없이 저장할 수 있다.
- 김시현 상세창에서 상담 책임자를 다른 활성 담당자로 바꾸고 저장할 수 있다.
- 저장한 적 없는 대기 정보는 선택값 없이 `입력 없음`으로 표시된다.
- 진행상태를 바꾼 뒤에도 이전 섹션의 업무 입력값을 다시 수정할 수 있다.
- 입력 정정만으로 외부 발송 또는 운영 반영이 자동 실행·취소되지 않는다.
