# SOLAPI 검증 증빙 분리 설계

## 목적

등록 운영 목록에서 테스트 업무를 완전히 삭제해도 SOLAPI의 검증 이력과 `live` 활성 상태가 유지되게 한다. 발송 전 미리보기와 실제 SOLAPI 요청이 정확히 같은지도 독립적으로 입증한다.

## 범위

- 등록 SOLAPI 7종 메시지 유형
  - `level_test_booking`
  - `visit_consultation_booking`
  - `appointment_reminder`
  - `waiting_notice`
  - `admission_application`
  - `observation_booking`
  - `observation_reminder`
- 검증용 수신번호는 실행 시에만 사용하고 평문으로 새 증빙 테이블이나 로그에 저장하지 않는다.
- 기존 운영 이벤트를 소급 발송하지 않는다. `live` 전환 이후 생성된 신규 이벤트만 자동 발송 대상이다.
- 일반 운영 등록 업무와 검증 증빙의 생명주기를 분리한다.

## 검토한 접근

### 1. 비공개 불변 증빙 분리 — 채택

성공 발송에서 필요한 비식별 증빙만 `dashboard_private`에 보존하고, 활성화 테이블은 일반 등록 업무와 메시지 행을 직접 참조하지 않는다. 테스트 업무는 검증 후 완전히 삭제할 수 있다.

장점은 운영 목록이 깨끗하고 증빙의 수명이 명확하다는 것이다. 단점은 활성화 RPC와 발송 게이트를 함께 바꿔야 한다는 것이다.

### 2. 테스트 업무 숨김 또는 보관 — 제외

현재 외래키를 유지한 채 목록에서만 감춘다. 구현은 작지만 테스트 데이터가 실제로 남으며 삭제 요구를 충족하지 못한다.

### 3. 증빙 제약 우회 — 제외

`live` 상태만 강제로 기록한다. 미리보기 일치, 템플릿 승인, 성공 발송 확인을 우회하므로 사용하지 않는다.

## 데이터 모델

`dashboard_private.registration_customer_solapi_activation_evidence`를 추가한다. 한 메시지 유형의 현재 검증 버전당 한 행만 활성 증빙으로 사용한다.

필수 필드:

- `message_kind`
- `template_id`
- `pf_id`
- `template_checksum`
- `rendered_variables_checksum`
- `rendered_body_checksum`
- `rendered_buttons_checksum`
- `provider_payload_checksum`
- `recipient_hash`
- `provider_message_id`
- `provider_status_code`
- `verified_at`
- `verified_by`
- `created_at`

평문 수신번호, 학생명, 메시지 본문, 등록 업무 UUID는 보존하지 않는다. 메시지 본문은 체크섬만 남긴다. 테이블은 비공개 스키마에 두고 `PUBLIC`, `anon`, `authenticated`, `service_role`의 직접 접근을 모두 철회한다.

`dashboard_private.registration_customer_solapi_activation`에서는 다음 외래키 의존을 제거한다.

- `verification_task_id`
- `live_test_message_id`

활성화 행은 현재 증빙 행을 참조하거나 동일한 버전 식별자를 보존한다. 기존 관리자 RPC 외의 쓰기 경로는 만들지 않는다.

## 미리보기와 실제 발송 일치

발송은 반드시 아직 소비되지 않았고 만료되지 않은 미리보기 ID에서 시작한다. 다음 값이 미리보기, 확정 메시지, SOLAPI 최종 요청 사이에서 모두 같아야 한다.

- 템플릿 체크섬
- 치환 변수 체크섬
- 렌더링 본문 체크섬
- 버튼 체크섬
- 수신번호 해시
- 원본 업무 사실 체크섬

SOLAPI SDK에 넘기기 직전의 정규화된 요청에서 `provider_payload_checksum`을 계산한다. 성공 응답과 함께 이 체크섬을 증빙에 기록한다. 렌더링을 다시 수행하거나 체크섬이 달라지면 발송 전에 실패시킨다.

대시보드 미리보기는 사용자가 읽는 본문과 버튼을 표시하고, 발송 확인 화면에는 메시지 유형과 템플릿 버전을 함께 표시한다. 실제 발송 직전 7종 미리보기를 다시 제시하고 사용자 확인을 받는다.

## 활성화 흐름

1. 관리자가 유형별 현재 SOLAPI 템플릿이 발송 가능 상태이고 공급자 체크섬과 카탈로그 체크섬이 같은지 확인한다.
2. 검증 수신 대상으로 7종 미리보기를 생성한다.
3. 사용자가 미리보기를 최종 승인한다.
4. 각 유형을 `verification`으로 전환하고 승인된 미리보기로 한 번씩 발송한다.
5. SOLAPI의 성공 응답과 수신 확인 시각을 기록한다.
6. 불변 증빙을 생성하고 해당 유형만 `live`로 전환한다.
7. `observation_reminder`의 자동 발송 기준 시각은 `live` 전환 시각으로 설정한다.
8. 임시 등록 업무와 고객 메시지 행을 삭제한다. 비식별 증빙과 활성 상태는 유지된다.

일부 유형이 실패하면 성공한 유형만 `live`가 되고 실패한 유형은 `verification` 또는 `off`에 남는다. 실패 유형을 다른 유형과 묶어 강제로 승격하지 않는다.

## 템플릿 변경 정책

학생명, 일정, 과목처럼 승인된 변수에 들어가는 값이 달라지는 것은 템플릿 변경이 아니며 재검증하지 않는다. 매 발송마다 미리보기 체크섬과 실제 요청 체크섬은 계속 비교한다.

본문 고정 문구, 버튼 이름이나 링크 구조, 변수 이름, 템플릿 ID가 바뀌면 해당 메시지 유형만 재검증한다.

- SOLAPI/Kakao 템플릿 재검수와 발송 가능 상태 확인
- 공급자 체크섬과 로컬 카탈로그 체크섬 일치
- 변경된 유형의 미리보기 승인
- 변경된 유형 1회 검증 발송
- 새 증빙 버전 기록

다른 메시지 유형의 체크섬이 바뀌지 않았다면 계속 `live`로 유지한다. 현재 증빙 체크섬과 현재 템플릿 체크섬이 다르면 변경된 유형만 자동으로 차단하고 `template_drift`를 표시한다.

## 오류 처리와 안전장치

- 증빙 없는 `live` 전환 금지
- 평문 수신번호 저장 금지
- 만료되었거나 소비된 미리보기 재사용 금지
- 미리보기와 최종 요청 체크섬 불일치 시 발송 금지
- 공급자 템플릿 미승인 또는 체크섬 불일치 시 발송 금지
- 이미 존재하는 이벤트와 예약 작업의 소급 발송 금지
- 유형별 성공·실패를 독립적으로 기록
- 외부 공급자 실패가 검증 데이터의 부분 커밋을 만들지 않도록 발송 전 상태와 발송 결과 기록 경계를 명확히 분리

## 마이그레이션과 롤백

현재 7종이 모두 `off`이고 유효한 성공 증빙이 없으므로 기존 행을 `live`로 자동 승격하지 않는다. 새 증빙 테이블과 RPC를 먼저 배포한 뒤 검증 발송으로만 증빙을 만든다.

롤백 시에는 7종을 `off`로 내리고 신규 자동 발송을 중단한다. 이미 기록된 비식별 증빙은 감사 목적으로 유지하며 운영 업무를 복원하지 않는다.

## 테스트

- 미리보기·확정 메시지·공급자 요청 체크섬이 같은 경우만 발송 가능
- 본문, 버튼, 변수, 수신번호 중 하나가 바뀌면 발송 차단
- 성공 증빙 없이 `live` 전환 차단
- 증빙 생성 후 테스트 업무 삭제 가능
- 테스트 업무 삭제 후에도 증빙과 `live` 상태 유지
- 템플릿 체크섬 변경 시 해당 유형만 차단
- 변수값 변경은 재검증 없이 허용
- `observation_reminder`는 전환 이전 이벤트를 소급 발송하지 않음
- 직접 테이블 접근 권한 없음
- 7종 미리보기와 공급자 요청 페이로드 체크섬 일치

## 완료 조건

- 7종 미리보기 승인 전 실제 발송 없음
- 검증 수신 대상에 7종 발송 성공
- 유형별 공급자 메시지 ID와 체크섬 증빙 저장
- 7종 `live` 확인
- 임시 테스트 업무가 등록 목록과 관련 운영 테이블에서 제거됨
- 배포 후 신규 이벤트만 자동 발송 가능
