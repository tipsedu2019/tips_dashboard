# 연속 수업과 일정 스냅샷 v3 설계

## 1. 목표

수업은 학기마다 다시 생성하지 않고 `종강` 처리 전까지 같은 수업 ID로
계속 운영한다. 수업의 기본 시간표를 바꾸면 이후 새로 생성하는 일정에만
새 기본값을 적용하고, 이미 생성된 일정에는 당시 요일·시간·선생님·강의실을
스냅샷으로 보존한다.

이 설계는 다음 운영 질문에 한 수업 안에서 답할 수 있게 한다.

- 특정 날짜에 실제로 수업했는가, 휴강했는가, 보강했는가
- 그 일정은 몇 시에 어느 선생님과 어느 강의실에서 진행됐는가
- 당시 사용한 교재와 회차별 계획·실제 진도는 무엇인가
- 현재 기본 시간표는 무엇이며, 언제부터 새 일정에 사용됐는가

## 2. 확정한 제품 원칙

1. **수업은 연속된다.** 학기 종료가 수업 종료를 뜻하지 않는다.
2. **종강은 명시적이다.** 운영자가 종강 처리하기 전까지 수업은 계속
   일정을 추가할 수 있다.
3. **기본값은 미래 생성 규칙이다.** 기본 요일·시간·선생님·강의실 수정은
   저장 이후 새로 생성하는 일정에만 적용한다.
4. **생성된 일정은 독립된 이력이다.** 기본값 변경으로 기존 일정이
   자동 수정되지 않는다.
5. **예외 기간 시간표는 만들지 않는다.** 기간별 두 번째 시간표나
   `schedule_overrides` 규칙 계층을 도입하지 않는다.
6. **예외는 일정에서 처리한다.** 휴강·보강·미정·해제 및 시간·선생님·
   강의실 변경은 해당 일정에만 저장한다.
7. **과거를 추정하지 않는다.** 기존 데이터에 당시 선생님·강의실이 없으면
   현재 기본값을 과거 이력으로 채우지 않는다.
8. **학기는 필요한 도메인에 남긴다.** 학사일정·시험·정산·통계처럼 학기가
   실제 기준인 화면과 `class_terms` 데이터는 유지한다.

## 3. 현재 구조와 변경이 필요한 이유

현재 수업계획은 `classes.schedule_plan` JSON 한 개에 기간, 일정 상태,
회차, 교재 범위와 진도를 함께 저장하고 클라이언트에서 JSON 전체를
덮어쓴다. 일정에는 날짜와 상태는 있지만 시간·선생님·강의실 스냅샷이 없다.

수업을 여러 학기 동안 유지하면 이 구조에는 세 가지 문제가 생긴다.

- 수업 이력이 늘어날수록 한 JSON 행이 계속 커지고, 작은 수정도 전체 JSON을
  다시 읽고 쓴다.
- 동시 수정 시 마지막 저장이 다른 관리자의 변경을 덮을 수 있다.
- 현재 수업 기본값을 바꾼 뒤 과거 일정의 실제 선생님·강의실을 판별할 수 없다.

또한 수업관리와 수업계획의 `기간` 필터는 두 종류의 값을 섞고 있다.

- `class_terms` 또는 `classes.period`에서 만든 합성 학기 그룹
- `class_schedule_sync_groups`와 멤버십으로 저장한 명시적 수업 그룹

수업관리와 수업계획에서는 이 혼합 `기간` 필터 자체를 제거한다. 명시적
수업 그룹 데이터와 수업 그룹 전용 관리·시간표 기능은 삭제하지 않지만,
이번 두 화면에 다른 이름의 대체 필터를 새로 만들지는 않는다.

## 4. 선택한 접근

### 4.1 권장안: 정규화된 기본 시간표와 일정 스냅샷

현재 기본 시간표, 생성된 일정, 교재 사용 구간을 별도 행으로 저장한다.
새 일정은 생성 순간 기본 시간표를 복사한다. 이후 기본값을 바꿔도 기존
일정 행은 변하지 않는다.

이 방식은 기간별 시간표 규칙 없이도 과거 이력을 보존하며, 날짜 범위로
필요한 일정만 조회할 수 있다.

### 4.2 채택하지 않는 접근

#### 기존 JSON에 스냅샷 필드만 추가

초기 구현은 작지만 연속 수업의 전체 이력이 `classes.schedule_plan`에
무한히 누적된다. 전체 덮어쓰기와 충돌 위험도 그대로여서 채택하지 않는다.

#### 기본 시간표 변경 이력을 유효기간으로 저장

시간표 버전과 적용 기간을 두면 과거 기본값은 알 수 있지만, 개별 보강·교체
수업과 이미 생성된 일정의 확정값을 다시 계산해야 한다. 결국 기간별 두 번째
시간표가 되어 이번에 합의한 단순한 운영 모델과 맞지 않는다.

## 5. 도메인 모델

### 5.1 `classes`: 계속 유지되는 수업

`classes.id`는 수업의 영구 식별자다. 학생 구성, 교재, 일정과 진도 이력은
이 ID 아래 누적된다.

기존 상태값을 유지한다.

- `개강 준비 중`: 기본정보와 일정을 준비하는 수업
- `수업 진행 중`: 일정을 추가하고 운영하는 수업
- `종강`: 새 일정 생성과 기본 시간표 변경이 잠긴 수업

학기 날짜로 상태를 자동 변경하지 않는다. 종강은 명시적 저장 작업이며
`closed_at`, `closed_by`를 기록한다. 기존 `start_date`, `end_date`,
`term_id`, `period`는 삭제하거나 새 의미로 재사용하지 않는다.

`classes`에는 현재 기본 시간표의 동시 수정 검사용
`schedule_revision bigint not null default 0`을 추가한다.

### 5.2 `class_schedule_slots`: 현재 기본 시간표

한 수업이 요일별로 서로 다른 시간·선생님·강의실을 가질 수 있으므로
기본 시간표를 행 단위로 저장한다.

필수 필드:

| 필드 | 의미 |
| --- | --- |
| `id` | 기본 시간표 행 UUID |
| `class_id` | 수업 FK |
| `weekday` | 일요일 0부터 토요일 6까지 |
| `start_time`, `end_time` | 기본 시작·종료 시각 |
| `teacher_catalog_id` | 현재 선생님 카탈로그 FK, 삭제 시 null |
| `teacher_name` | 현재 표시명 |
| `classroom_catalog_id` | 현재 강의실 카탈로그 FK, 삭제 시 null |
| `classroom_name` | 현재 표시명 |
| `sort_order` | 같은 요일 복수 수업의 표시 순서 |
| `created_at`, `updated_at` | 변경 시각 |

이 테이블은 **현재 기본값만** 표현한다. 행을 바꾸거나 삭제해도 이미 생성된
일정 스냅샷은 바뀌지 않는다. 기존 `classes.schedule`, `teacher`, `room`은
호환 기간 동안 같은 저장 RPC가 파생 표시값으로 함께 갱신한다. 클라이언트의
`classroom` 속성은 기존처럼 `room`의 표시용 별칭으로 취급한다.

### 5.3 `class_lesson_sessions`: 일정별 확정 스냅샷

일정 한 건이 캘린더 상태와 당시 자원을 소유한다.

필수 필드:

| 필드 | 의미 |
| --- | --- |
| `id` | 일정 UUID |
| `class_id` | 수업 FK |
| `session_key` | 기존 문자열 세션 ID와 URL·진도 연결을 보존하는 안정 키 |
| `source_schedule_slot_id` | 생성에 사용한 기본 시간표 행, 삭제 시 null |
| `session_date` | 일정 날짜 |
| `schedule_state` | `active`, `exception`, `makeup`, `tbd`, `skipped` |
| `start_time`, `end_time` | 해당 일정의 시간 스냅샷 |
| `teacher_catalog_id` | 당시 선택한 선생님 FK, 삭제 시 null |
| `teacher_name_snapshot` | 카탈로그 변경·삭제 후에도 남는 당시 표시명 |
| `classroom_catalog_id` | 당시 선택한 강의실 FK, 삭제 시 null |
| `classroom_name_snapshot` | 당시 강의실 표시명 |
| `origin` | `default`, `manual`, `legacy` |
| `makeup_of_session_id` | 보강이 대체하는 원 일정, 없으면 null |
| `legacy_billing_id`, `legacy_billing_label`, `legacy_billing_color` | 호환 투영용 기존 기간 메타데이터 |
| `memo`, `public_note`, `teacher_note` | 일정 메모 |
| `revision` | 일정 단위 낙관적 동시 수정 값 |
| `created_by`, `updated_by`, `created_at`, `updated_at` | 감사 정보 |

요일은 `session_date`에서 결정되므로 중복 저장하지 않는다. 회차 번호도
외부 참조 키로 쓰지 않고 조회 결과에서 날짜·시간·안정 키 순으로 계산한다.
휴강이나 해제를 복원해 회차 표시가 달라져도 교재 진도 연결은
`class_lesson_sessions.id` 또는 `session_key`로 유지한다.

기본 시간표에서 생성한 일정은
`(class_id, session_date, source_schedule_slot_id)`를 중복 생성할 수 없다.
수동 일정은 같은 날짜에도 여러 건을 허용하되 요청 키 재시도로 중복되지
않게 한다. `legacy_billing_*`는 새 도메인의 학기나 기간 규칙이 아니며,
기존 `schedule_plan` 소비자가 전환되는 동안만 원래 표시를 보존한다.
새 일정의 호환 투영에서는 캘린더 월을 기준으로 이 메타데이터를 만든다.

### 5.4 `class_textbook_assignments`: 교재 사용 이력

수업과 교재의 연결을 현재 ID 배열이 아니라 사용 구간으로 저장한다.

필수 필드:

- `id`, `class_id`, `textbook_id`
- `role`, `display_alias`, `area`, `sub_subject`, `sort_order`
- `started_session_id`
- `ended_session_id` 또는 현재 사용 중임을 뜻하는 null
- `created_by`, `ended_by`, `created_at`, `ended_at`
- `revision`

교재를 바꿀 때 기존 연결을 삭제하지 않고 종료 회차를 기록한 뒤 새 연결을
추가한다. 따라서 수업별 과거 교재 목록과 사용 기간을 바로 조회할 수 있다.

### 5.5 `progress_logs`: 회차별 진도

기존 `progress_logs`를 재사용한다. 다음 FK를 추가한다.

- `lesson_session_id -> class_lesson_sessions.id`
- `textbook_assignment_id -> class_textbook_assignments.id`

기존 `session_id`, `textbook_id`, `progress_key`는 호환 기간 동안 유지한다.
백필 후 새 저장은 FK와 기존 키를 함께 기록한다. 별도 진도 테이블을 하나 더
만들지 않는다.

### 5.6 멱등성 영수증

`class_schedule_mutation_receipts`는
`actor_id + operation + request_key`를 고유 키로 저장한다. 요청 본문 해시와
결과 JSON을 보관해 네트워크 결과가 불확실한 저장을 같은 키로 재시도해도
동일한 결과를 돌려준다. 같은 키에 다른 본문이 오면 거부한다.

## 6. 핵심 동작

### 6.1 기본 시간표 변경

`save_class_schedule_defaults_v1`은 다음을 한 트랜잭션에서 수행한다.

1. 수업 행을 잠그고 `expected_schedule_revision`을 확인한다.
2. 종강 여부와 요일·시간·선생님·강의실 후보를 검증한다.
3. `class_schedule_slots`의 현재 행을 교체한다.
4. 기존 소비 화면을 위한 `classes.schedule`, `teacher`, `room` 및
   `classroom` 파생 표시값을 갱신한다.
5. `schedule_revision`을 1 증가시키고 감사 로그를 남긴다.

이 작업은 `class_lesson_sessions`를 갱신하지 않는다. 저장 화면에는
`새로 추가하는 일정부터 적용`이라는 짧은 상태 문구만 표시한다.

### 6.2 일정 추가

운영자는 종료일 없는 자동 생성을 켜지 않는다. 날짜 범위 또는 생성할 회차
범위를 명시해 일정을 추가한다.

`generate_class_lesson_sessions_v1`은 다음 순서로 동작한다.

1. 수업과 현재 기본 시간표를 잠그고 revision을 확인한다.
2. 입력 범위 안에서 요일별 생성 후보를 계산한다.
3. 기존 일정과 겹치는 후보를 미리 구분한다.
4. 새 일정마다 시간·선생님·강의실을 스냅샷으로 복사한다.
5. 한 요청을 원자적으로 저장하고 생성·기존·제외 건수를 반환한다.

기본 동작은 기존 일정 유지다. 겹치는 일정은 자동 덮어쓰지 않는다.

### 6.3 일정 직접 수정

캘린더 또는 왼쪽 일정 상세에서 다음 필드를 수정할 수 있다.

- 일정 상태
- 날짜와 시간
- 선생님
- 강의실
- 메모

`save_class_lesson_session_v1`은 해당 일정의 `expected_revision`을 확인하고
그 일정만 갱신한다. 기본 시간표와 다른 값을 저장해도 별도 기간 규칙은
만들지 않는다.

현재의 셀 순환
`정상 → 휴강 → 보강 → 미정 → 해제 → 정상`은 유지한다. `해제`는
`skipped` 행을 삭제하지 않고 남겨 ID와 진도를 보존한다.

### 6.4 종강과 재개

종강 시 새 일정 생성과 기본 시간표 변경을 막고 `closed_at`, `closed_by`를
기록한다. 일정·교재·진도 이력은 읽을 수 있다.

종강 후 과거 기록 정정은 관리자만 가능하며 사유를 필수로 남긴다. 수업 재개는
실수로 상태값만 바꾸지 않도록 별도 관리자 RPC로 처리하고 감사 로그를 남긴다.

## 7. 저장 서비스와 충돌 처리

브라우저에서 `classes.schedule_plan`을 직접 업데이트하는 현재 저장 경로를
최종 권위 경로로 사용하지 않는다. 일정 관련 변경은 타입이 정의된 RPC와
서버 어댑터를 거친다.

모든 변경 RPC는 다음 계약을 공유한다.

- `request_key`
- 예상 revision
- 허용된 필드만 포함한 입력
- 권위 데이터 잠금 후 재검증
- 전체 성공 또는 전체 실패
- 안정적인 camelCase 결과

revision이 다르면 저장 내용을 합쳐 추측하지 않고
`다른 사용자가 먼저 수정했습니다. 최신 내용을 확인하세요.`를 표시한다.
사용자가 최신 값을 확인한 뒤 다시 적용한다.

## 8. 기존 `schedule_plan` 호환과 소비 화면

현재 다음 경로가 `schedule_plan`을 직접 사용한다.

- 수업계획 화면
- 등록 시작 회차 검증
- 보강 승인과 원복
- 대시보드 시험 충돌 계산
- 일부 수업·업무 상세 조회

따라서 한 번에 제거하지 않는다.

1. 정규화 테이블을 추가하되 capability가 꺼진 상태에서는 읽기 전용으로
   백필·대조한다.
2. 정규화 저장 RPC가 성공할 때 호환용 `classes.schedule_plan` 투영도 같은
   트랜잭션에서 갱신한다.
3. 공용 `lesson-schedule-service`가 capability에 따라 정규화 조회를 우선하고
   준비되지 않은 수업은 기존 JSON으로 폴백한다.
4. 등록·보강·대시보드 소비자를 공용 서비스 또는 권위 RPC로 순차 전환한다.
5. 모든 소비자가 전환되기 전에는 `schedule_plan` 컬럼과 기존 키를 삭제하지
   않는다.

capability가 켜진 수업에 대한 직접 `schedule_plan` 변경은 DB 경계에서
거부한다. 보강 승인도 정규화 일정 mutation을 호출하도록 전환한 뒤에만
capability를 활성화한다.

등록의 시작 회차는 표시용 날짜·회차 문자열을 장기 식별자로 사용하지 않는다.
`ops_registration_enrollments`에 nullable `class_start_lesson_session_id`를
추가하고 기존 `class_start_session_key`, 날짜와 라벨은 호환 표시값으로
유지한다. 정규화 capability가 켜진 수업은 일정 FK, 수업 ID와 선택 가능한
상태를 권위 기준으로 검증한다. 기존 등록 행은 안정적으로 일치하는 경우만
FK를 백필하고, 일치하지 않으면 기존 검증 경로를 유지한다.

## 9. 기존 데이터 전환

### 9.1 기본 시간표

기존 `classes.schedule`, `teacher`, `room` 및 `classroom`을 현재 슬롯으로
파싱한다. 파싱 결과가 애매한 수업은 자동 저장하지 않고 전환 검토 목록에
남긴다.

### 9.2 일정

`schedule_plan.sessions`의 안정 ID, 날짜, 상태, 메모와 진도 연결은 보존한다.
기존 일정은 `origin = 'legacy'`로 표시한다.

기존 일정에 시간·선생님·강의실 스냅샷이 없으면 null과 빈 스냅샷으로
백필한다. 화면에서는 `기록 없음`으로 표시한다. 미래 일정이라도 현재
기본값으로 몰래 채우지 않는다. 운영자가 해당 일정을 처음 명시적으로
수정하면 그때 확정 스냅샷이 생긴다.

### 9.3 교재와 진도

기존 `schedule_plan.textbooks`의 시작·종료 세션 키로
`class_textbook_assignments`를 만든다. 기존 `progress_logs`는
`class_id + session_id + textbook_id`로 새 FK 후보를 연결한다.

다음 항목은 수업별 전환 검토 대상으로 남긴다.

- 존재하지 않는 세션 또는 교재를 가리키는 진도
- 같은 교재의 겹치는 사용 구간
- 중복 세션 키
- 날짜나 상태가 없는 세션
- 기본 시간표 파싱 실패

전환 검토가 남은 수업은 기존 경로로 계속 읽고 쓰며 강제 활성화하지 않는다.

## 10. 학기와 수업 그룹 UI

### 수업관리와 수업계획

- `기간` 필터를 두 화면에서 제거한다. 합성 학기와 명시적 수업 그룹을
  섞던 옵션 생성도 이 두 화면에서는 실행하지 않는다.
- 기존 `period` URL 파라미터는 무시하고 필터 없는 주소로 정리한다.
- `class_schedule_sync_groups`와 멤버십 데이터는 삭제하지 않는다. 수업 그룹
  전용 관리·시간표 기능은 그대로 유지하지만 이 두 화면의 대체 필터로
  노출하지 않는다.
- 신규 수업과 일반 수정에서 학기를 필수로 받지 않는다.
- 카드의 `학기 미정` 같은 보조 문구를 제거한다.
- 기존 학기 값은 삭제하지 않고 과거 상세의 `기존 분류`에서만 읽을 수 있다.

기존 `period` 링크는 한 차례 호환 처리해 해당 파라미터만 제거한 같은
화면으로 연다. 검색어, 상태, 과목 등 다른 필터는 보존한다.

### 학기가 실제 기준인 화면

다음은 그대로 유지한다.

- 학사일정과 시험의 학기 분류
- 학기 마스터
- 학기 기준 정산·통계
- 등록 대기의 `현재 학기`, `다음 학기` 같은 업무 상태

이 설계는 `class_terms` 테이블을 삭제하지 않는다.

## 11. 권한과 감사

- 인증 사용자는 허용된 수업과 일정 이력을 읽을 수 있다.
- 관리자·직원은 기본 시간표, 일정, 교재 사용 구간을 변경할 수 있다.
- 선생님은 권한 있는 수업의 진도와 선생님 메모만 변경할 수 있다.
- 종강 수업의 일정 정정과 재개는 관리자만 가능하다.
- 카탈로그 ID는 현재 참조 검증에 사용하고, 표시명 스냅샷은 삭제·이름 변경
  이후에도 보존한다.
- 새 테이블은 RLS를 활성화하고 SECURITY DEFINER RPC는
  `search_path`, 소유자, EXECUTE 권한을 명시한다.
- 기존 `dashboard_audit_logs`에 기본 시간표·일정·교재 변경의 행 ID,
  before/after, actor, request key와 정정 사유를 남긴다.

## 12. 오류 처리

| 상황 | 동작 |
| --- | --- |
| 기본 시간표 revision 불일치 | 저장하지 않고 최신값 확인 안내 |
| 일정 revision 불일치 | 해당 일정만 저장하지 않고 재검토 안내 |
| 같은 생성 요청 재시도 | 영수증의 동일 결과 반환 |
| 같은 요청 키에 다른 입력 | 요청 키 충돌로 거부 |
| 생성 범위에 기존 일정 존재 | 기존 유지, 생성·기존·제외 건수 표시 |
| 선생님·강의실 카탈로그 삭제 | FK는 null, 스냅샷 표시는 보존 |
| 종강 수업에 일정 추가 | 전체 요청 거부 |
| 전환 검토가 남은 수업 | capability 비활성, 기존 경로 유지 |
| 저장 중 일부 검증 실패 | 트랜잭션 전체 롤백 |

## 13. 성능 원칙

- 수업 목록은 전체 일정·진도 JSON을 읽지 않는다.
- 수업 상세은 선택한 수업과 필요한 날짜 범위만 조회한다.
- 일정 목록은 `(class_id, session_date, start_time)` 인덱스를 사용한다.
- 미정·휴강·보강 조회는 상태 인덱스를 사용한다.
- 교재 이력은 `(class_id, created_at)`과 사용 구간 인덱스를 사용한다.
- 수년치 일정은 페이지 또는 월 범위로 불러오며 클라이언트에 한 번에
  적재하지 않는다.

## 14. 검증 전략

### 모델·서비스 테스트

- 기본값 변경이 기존 일정 스냅샷을 바꾸지 않는다.
- 기본값 변경 후 생성한 일정만 새 시간·선생님·강의실을 가진다.
- 한 수업에 요일별 다른 선생님·강의실을 생성한다.
- 일정 직접 수정은 기본 시간표와 다른 일정을 한 건만 갱신한다.
- skipped 복원 후 세션 키와 진도 FK가 유지된다.
- 종강 수업은 새 일정 생성이 거부된다.
- 같은 요청 키 재시도와 stale revision이 계약대로 동작한다.

### 마이그레이션·DB 테스트

- 제약조건, FK 삭제 정책, RLS, RPC 권한과 search path를 검사한다.
- 백필을 두 번 실행해도 중복 행이 생기지 않는다.
- JSON과 정규화 투영의 세션 날짜·상태·교재·진도 수를 대조한다.
- 과거 선생님·강의실이 현재 기본값으로 오염되지 않는다.
- capability가 꺼진 수업과 전환 검토 수업은 기존 경로를 유지한다.

### 소비자 회귀 테스트

- 등록 시작 회차는 정상·보강만 선택할 수 있다.
- 보강 승인·취소가 동일 일정과 진도 연결을 보존한다.
- 대시보드 시험 충돌 날짜가 정규화 전후 동일하다.
- 수업 목록은 전체 일정 데이터를 요청하지 않는다.
- 수업관리·수업계획의 기간 필터가 사라지고 수업 그룹 전용 기능은 유지된다.

### 브라우저 QA

- 기본 시간표 수정 후 기존 일정이 그대로인지 확인한다.
- 새 일정만 변경된 기본값으로 생성되는지 확인한다.
- 특정 일정의 선생님·강의실·시간을 수정한다.
- 수업별 과거 일정과 교재 이력을 날짜 범위로 찾는다.
- 수업관리와 수업계획에서 학기 필터가 사라지고 수업 그룹은 유지되는지 본다.
- 학사일정·학기 마스터·학기 기준 업무 화면은 그대로인지 확인한다.

## 15. 단계적 출시와 롤백

1. **기준선:** 현재 JSON의 구조·크기·오류 유형과 소비자 결과 fixture를 고정한다.
2. **어두운 스키마:** 새 테이블, 제약, RLS, RPC와 capability probe를 배포하되
   운영 UI는 기존 경로를 사용한다.
3. **백필·대조:** 자동 전환 가능한 수업을 백필하고 JSON과 결과를 비교한다.
4. **쓰기 호환:** mutation RPC와 `schedule_plan` 호환 투영을 활성화한다.
5. **읽기 전환:** 수업계획을 시작으로 등록·보강·대시보드를 순차 전환한다.
6. **연속 수업 UI:** 종강 전까지 일정 추가, 일정 스냅샷 수정, 교재 이력 조회를
   노출한다.
7. **필터 정리:** 수업관리·수업계획의 기간 필터와 학기 보조 문구를 제거하되
   수업 그룹 전용 관리·시간표 기능은 유지한다.
8. **운영 관찰:** 전환 오류 0건, 투영 불일치 0건, 주요 조회 성능 기준을
   확인한 뒤 기본 capability를 전환한다.

롤백은 capability를 끄고 기존 `schedule_plan` 읽기로 복귀한다. 호환 기간
동안 모든 정규화 mutation이 같은 트랜잭션에서 JSON 투영을 갱신하므로
롤백 시 데이터가 사라지지 않는다. 새 테이블이나 백필 데이터를 즉시 삭제하지
않는다.

### 15.1 구현 계획 분할

이 설계 전체를 한 번의 거대한 구현 태스크로 처리하지 않는다. 다음 세
릴리스 계획이 각각 독립된 검증·중지 지점을 가진다.

1. **기반과 어두운 전환:** revision, 기본 슬롯, 일정 스냅샷, 멱등성 영수증,
   RLS/RPC 골격, 읽기 어댑터, 백필 dry-run과 대조 보고서. 운영 UI의 권위
   저장 경로는 바꾸지 않는다.
2. **일정 저장 전환:** 기본값·일정 mutation, JSON 호환 투영, 수업계획 UI,
   등록·보강·대시보드 소비자 전환과 수업별 capability 활성화.
3. **연속 이력 완성:** 교재 사용 구간, 진도 FK, 수업별 과거 조회, 종강·재개,
   수업관리·수업계획 기간 필터 제거와 성능 검증.

각 계획은 이전 단계의 운영 대조 결과가 통과해야 시작한다. 첫 세부 구현
계획은 1번 `기반과 어두운 전환`만 대상으로 작성한다.

## 16. 명시적 범위 제외

- 기간별 두 번째 시간표와 `schedule_overrides`
- 기존 미래 일정에 새 기본값을 자동 일괄 적용하는 기능
- 확인되지 않은 과거 선생님·강의실 추정
- `class_terms`와 기존 학기 이력의 물리적 삭제
- 수업료·급여·정산 규칙 변경
- 출결 시스템 신설
- 알림 공급자 활성화 또는 메시지 발송
- 호환 기간 안의 `classes.schedule_plan` 컬럼 삭제

## 17. 완료 기준

- 같은 수업 ID로 학기를 넘어 일정을 계속 추가할 수 있다.
- 기본 시간표 변경 전후 일정의 자원 스냅샷이 서로 독립적이다.
- 일정별 선생님·강의실·시간을 직접 수정하고 과거값을 조회할 수 있다.
- 수업별 교재 사용 구간과 회차별 진도를 조회할 수 있다.
- 종강 전에는 일정 추가가 가능하고 종강 후에는 명시적으로 차단된다.
- 수업관리·수업계획에서 기간 필터가 사라진다.
- 수업 그룹 전용 기능과 학기가 실제 기준인 다른 화면은 유지된다.
- 기존 등록·보강·대시보드 결과가 전환 전후 동일하다.
- 전환이 준비되지 않은 수업은 기존 경로로 안전하게 폴백한다.
- 롤백 시 기존 JSON 읽기로 복귀할 수 있고 운영 이력이 유실되지 않는다.
