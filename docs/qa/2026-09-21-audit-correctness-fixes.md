## 검증 기록

- Node/React 회귀 검사 952개 통과. 최종 결과는 `output/audit-fixes-20260921/regression-final.log`에 기록. 마이그레이션 안전장치 검사는 `migration-layout-final.log`에 별도 기록.
- 격리 DB: baseline/catalog 1,937개, 변경·인접 기능 pgTAP 183개 통과.
- 독립 DB 연결 경합: 구매 4개 + 출고 5개 시나리오 통과. 실제 충돌 SQLSTATE `23514`, 중복 이동 `23505`, 권한 거부 `42501` 확인. 업무 상태 충돌에 `40001`을 사용하지 않음.
- Supabase DB lint: 변경한 5개 함수의 지적 없음. 전체 DB의 기존 warning은 별도 로그에 보존.
- Squawk 2.63.0: 새 마이그레이션 2개, 지적 0건.
- TypeScript 검사 통과. 전체 ESLint 오류 0건, 기존 경고 5건.
- Next.js production build 통과. Supabase 운영 환경 변수 없이 빌드했으며 공개 수업 조회의 미설정 로그가 출력됨. 실서비스 조회 성공 증거로 사용하지 않음.
- 로컬 브라우저: 등록 fixture에서 예약 초안 보호 및 과목 변경 시 상담 취소 확인 폐기 확인. 브라우저 console error 없음. 실제 고객 데이터·발송 연결을 사용하지 않음.
- CI에 새 회귀 테스트와 DB 경합 probe를 추가하고, 변경한 CI 파일의 허용 해시를 갱신. 검증 범위나 secret 접근 범위는 확대하지 않음.

격리 DB runner는 테스트 프로젝트를 종료하고 임시 파일을 정리했다. 기존 로컬 DB 컨테이너는 유지했다.

## 배포 전 리뷰 보완

PR #56에서 확인한 묶음 반품 및 가입 교사 연결 문제는 후속 마이그레이션으로 보완했다. 최초 두 마이그레이션은 변경하지 않았다.

- 반품·삭제 후 부모 발주 상태를 남아 있는 모든 품목으로 계산한다. 한 품목 반품 이후 다른 품목 입고가 `23514`로 막히는 실패를 먼저 재현했다.
- 사용자 메타데이터의 이름은 교사 소유권 근거에서 제거했다. 미연결 교사는 확인된 이메일로만 연결하고, 현재 소유자 조건과 행 잠금을 적용한다. 오래된 프로필 역참조도 다른 소유자의 교사를 덮어쓰지 않는다.
- 기존 교사의 권한·표시 여부·계정 이메일을 보존한다. 동명이인 신규 가입은 기존 이름 고유 제약을 유지하면서 별도 이름 번호와 교사 ID를 얻는다. 이름 배정 한도에서는 `23505`를 반환하고 가입 계정·프로필을 함께 롤백한다.
- 권한 저장 반환 조회는 필요한 필드와 ID를 지정한 단일 행, 8초 제한, 자동 재시도 없음으로 명시했다. 스키마 대체 경로도 같은 계약을 따른다.
- 최종 보완 검증: baseline/catalog 1,937개, 변경·인접 pgTAP 206개, 구매 경합 4개 및 동명이인 가입 경합 2개 통과. 변경 함수 DB lint와 새 SQL 2개 Squawk 지적 0건. 관련 Node 계약 검사 31개 통과.
- 첫 운영 파이프라인은 추가 리뷰 수신 후 `db-push` 전에 취소했다. 운영 migration ledger에서 이번 버전이 아직 적용되지 않은 것을 확인했다. 검증 로그는 `output/audit-release-20260921/`에 보관한다.

## 운영 반영 순서와 범위

이 문서의 검증 기록은 구현 및 배포 전 검사에 관한 것이다. 운영 DB 적용과 앱 배포의 실제 결과는 PR #56과 연결된 배포 파이프라인에서 별도로 확인한다. 실제 알림 발송은 검증에 포함하지 않는다.

새 프런트엔드가 RPC를 사용하므로 운영 적용 시 다음 네 DB 마이그레이션을 먼저 반영해야 한다.

1. `20260921114313_textbook_lifecycle_atomic.sql`
2. `20260921114314_signup_identity_isolation.sql`
3. `20260921132000_purchase_group_return_state.sql`
4. `20260921132001_signup_teacher_ownership.sql`

고유 제약 추가 전 기존 중복 이동이 없는지 읽기 전용으로 확인한다. 중복이 있으면 마이그레이션이 중단되며, 이 변경은 과거 재고 이력을 자동 삭제하거나 정정하지 않는다.

```sql
select purchase_order_line_id, move_type, count(*)
from public.textbook_stock_moves
where purchase_order_line_id is not null
  and move_type in ('purchase_receipt', 'return_out')
group by purchase_order_line_id, move_type
having count(*) > 1;
```

운영 마이그레이션 성공 후 앱을 배포하고 저장·반품·과목 전환을 운영 권한으로 확인해야 한다. 기존 가입 충돌로 이미 잘못 연결된 계정이 있는지와 과거 재고 불일치 여부는 운영 데이터 검사 전에는 확정하지 않는다.
