## Sanitized change signals across Tasks3/4/5

No existing reusable realtime/pg_notify change channel was found in affected repository sources. Spec requires access-limited ID/revision-only signals, so subscribing directly to full plan/classes rows would carry unnecessary names or operational metadata. Controller ruling: add one narrow public.timetable_invalidation_signals table in Task3, containing only signal identity, optional plan_id, change_sequence and timestamp (no class names/subjects/students/rosters). A per-plan signal uses the same plan read permission; an operational invalidation singleton is readable only to authorized timetable roles. Authenticated SELECT only with RLS, no direct client writes; private emitter/trigger owns changes. Ordinary plans/items still use the six specified storage/history tables; this extra table is only an invalidation transport.

Task3 owns schema/RLS/minimal typed event contract and per-plan emission when change_sequence changes. Task4 connects the operational signal to all relevant guarded operating/resource changes. Task5 subscribes to INSERT/UPDATE for the selected plan and operating singleton, re-fetches authorized snapshots, and keeps20second visible-only revision/fingerprint polling and focus refresh. No event payload data is trusted as the new schedule itself. Do not publish full public.classes or timetable_plan_items records. Avoid DELETE event reliance; plans are archived, signal rows can persist.

Actual isolated DB has supabase_realtime publication (puballtables=false), wal_level=replica, and no Realtime server/network. Migration can add only this table to existing publication. Verify DB signal writes/RLS/ACL and client subscription behavior locally; do not claim delivered websocket events/provider runtime from this fixture. Poll/focus fallback can be exercised against local DB transport. Production websocket verification stays a separately identified rollout gate.
