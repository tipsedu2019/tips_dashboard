# 주문·입고 일괄 수량 편집과 선택 대상 보존

- 날짜: 2026-09-10
- 작업 브랜치: `codex/dashboard-apple-design-20260909`, 기존 누적 변경 보존.
- 범위: 주문·입고 목록의 묶음 선택과 ‘선택 요청 일괄 주문’ 수량 편집.

## 변경과 판단

목록의 행 작업/메뉴는 이미 공통 컴포넌트로 적용되어 있어 유지했다. 일괄 주문 안의 표는 모바일에서도 고정 3열을 유지해 교재명이 작은 영역에서 여러 줄로 끊어지고 입력칸이 80×36px이었다.

- 기존 FormDialogContent/Input 및 색상·간격·테두리 토큰을 재사용했다. 별도 버튼이나 디자인 시스템을 추가하지 않았다.
- 데스크톱은 교재/요청/주문 수량을 같은 열에 정렬하고, 모바일은 교재명을 전체 너비로 보여준 뒤 요청 수량과 주문 입력을 배치한다.
- 학생용/교사용 배지를 보조 정보 한 줄로 정리하고 기존 조회 결과의 출판사·수업·위치를 함께 표시한다. 교재명과 보조 정보는 생략하지 않는다.
- 모바일 주문 입력을 112×44px, 데스크톱96×36px로 구성하고 숫자는 오른쪽 정렬한다. 모바일 요청 수량과 입력값의 수직 중심227px가 일치한다. 이는 프로젝트 선택 값이며 Apple 공식 치수가 아니다.

## 함께 발견한 선택 오류

준비된 목록의 한 행에는 학생용·교사용 실제 member가 포함되지만, 일괄 작업 가능 ID와 그룹 전체 선택을 대표 line만으로 계산하고 있었다. 브라우저에서 교재2건 선택 시 학생용 입력2개만 나타났고, 독립 runtime 검사에서도 교사용 입력 부재로 재현했다.

기존 `getPurchaseScopeLines`로 실제 member들을 펼쳐 처리 가능 여부를 판정하고 그룹/행 체크박스가 양쪽을 포함하게 했다. strict read-service가 검증한 기존 member ID를 사용하며, 서비스나 저장 payload를 새로 정의하지 않는다. 수정 후 같은 교재2건에서 학생용2개+교사용2개의 입력이 생성된다.

## 브라우저 검수

실제 제품 소스 + 로컬 합성 fixture의 `process-long` 데이터. 운영 데이터와 구분한다.

| 조건/동작 | 결과 |
|---|---|
| 1280×720 | 긴 교재명, scope·수업·위치, 요청/주문 수량 열 비교 |
| 390×844 | 입력80×36→112×44px, 전체 너비 제목, 페이지 가로 넘침 없음 |

| 모바일 내부 스크롤 | 본문87.5px 이동, 실행 버튼 위치 유지 |
| 학생용9·교사용4 입력 후 실패 | 두 값 유지, 오류로 초점 이동 |
| Esc 취소 후 재열기 | 시작 ‘선택 요청 일괄 주문’ 버튼으로 초점 복귀, 기본값2/2 복원 |

## 보존과 검증

- 기존 함수213개와 textbookService 호출식25곳이 동일하다. 변경 함수는 workspace의 표시 JSX와 PurchaseProcessTable의 member 선택이다. submit/open/close/입력 setter, fresh recheck, 오래된 응답 보호, 수량/가격 계산, 서비스/API/DB는 유지했다.
- 주문서·반품 요청서·이미지·PDF 코드 및 호출식은 변경하지 않았다. 기존 문서 검수를 재사용했고 이번 단계에서 출력 파일을 새로 생성하지 않았다.
- 관련 고유 검사95개 통과: workspace 구조 계약91개 + 실제 workspace 동작4개. 집중 실행한 표시 계약1개는 91개에 포함되므로 중복 합산하지 않았다. 최종 제품 빌드(TypeScript 포함), 대상 ESLint, diff 공백 검사 통과.
- 동작 검사는 모바일 행/데스크톱 행/그룹 헤더가 두 member를 선택하는지, 취소 read/write0과 재열기 기본값, 학생용9/교사용4의 정확한 lifecycle payload, 중복 제출과 실패 입력 보존, 전체6개 저장 연산 완료 후 stale 결과 억제를 검증했다.
- 추가로 ordered/received 묶음 선택이 두 scope를 입고·반품 경로에 전달하고 returned/cancelled 행은 선택되지 않는지 확인했다. 반품은 확인 미리보기와 취소까지, 입고는 fresh membership 검증 후 writer 진입까지 검사했다. 실제 반품·입고 완료나 운영 결과를 검증했다고 주장하지 않는다.
- 공용 컴포넌트 재사용을 속도 향상으로 주장하지 않는다. 새로운 요청은 추가하지 않았으며, 교사용 수량을 포함하므로 실제 저장 시 요청 수가 늘어나는 것은 누락된 업무 처리의 복구다.
- 브라우저 저장은 null Supabase의 `fixture_transport_disabled`로 차단했다. 성공 payload와 지연/실패는 합성 transport 검사로 구분한다. 운영 쓰기·외부 발송·푸시·배포 없음.
