## 저장 실패 원인과 현재 운영 상태

연결된 설정 대상 DB의 해당 반은 `legacy`이다. 서울 기준 2026-10-02에 새 10월 1일 정규 회차를 시간·강사·강의실 없이 저장하면, 과거 날짜에는 기본 주간 정보 상속이 적용되지 않아 새 `incomplete_read` 일정이 된다. 충돌 검사는 새 미확인 점유를 `23P01 / timetable_resource_conflict`로 거절한다. 다른 반과의 중복이 없어도 이 조건만으로 거절될 수 있다.

확인한 여섯 함수의 최종 로컬 본문 해시·인자·문자 수가 05:19:08 UTC DB 카탈로그와 일치했다. 합성 SELECT 네 사례에서 과거 date-only 차단, 명시 정보가 있는 과거 회차, 정상 미래 회차, 동일한 기존 미확인 이력의 보존 조건을 확인했다. 이 SELECT는 전체 저장 RPC나 운영 충돌 자료를 실행한 검증이 아니다. 실제 실패 요청 본문은 캡처하지 않았다.

사용자가 시작일을 10월 2일로 바꾸어 저장 성공을 확인했다. 에이전트가 운영 저장을 실행한 것이 아니다. 이후 05:41:09 UTC 읽기에서 10월 구간은 **10월 2일~27일**, 회차는 **6·8·13·15·20·22·27일의 7회**였다. 1일과 29일은 없다. 앞선 8회 예상은 산술상 가정이며 실제 상태로 쓰지 않는다. 9월은 1~29일, 24일 취소와 29일 정상의 기존 8회를 유지한다. 앞선 05:31 데이터의 '10월 없음'은 저장 전 관측이다.

## 수정

- 사용자가 초안에 새 정규 회차를 생성할 때 요일별 기본 시간·강사 ID·강의실 ID를 명시 값으로 채운다. 초기 조회나 렌더에서 기존 회차를 소급 보완하지 않는다.
- 같은 요일의 슬롯이 하나이고 시간과 카탈로그 자원을 유일하게 확인할 때만 채운다. 기본값이 누락·모호하면 빈 명시 필드를 남겨 저장 전 해당 날짜의 입력을 안내한다. 여러 자원 이름을 순서로 추측하지 않는다.
- 기존 회차와 직접 지정한 값은 유지한다. 새 회차의 snapshot은 재계산과 기본 정보 변경 후에도 유지되며, 일반 정규 회차의 네 입력에서 확인·수정할 수 있다.
- 변경된 과거 정규 회차 및 일부만 명시된 회차는 저장 전에 날짜별로 검증한다. 변경하지 않은 기존 이력과 date-only 미래 회차는 보존한다. 동일 날짜의 여러 회차를 날짜 단위 입력으로 함께 덮어쓰지 않는다.
- 앞쪽 날짜를 삽입할 때 회차 번호 기반 fallback이 아직 존재하는 날짜의 ID·기록을 가져가지 않게 한다. 날짜 자체를 이동하는 기존 fallback은 유지한다.

저장 대상은 선택한 월만이 아니라 전체 `schedule_plan` JSON이다. 기존 기간 보존, 학습 기록 보존, 예상 이전 plan, 요청 키, 20초 deadline, 자동 재시도 금지는 유지했다. SQL·권한·RLS·API 과거 변경 정책은 바꾸지 않았다.
