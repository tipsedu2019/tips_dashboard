## 1. 핵심 판단

현재 TIPS는 복잡한 학원 운영을 실제로 다루는 기능과 공통 UI 기반을 갖고 있다. 학생·수업·교재에는 최근 정리한 표, 페이지 이동, 상세창, 저장 보호가 있다. 따라서 새 템플릿을 씌우거나 모든 화면을 다시 만드는 것은 투자 효율이 낮다.

가장 부족한 것은 **전체 제품을 관통하는 완성도**다. 대시보드 첫 화면, 학생관리, 등록, 교재가 서로 다른 시기의 제품처럼 보인다. 고급스러움을 결정하는 날짜·단위·우선순위·정렬·버튼 위치·갱신 중 상태·긴 이름 처리까지 한 규칙으로 묶여 있지 않다. 사용자가 다음 일을 판단하고 처리하는 연속 경험도 더 다듬어야 한다.

추천 방향은 ‘조용하고 정밀한 TIPS 운영 데스크’다. 기존 흰 바탕·청색·전구 로고를 유지하고, 교육 운영의 시간·사람·수업·교재 관계가 선명하게 읽히도록 만든다. 화면의 고유성은 장식보다 **일정의 시간축, 일정한 정보 정렬, 선택 항목과 상세의 연결, 결과가 확인되는 저장 경험**에서 만든다.

## 4. ‘고가의 완성도’를 판정하는 기준

외관만으로 가격을 판단하지 않는다. 아래 결과가 함께 나와야 목표에 도달한다.

| 경험 | 목표 | 검증 방법 |
|---|---|---|
| 첫 5초 | 현재 날짜, 화면 범위, 가장 중요한 정보 1개를 찾는다 | 직원 5명에게 5초 노출 후 질문; 4명 이상 정답, 초기 내부 목표 |
| 반복 사용 | 같은 역할의 검색/추가/필터/더보기/저장이 같은 위치에 있다 | 대표 경로 8개 비교와 업무별 관찰 |
| 정보 읽기 | 숫자 단위·기준일·상태 의미를 오해하지 않는다 | 서로 다른 학생 수/수강 건수, 0/미입력/실패 구분 시나리오 |
| 행동 속도 | 핵심 5업무의 중앙 완료시간을 기존 대비 20% 단축 | 동일 합성 데이터, 같은 참여자, 순서 교차, 2회 반복; 목표값이며 현재 측정치 아님 |
| 실수 방지 | 의도하지 않은 상태 변경·이중 저장·잘못된 발송 0건 | 장애/동시성 시나리오, 기존 DB 계약 검증 |
| 디테일 | 임의 색·크기·카드·버튼의 화면별 변종을 없앤다 | 컴포넌트 목록과 시각 비교 |
| 접근성 | 주요 흐름 키보드 완료, 명확한 focus, WCAG 2.2 AA 관련 항목 검증 | 자동 검사 + 수동 키보드/스크린리더 |
| 성능 | LCP ≤2.5s, INP ≤200ms, CLS ≤0.1의 p75 목표 | 실제 사용자 환경 자료와 별도 실험실 계측 구분 |

성능 목표는 [Google Web Vitals](https://web.dev/articles/vitals), 접근성 기준은 [WCAG 2.2](https://www.w3.org/TR/WCAG22/)에 근거한다. 실제 사용자 표본이 부족하면 p75 통과를 선언하지 않고 실험실 측정만 보고한다.

| 업무 | 시작 조건 | 사용자가 할 일 | 종료 판정 |

| U04 수업계획 검토 | 작업상태 필터 적용 목록 | 지정 수업 다음 작업 열기→계획 검토→목록 복귀 | 수업·필터·페이지가 같음 |

U03/U05는 합성·격리 환경에서만 수행한다. 시작 클릭부터 종료 사실 확인까지 기록하고, 잘못 클릭/되돌아감/도움 요청을 별도로 센다. 기존/개선 화면의 수행 순서를 참여자별 교차해 학습 효과를 줄인다.

## 5. 확정할 아트 디렉션

### 5.1 시각 언어

1. 기본은 백색 작업면, 약한 중성색 탐색 영역, 기존 TIPS 청색이다.
2. 본문은 중요한 이름 → 업무 사실 → 부가 정보 순으로 무게를 둔다.
3. 브랜드 전구 로고는 현 자산을 사용한다. 임의 리디자인이나 외부 stock 이미지를 넣지 않는다.
4. 간격은 관계를 표현한다. 같은 업무의 제어는 8px, 한 영역의 내용은 16px, 영역 사이는 24px를 기본으로 한다.
5. 한 영역의 가장 중요한 실행 버튼만 청색 면으로 표시한다. 탭과 선택 상태가 같은 강한 버튼처럼 경쟁하지 않게 한다.
6. 표·필터·헤더를 각각 카드로 겹치지 않는다. 작업면 외곽 하나와 필요한 내부 구분선만 사용한다.
7. 배지는 사용자 판단을 바꾸는 상태에 사용한다. 학년·학교·과목을 모두 장식 캡슐로 만들지 않는다.
8. 수업 시간, 수량, 금액은 숫자 정렬을 지킨다. 숫자 주변에 장식 아이콘을 반복하지 않는다.

### 5.2 TIPS를 기억하게 할 세 장면

| 장면 | 표현 | 업무상 이유 |
|---|---|---|
| 오늘 일정 | 시각이 정렬된 수직 목록, 현재의 세 가지 일정 유형을 정확히 표시 | 오늘 상담/테스트/청강의 시각과 대상을 함께 판단 |
| 목록→상세→복귀 | 선택한 이름의 위치와 목록 문맥을 보존하고 상세를 연다 | ‘내가 어떤 학생/수업을 보고 있었는지’ 유지 |
| 편집→저장 결과 | 고정된 저장 영역, 정확한 진행/오류/완료 문구, 반환된 사실 표시 | 클릭했는지와 저장됐는지의 혼동 제거 |

독자성은 이 세 장면의 완성도로 만든다. 추가 3D·배경 영상·커스텀 커서·스크롤 가로채기·숫자 카운트업은 이번 운영 화면 계획에 포함하지 않는다.

## 6. 디자인 수치 명세

아래는 **권장 구현 목표**다. 현재 값을 바꿔야 하는 항목은 토큰 작업에서 한 번만 바꾸고 이후 작업은 고정값을 소비한다. 기존 `DESIGN.md`의 명시된 업무 계약은 유지한다.

### 6.1 색과 테마

| 역할 | 기본 결정 |
|---|---|
| 배경/본문/경계 | 기존 `--background`, `--foreground`, `--border` 사용 |
| 브랜드 청색 | 기존 `--primary: oklch(0.6231 0.1880 259.8145)`를 출발점으로 사용 |
| 탐색면 | 기존 `--sidebar`, 선택면은 `--sidebar-accent` |
| 보조 본문 | `--muted-foreground`; 12–14px에서도 정상 텍스트 대비 충족 확인 |
| 위험 행동 | `--destructive` 계열, 의미 있는 텍스트 라벨 동반 |
| 성공/주의 | 기존 의미 토큰 우선; 없으면 공통 토큰으로 추가하고 light/dark 쌍 정의 |
| 표 hover | 낮은 대비의 `muted` 면; 파란색 전체 행 채색 기본 금지 |
| 선택 | 공통 `accent` 면+선택 제어; focus와 동일한 의미로 쓰지 않음 |

기존 청색+흰 글자 조합의 대비는 변경 전 수치 측정한다. 4.5:1 미달이면 토큰 작업에서 청색의 명도만 필요한 만큼 낮추고, 화면별 색 보정은 금지한다. `primary`의 hue는 유지한다. hex 색을 여러 feature에 직접 넣지 않는다.

### 6.2 타이포그래피

| 용도 | 크기/행간 | 무게 | 적용 |
|---|---|---|---|
| 셸 경로 제목 h1 | 18/26px | 600 | 모든 경로 동일 |
| 대시보드 날짜 제목 h2 | 28/36px, 모바일 24/32px | 650 또는 실제 지원 600 | 첫 화면에 한 번 |

| 표 이름·일반 본문 | 14/20px | 400; 이름 550/600 | 클릭 이름의 색보다 굵기로 위계 |
| 입력 | 14/20px; 모바일 16/24px | 400 | 모바일 자동 확대 가능성 검수 |

| 보조 정보 | 12/18px | 400 | 필요한 시간·단위·맥락 |
| 대표 지표 | 28/36px | 600 | `tabular-nums` |

일반 한글의 letter-spacing은 0을 기본으로 한다. 큰 날짜 제목만 -0.02em까지 허용한다. 한글을 좁게 압축해 ‘고급’처럼 만들지 않는다. 폰트 공급은 Pretendard의 공식 배포·라이선스 확인 후 자체 호스팅하고 시스템 폴백을 남긴다. 전체 한글 폰트를 무조건 preload하지 않는다.

### 6.3 레이아웃·제어·모션

| 항목 | 목표 |
|---|---|
| 데스크톱 sidebar | 256px, 접힘/오른쪽/숨김의 기존 설정 보존 |
| 공통 header | 데스크톱 64px, 모바일 기본 56px; 긴 제목 확대 시 자연 확장 |
| 페이지 좌우 여백 | ≥1280:24px / 768–1279:20px / <768:16px |
| 본문 최대 너비 | 목록은 사용 가능한 전체 너비; 대시보드 읽기 영역은 1120px까지 |

| radius | 버튼·입력6px / 표면8px / 공통 dialog는 기존 token 규격 우선 |
| 표면 shadow | 기본 0; popover/dialog처럼 겹치는 면에만 기존 shadow 사용 |

44px는 이 계획의 주요 터치 제어 목표다. WCAG 2.2 AA의 최소 타깃 24 CSS px 및 예외와 같은 수치가 아니다. 작은 보조 아이콘은 hit area와 간격을 포함해 [W3C 타깃 크기 기준](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)을 별도 검증한다.

모바일 header는 제목·메뉴·검색 아이콘·테마 아이콘을 한 줄에 둔다. 현재 모바일의 전체 너비 ‘빠른 이동’ 제어는 아이콘으로 축약하되 접근 이름과 기존 검색 dialog를 유지한다.

## 7. 공통 컴포넌트별 계약

### 7.1 셸

- 소유 파일: `src/app/admin/layout.tsx`, `src/components/site-header.tsx`, `app-sidebar.tsx`, `nav-main.tsx`, `ui/sidebar.tsx`.
- 학생/수업만 대상으로 셸을 바꾸는 `body:has(...)` 규칙을 공통 셸로 옮긴다.
- header의 section과 title이 같으면 같은 단어를 두 번 반복하지 않는다. section 텍스트만 생략하고 h1은 유지한다.
- 메뉴 명칭·순서·권한·URL은 1차에서 변경하지 않는다. navigation redesign은 측정 후 별도 과제다.
- sidebar 스크롤 영역, 계정 메뉴 위치, 클릭으로 펼치기/접기와 포커스 복귀를 보존한다. 커스텀 단축키는 추가하거나 복원하지 않는다.
- 로고는 전 화면에서 같은 크기와 여백을 사용한다. 36px mark + 기존 2행 wordmark를 목표로 실제 자산 여백을 비교한다.
- 모바일 제목이 2행이 되면 자연 높이 확장을 허용한다. 고정 높이 때문에 제목을 잘라 의미를 잃게 하지 않는다.

### 7.2 목록 도구와 필터

- `DataTableToolbar`를 사용한다. 기본 순서는 검색 → 대표 추가/등록 → 표 설정이다.
- desktop 검색은 flex:1, min-width:240px. 주요 action과 설정은 shrink:0.
- desktop 필터는 아래 행에서 label+control로 정렬. 항목 폭160px, 긴 학교/세부과목 최대240px.
- 필터 결과 수/오류로 검색과 action의 x/y 위치가 바뀌지 않아야 한다.
- 모바일 개선은 먼저 **교재 재고의 4개 분류 필터만** 검색 한 행, 다음 행 `필터 N`과 주 행동으로 바꾼다. 다른 화면·다른 교재 탭의 직접 필터는 유지한다.
- 이 네 필터의 draft/적용은 현재 직접 노출·즉시 반영 기준을 의도적으로 바꾸는 별도 상호작용 작업이다. T09에서 UI README의 예외와 상태 계약을 함께 기록한다. 취소/Escape는 이전 조건 유지, 적용 시 페이지1. 검색·미사용 교재·기존 reset 의미는 유지한다.
- 이미 적용한 조건은 트리거 개수와 검색 아래 한 줄 값으로 표시. 동일 조건을 배지·문장·카드로 세 번 반복하지 않는다.
- 선택 가능한 값이 실제로 하나인 필터는 서버 계약·접근권한을 확인한 뒤 숨길 수 있다. 데이터 오류로 1개처럼 보인 경우 숨기지 않는다.

### 7.3 데이터 표

- 기존 `DataTableSurface`·TanStack Table·공유 pagination 사용. 가상 스크롤이나 새 표 라이브러리로 바꾸지 않는다.
- HTML table을 우선하되 등록의 다중 과목 트랙 구조는 유지한다. 공통 외관을 위해 업무 데이터를 평탄화하지 않는다.
- 첫 열은 대상 식별, 가운데는 판단 정보, 끝은 작업. 모든 열이 같은 굵기가 되지 않게 한다.
- 학생·수업·교재 식별명은 전체 줄바꿈과 행 자동 확장을 허용한다. `line-clamp-2`나 ellipsis로 구별에 필요한 뒷부분을 숨기지 않는다. 장문 메모만 상세에서 읽게 할 수 있다. 이름 전체 확인을 hover만으로 제공하지 않는다.
- 행에는 이동/상세 열기와 선택 checkbox가 충돌하지 않아야 한다. 버튼/메뉴/링크 클릭은 상위 행 동작을 중복 실행하지 않는다.
- 체크박스 범위는 ‘현재 페이지’로 명확히 유지한다. 전 페이지 bulk 선택을 새로 만들지 않는다.
- 선택 action bar는 기존 toolbar 안에서 정해진 슬롯 사용. 선택 해제/대상 변경/페이지 이동의 기존 정책을 재사용한다.
- 표 header는 내부 스크롤에서 sticky 가능. body 전체의 불필요한 가로 스크롤은 0. 내부 스크롤은 이름이 있는 region.
- `10/15/20`, 기본10, 10페이지 묶음, 첫/이전/다음/마지막은 기존 제품 계약 그대로다.

### 7.4 상세와 폼

- 학생/수업은 현재 검증된 넓은 편집 구조를 유지한다. 모든 상세를 좁은 오른쪽 drawer로 강제하지 않는다.
- 새 폼과 이미 공통 wrapper를 쓰는 화면은 조회 `DetailDialogContent`, 입력 `FormDialogContent`, 문서 `DocumentDialogContent`, 확인 `ConfirmationDialogContent`를 따른다. 학생·수업의 기존 편집 시트는 자동 치환하지 않는다. 학생 시트의 최대920px·container query·초안 수명·관계/이력 배치를 보존한다.
- dialog 크기는 내용 역할에 따라 기존 규격에서 선택한다. 화면별 무작위 max-width를 더하지 않는다.
- 제목·상태·핵심 식별은 header, 주 작업은 footer, 내용은 내부 스크롤이다.
- 한글 필드 라벨을 유지하고 필수 여부는 실제 validation 계약에서 온다. UI 디자인이 새 필수 조건을 만들면 안 된다.
- 제출 직전 입력 검증, 중복 제출 잠금, 저장 중 문구 유지, 실패 입력 보존, 성공 반환값 반영.
- 닫기/Escape/경로 이동은 기존 unsaved guard 사용. 버리기 확인을 feature별로 재구현하지 않는다.
- 포커스는 열기 버튼으로 복귀. 대상 행이 사라졌으면 같은 목록의 검색 또는 제목으로 복귀.
- 모바일 키보드가 열린 상태에서도 오류 필드와 저장 버튼에 도달할 수 있어야 한다.

### 7.5 비동기 상태

| 상태 | 화면 계약 | 금지 |
|---|---|---|
| 최초 로딩, 데이터 없음 | 최종 레이아웃과 유사한 skeleton + aria-busy | 0건 표시, 무한 spinner |
| 데이터 있음, 동일 범위 재조회 | 기존 결과 유지, 해당 영역에 작게 갱신 중 | 화면 전체 삭제 |
| 질의 변경, 결과 대기 | 새 조건은 유지; 결과가 이전 조건이면 이전 조건임을 명시하거나 결과 영역 skeleton | 새 조건 라벨 아래 이전 결과를 새 결과처럼 표시 |
| 정상 0건 | 정확한 범위의 빈 문구, 가능한 행동1개 | 오류처럼 빨간색 표시 |
| 검색 0건 | 검색 결과 없음 + 검색/필터 초기화 | 데이터 삭제처럼 표현 |
| 재조회 실패, 동일 범위 이전 결과 있음 | 마지막 조회시각+갱신 실패+재시도, 이전 결과 유지 | 최신 결과라고 표시 |
| 세션만료/권한 변경 | 보호된 결과 제거, 현재 로그인/접근 절차 | 이전 계정의 캐시 유지 |
| 저장 실패 | 입력과 상세창 유지, field 또는 footer 오류 | 성공 toast, 빈 폼 초기화 |
| 응답 역전 | 현재 요청/조건의 결과만 수락 | 늦은 응답이 현재 조건 덮어쓰기 |

‘유효 데이터 유지’는 **같은 사용자·권한·질의·날짜 범위**에서만 적용한다. 날짜가 바뀌면 어제 결과를 오늘로 표시하지 않는다. 자동 재시도/폴링/전수 catalog 요청을 새로 추가하지 않는다.

## 8. 화면별 구현 설계

### S01. 대시보드 — 가장 먼저 완성할 대표 화면

**유지:** 기존 daily brief RPC, 세 가지 일정 유형, 최대5개 upcoming, 각 항목 href. 통계·등록·학사 경로.

**desktop 배치:**

1. 셸 아래24px, 왼쪽에 `오늘의 일정` h2와 `9월 12일 토요일` 날짜, 오른쪽에 `14:30 기준`+아이콘 새로고침.
2. 아래16px에 세 지표를 하나의 정돈된 영역으로 표시. `레벨테스트 2건 / 방문상담 1건 / 청강 0건`처럼 단위 포함.
3. 아래24px에 `오늘 일정 · 시간순 최대 5개` 목록. 시각64px / 제목flex / 유형·장소 보조 정보. 각 행 최소64px, 긴 식별명은 행 자동 확장.
4. 세부 제목은 source title 전체를 사용한다. source href로 이동. 해당 유형 counts 합계가5 초과면 `등록 일정 보기`로 전체 접근을 보장한다.
5. 일정0개여도 영역 유지: `오늘 예정된 레벨테스트·방문상담·청강이 없습니다.` 한 문장. `등록 일정 보기` 링크1개.
6. 기존 바로가기3개는 하단의 낮은 위계 텍스트 링크로 보존. 사이드바보다 눈에 띄는 별도 카드로 만들지 않는다.

**모바일:** 제목/날짜와 갱신을 두 줄 이내, 지표3개는 작은 동일 폭 컬럼, 시간48px+본문, 최초 일정 또는 빈 상태가844px 높이 첫 화면에 보인다.

**날짜/상태:** `brief.localDate`를 Asia/Seoul의 달력 날짜로 해석, `generatedAt`은 실제 조회시각. 0과 미조회는 다르게 표현. `openTasks`가 계약에 있어도 정의와 현재 정책을 확인하지 않고 새 카드로 노출하지 않는다.

**시간 의미:** 현재 SQL은 오늘 scheduled 상태 일정의 시간순 첫5개를 반환한다. 현재 시각 이후 조건이 없으므로 ‘앞으로 남은 일정’이라고 부르거나 지난 시각을 임의로 제외하지 않는다. 최종 migration 정의 `20260813192115_dashboard_daily_brief.sql`을 구현 때 재확인한다.

**범위 확장 조건:** ‘오늘 처리할 업무’ 집계는 기존 action producer와 권한, 완료 정의, 링크, bounded query가 별도로 확정될 때만 2차에서 도입. 첫 작업에서 과거에 없앤 할 일/알림 패널을 복원하지 않는다.

### S02. 학생관리 — 전체 표의 기준 화면

- 현재의 검색/필터/추가/표 설정 위치와 넓은 표를 기준으로 한다.
- 기본 열은 선택44 / 이름 min180 / 학교 min120 / 학년64 / 학생연락처152 / 학부모연락처152 / 재원상태88 / 작업44. 사용자 저장 너비가 있으면 우선하고 초기화 동작 유지.
- 학생명은14/20·600, 학교/학년/연락처14/20·400. 상태는 텍스트 기반, 특별한 상태만 의미색.
- 전화번호는 저장값을 바꾸지 않고 표시 함수만 통일한다. 유효 국내 휴대폰은 `010-0000-0000`; 기타 포맷/국제번호는 원문 보존. `tel:`/복사 동작이 있으면 정규화된 표시와 실제 값 정책을 구분.
- 상세의 기본정보 → 수업 연결 → 수업교재 이력 순서를 유지. 연결/이력은 공간을 충분히 사용하고 복수 작은 카드로 잘게 나누지 않는다.
- 모바일은 현재 지원 방식을 검토해 이름·학교·학년·재원상태가 첫 줄/두 번째 줄에 보이게 한다. 두 연락처를 삭제하지 않고 상세에서 접근 유지.
- 정렬·필터·페이지·열 설정·선택·학생 detail deep link를 회귀 항목으로 고정한다.

### S03. 수업관리

- 학생 표와 같은 shell/toolbar/table/action 체계를 사용한다.
- 수업명 → 과목·학년 → 선생님 → 요일·시간 → 수강 인원 → 상태 → 작업 순으로 판단 흐름을 검토한다. 기존 필수 열/사용자 설정은 보존한다.
- 같은 선생님·장소를 매 요일마다 장문으로 반복하지 않는다. 단, 요일별 담당자/장소가 다른 수업은 반드시 각각 표시한다.
- 날짜·시간은 `월 19:30–21:30` 형식. 배열을 문자열로 합치다 다른 슬롯과 혼동하지 않게 각 슬롯 줄 단위.
- 신규 수업 생성/그룹 연결/폐강/삭제는 기존 원자적 서비스 호출과 상태 조건 그대로. UI 단순화를 이유로 두 개 독립 쓰기로 분리 금지.

### S04. 등록

- 9단계의 현재 workflow와 counts, 내 담당/전체, 목록/달력, 학생별 복수 과목 트랙을 유지한다.
- 같은 과목 표식은 트랙의 기준 위치에서1회 표시. 각 셀에서 필요 없이4회 반복하지 않는다.
- 복수 과목이면 각 트랙이 같은 행 높이/순서로 정렬되어야 한다. 과목 표식을 없애 대응이 불분명해지는 경우는 제거하지 않는다.
- 기본 판단 순서: 학생·학교 → 과목/진행 → 예정일시·장소 → 담당자 → 가능한 다음 행동.
- 조회 행 클릭은 상세만 연다. 상태 select/발송/취소는 기존 명시 동작과 guard를 사용한다.
- `미정`은 작은 중성 텍스트. 업무상 필수 일정 누락이 확인된 경우만 주의 상태를 표시한다.
- 모바일 단계탭은 수평 탐색 또는 기존 공유 responsive pattern; 현재 선택 단계가 늘 보이게 한다. 9단계를 새 funnel로 합쳐 상태 규칙을 바꾸지 않는다.
- 고객 안내 문구/템플릿/발송 트리거는 UI 통일 작업에서 수정하지 않는다.

### S05. 수업계획 / 수업일정

- 수업계획의 현재 작업상태 구분·공통 표·모바일 목록·다음 행동은 보존한다.
- 수업일정의 `0/0회`는 관련 조회가 성공했고 현재 수업·기간에 수락된 계획 회차가 실제0인 경우에만 백분율 대신 `계획 없음`으로 표시한다. 로딩/오류/미조회/권한 없음/선택 기간 없음은 기존 별도 상태를 유지한다. 실제 값과 상태 판정은 바꾸지 않는다.
- `기록 없음`과 `대기 회차가 없습니다`가 같은 사실을 반복하는 조건이면 하나만 표시한다. 둘의 원천/의미가 다르면 병합하지 않는다.
- 모든 행의 `정상` 배지는 약한 텍스트로 낮춘다. 실제 경고가 있는 행은 텍스트+아이콘+수정 링크로 식별한다.
- ‘설계’와 상세 열기의 차이를 문맥에서 분명히 한다. 반복 청색 버튼은 보조 variant로 낮추되 action은 유지한다.
- 동기 그룹과 실제 회차의 구분을 보존. 값이 없다고 자동으로 ‘미연결’로 바꾸지 않는다.
- 행 자체 link 안의 개별 link/button은 의미 구조와 키보드 동작을 점검하고, 중첩 anchor가 실제 생성된다면 수정한다. AX만으로 HTML 위반 확정 금지.

### S06. 교재관리

- 5탭과 각 탭의 주 업무를 유지한다. `정산` 탭과 과거 중복 ‘교재 목록’을 다시 만들지 않는다.
- 재고: 이름 최우선, 분류 보조, 본관·별관·합계 우측 정렬. 합계 숫자가0이라고 경고색을 주지 않는다.
- 요청: 요청 수량과 실제 대상, 주문할 수량의 관계가 한 행에서 읽혀야 한다. 임의 ‘부족10권’ 같은 고정 기준 금지.
- 주문·입고: 주문/입고/남은 수량과 다음 입고 동작의 정렬. 부분 입고·완료 상태를 실제 서버 계약대로 표시.
- 출고: 실제 출고 대상/수량/반품 가능 상태와 작업을 함께 읽는다. 반품 액션은 기존 계약의 가능 여부를 따른다.
- 재고 실사: 조사 수량 입력, 기존 수량, 적용 결과의 차이를 같은 행에 표시. 편집 중 셀과 저장된 결과를 섞지 않는다.
- 모바일: header56 + 업무탭 최대88 + 검색44 + action44 + 간격을 합쳐 **필터 닫힘 기본 상태 첫 재고 항목 시작 y≤360px**를 목표로 한다. 긴 제목/200% zoom에서는 고정 좌표보다 접근성을 우선.
- 여러 탭의 수량 편집과 dialog는 현재 공통 component를 사용한다. 출력 문서/내보내기의 데이터와 계산은 별도 회귀 확인.

- 숫자7개를 모두 큰 카드로 만들지 않고 재고/배정/진도처럼 실제 의미의 섹션으로 정리한다.

### S08. 학사일정·시간표·기타 운영·설정

- 이번에는 코드 경로와 운영 화면 일부만 확인했다. 완성된 시각 감사라고 보고하지 않는다.

## 10. 성능과 구현 구조

1. Next/React/Radix/TanStack/React Hook Form/Zod/Lucide/Recharts를 유지한다. 라이브러리 교체와 디자인 변경을 함께 하지 않는다.
2. 기존8초 RPC timeout·retry 정책, bounded query, 페이지 크기를 유지한다. 체감 개선을 위해 캐시 전체를 전수 미리 읽지 않는다.
3. 디자인 작업에서 effect·service·RPC·SQL을 동시에 바꾸지 않는다. 순수 view 추출과 동작 변경은 다른 카드다. T02/T17은 accepted-data와 identity/query 경계를 다루는 명시적 비동기 상태 카드이며, 표시 전용 T03/T18과 분리한다.
4. 색/폰트/크기/상태는 공통 layer에 둔다. 학교·수업·등록 규칙은 feature가 소유한다.
5. 향후 entity 검색은 별도 API 설계로 다룬다. 사용자·role·tenant 범위, 응답 cap, IME 조합, abort, stale guards, detail href 계약이 먼저다.
6. 측정은 같은 장비·브라우저·빌드·데이터·네트워크 조건으로 before/after 비교한다. 초기 cold5회/warm5회는 개별값·중앙값·최소/최대만 기록한다. p95 판정은 충분한 별도 표본과 측정 방법이 있을 때만 사용한다. 소표본 실험실 결과를 실제 사용자 p75로 표기하지 않는다.
7. 대표 화면의 초기 JS와 전송 크기는 baseline 대비10% 이상 증가하면 원인을 검토한다. 수치만 맞추려고 접근성/기능을 제거하지 않는다.
8. 폰트 전송량·layout shift를 별도로 기록한다. 한국어 subset 전략의 비용을 화면 로드 이득과 비교한다.

## 11. 구현 순서와 병렬화

| 단계 | 작업 | 단계 종료 기준 | 권장 기간* |
|---|---|---|---|
| 0 | 최신 기준, 역할/fixture, before 증거, 대표 target 확정 | 같은 화면 재실행 가능 | 1–2일 |
| 1 | 첫 대시보드 상태·날짜·빈 화면 완성 | S01의 모든 상태가 명확 | 2–3일 |
| 2 | 셸, 폰트, 공통 token·상태 gallery | 경로 이동 시 외곽·제어가 동일 | 3–5일 |
| 3 | 학생/수업 대표 표·상세와 모바일 | 목록→편집→복귀 workflow 통과 | 3–5일 |
| 4 | 등록/교재/수업일정 확장 | 반복 표식·모바일 밀도 개선, 도메인 회귀0 | 5–8일 |
| 5 | 통계·나머지 화면 정렬 | 전 경로 일관성과 정보 정확성 | 3–5일 |
| 6 | 직원 사용성 검수·성능·접근성·릴리스 검수 | 실측 근거와 결함 종료 | 3–5일 |

*작은 숙련 팀과 AI 협업을 가정한 계획 범위이며 약4–7주의 달력 기간이 적절하다. 운영 이슈/검수 참여/수정 라운드에 따라 달라진다. AI 코드 생성 시간과 승인·사람 검수·배포 시간을 합쳐 ‘당일 완성’으로 약속하지 않는다. 실제 작업량은 첫 대표 화면 완료 후 다시 추정한다.

병렬화는 최대3개 쓰기 lane: A 셸/공통 토큰 담당, B 화면 feature 담당, C QA/접근성 담당. A의 token/interface 변경이 끝나기 전 B가 독자적인 수치를 도입하지 않는다. 같은 파일을 여러 AI가 동시에 수정하지 않는다. 각 카드 전후로 최신 baseline을 확인한다.

## 12. 낮은 추론 모델로 빠르게 구현하는 운영법

- **계획 결정과 실행을 분리한다.** 이 문서에서 고정한 수치/상태/위치를 구현 모델이 새로 고민하지 않게 한다.
- 작업은 한 화면·한 상태 묶음으로 끝낸다. 한 카드가5개 이상의 복잡한 feature에 걸치면 다시 나눈다.
- 카드 입력은 목표 + 읽을 파일 + 허용 수정 파일 + 사용하는 컴포넌트 + 입력/기대값 + 실행할 검사만 준다.
- 기초 상태/레이아웃 조정은 낮은 추론으로 가능하다. 상태 규칙·권한·캐시 범위·DB·동시성은 별도 설계와 검토로 분리한다.
- 기준 이미지와 실제 component fixture를 함께 준다. prose만으로 미세 배치를 매번 재해석시키지 않는다.
- 모델이 문서와 코드 차이를 발견하면 새 구현으로 덮지 말고 차이3줄과 제안1개를 남긴다. 범위 밖 파일을 조용히 고치지 않는다.
- 완료 보고는 변경·검사·증거·남은 문제4항목. 성공한 테스트가 증명하지 않는 배포/실제 저장을 주장하지 않는다.

복사할 프롬프트와 개별 작업의 상세는 작업 카드 문서에 있다. 첫 실행은 **T00 → T01 → T02 → T03** 순서다.

GPT-6 Astra의 카드 단위 실행은 **Medium**을 시작점으로 권장한다. 비동기 상태·권한 경계·초안 저장·여러 화면에 걸친 변경은 **High**, 재현이 어려운 결함이나 계획과 실제 구조의 충돌은 **XHigh**로 검토한다. 수준을 바꾸지 않고 전체 구현을 맡길 경우에는 **High**를 권장한다. 이는 이 계획의 작업 범위에 대한 실무 권장값이며 공식 성능 보장이나 벤치마크가 아니다. 실제 설정은 Codex의 모델/추론 선택에서 바꾸며 문서의 문구만으로 변경되지 않는다.

## 13. 제품 내부 품질 목표

목표는 직원이 매일 사용하는 대시보드의 높은 완성도다. 실제 출품은 진행하지 않는다. 기존 T24는 취소하며 완료 조건에 포함하지 않는다.

- 업무 정확성과 빠른 다음 행동을 기본 통과 조건으로 삼는다.
- 전구 로고·청색·시간축·목록/상세 연결을 일관되게 적용한다.
- 정상·빈 화면·로딩·실패·저장 중 상태까지 실제 브라우저에서 확인한다.
- 기존 합성 fixture와 화면 캡처는 구현 및 회귀 검수에 사용한다. 별도의 심사용 체험 환경을 만들지 않는다.
- T22의 사용성·접근성·성능 검수와 T23의 릴리스 검토 자료는 제품 완성도를 확인하기 위해 유지한다.
- 개선 수치는 실제 측정 결과가 있을 때만 기록한다.

최근 [Linear의 공식 UI 개선 기록](https://linear.app/now/behind-the-latest-design-refresh)도 같은 화면 위계와 행동 위치의 일관성에 집중한다. TIPS가 참고할 점은 그 작업 방식이며, Linear의 모양이나 영문 UI를 그대로 복제하는 것이 아니다.

## 14. 최종 완료 판정

### 기능 및 사용성

- 핵심5개 업무를 처음부터 끝까지 실행하고 기존보다 덜 혼동하는지 확인.
- 모든 대표 화면에서 이름·현재 상태·다음 행동·조회/저장 결과를 찾을 수 있음.
- 모든 기존 메뉴·권한·deep link·pagination·저장·발송 보호 유지.

### 시각

- 전 화면의 셸/브랜드/글꼴/제어/표/모달이 같은 시스템으로 보임.
- 1440·1280·390에서 잘림/과도한 빈 영역/불필요한 가로 넘침/중복 CTA 없음.
- 빈 화면과 실패 화면에도 의도된 구조가 있음.

### 기술과 증거

- 변경 범위 focused test, typecheck/lint/build, 실제 browser, 접근성/성능 검증을 구분해 기록.
- UI만 바꾼 릴리스와 DB 변경 릴리스의 검사 범위 구분.
- DB를 바꾸는 별도 작업은 migration 순서상 최종 함수, 정확한 SQLSTATE, pgTAP, RLS/ACL/lock/idempotency 검증.
- 업무 충돌에 임의 `40001`을 붙이지 않음. 실제 데이터베이스 동시성 충돌만 해당 SQLSTATE 사용.
- 운영 배포는 승인된 별도 실행 때 CI/main SHA/Vercel READY/alias/runtime을 다시 확인.
- 외부 provider 활성화·고객 발송은 배포 성공과 분리.

가장 중요한 첫 결과물은 ‘전체 화면을 한 번에 고친 사이트’가 아니라, **나머지 화면이 그대로 따라 만들 수 있을 만큼 완성된 대시보드와 학생관리 기준 화면**이다. 그 기준을 고정하고 빠르게 확장한다.
