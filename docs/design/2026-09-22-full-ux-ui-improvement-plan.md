# TIPS UX/UI 개선 실행 계획

2026-09-22 · 상태: 구현 반영, 최종 검증 진행 중 · 사용자 추가 메뉴 정리 범위 반영

[구현·검증 기록](2026-09-22-ux-ui-implementation.md) · [리뷰와 근거](2026-09-22-full-ux-ui-review.md)의 F01–F17에 사용자가 추가한 **최근 대시보드 수준의 메뉴 내부 정리**를 통합했다. 공통 버튼·글꼴·색상·기본 틀을 유지하면서, 메뉴 안의 정보 순서·표 폭·검색·필터·주 행동을 정리한다. 조회 실패를 빈 결과로 오인하지 않고 모바일과 편집 창에서 작업을 끝낼 수 있어야 한다.

## 1. 순서와 분할

### 메뉴 개선 순서

아래 메뉴 순서가 실행 우선순위다. 뒤의 T 번호는 수정 범위를 연결하는 식별자이며 번호 순서대로 모든 메뉴를 일괄 수정한다는 뜻이 아니다. 각 메뉴에서 관련 조회·편집·접근성 문제를 함께 해결한다.

| 순서 | 우선순위 | 메뉴 | 내부 정리 범위 | 연결 작업 |
|---|---|---|---|---|
| 1 | 높음 | 학사일정 → 캘린더 | 일정 셀의 강한 색·그림자, 잘리는 제목, 날짜 이동·검색·보기 전환 배치, 최초 실패→재시도 복구 안정성 | T9, 해당 범위의 T1·T6 |
| 2 | 높음 | 전반·퇴원 | 넓은 표, 숨겨진 검색, 신청·처리 단계별 핵심 정보와 다음 행동 | 해당 범위의 T1·T4 |
| 3 | 높음 | 휴보강 | 상태별 불필요한 열, 검색·필터, 신청/처리 창의 정보 계층과 실패 복구 | 해당 범위의 T1→T2→T4 |
| 4 | 중간 | 영어 단어 재시험 | 중첩 외곽 틀, 반복 배지·강조, 필터와 시험 시작·점수·처리 행동 배치 | 해당 범위의 T1·T4 |
| 5 | 중간 | 알림 설정 | 이중 탭의 역할·스타일, 강한 선택 표시, 하단 저장 영역, 채널 장애 격리 | 해당 범위의 T8 |
| 6 | 중간 | 홈페이지 관리 | 검색·필터·목록의 공통 구성, 행 높이, 수정·순서 변경 배치, 탭 연결 | 해당 범위의 T8 |
| 7 | 낮음 | 채용 지원서 | 중복 제목, 빈 상태·목록·페이지 이동 구성, 삭제 후 초점 복귀 | 해당 범위의 T2·T8 |

대시보드·등록·학생관리·수업관리·교재관리·수업계획·시간표·학교 연간 일정표는 주요 개편이 반영된 기준 화면으로 유지한다. 통계와 기본 설정 목록의 추가 시각 정리는 위 메뉴보다 후순위다. 기존 F06 상세 총원, F07 일정 미리보기, F09/F10 설정 저장 문제 등은 해당 결함을 고치는 범위로 남긴다. **전자결재와 수업그룹 설정은 삭제된 기능이므로 개선 대상에서 제외한다.** 활성 화면에 남은 퇴역 기능 문구만 정리한다.

프로필 잘림(F02)과 모바일 탐색(F04/F16)은 메뉴 공통 결함이므로 T2/T3의 작은 독립 변경으로 처리할 수 있다. 메뉴 내부 정리의 기본 순서는 **캘린더 → 전반·퇴원 → 휴보강**으로 유지한다.

### 수정 범위와 의존 관계

| 묶음 | 해결 항목 | 적용 시점·선후 관계 | 결과 |
|---|---|---|---|
| T0 기준 고정 | 전체 | 가장 먼저 | 최신 main 기반 재현·fixture·비교 화면 |
| T1 조회 상태/복구 | F01 | 메뉴 순서에 따라 해당 조회 범위부터 | 실패/0건/이전 결과의 명확한 구분 |
| T2 편집 창 완결성 | F02, F03, F15 | 프로필은 독립, 휴보강은 해당 T1 뒤, 채용은 메뉴 순서 | 오류·저장·닫기·초점 도달 |
| T3 모바일 탐색 | F04, F16 | 독립 공통 변경 | 선택한 화면이 바로 드러남 |
| T4 업무 검색/표/정보 계층 | F05, F08, 추가 메뉴 정리 | 전반·퇴원→휴보강→재시험, 각 T1 및 휴보강 T2 뒤 | 찾기·식별·다음 행동의 일관성 |
| T5 상세 인원 | F06 | 독립 재현 후 결함 범위 수정 | 목록/상세 총원 일치 |
| T6 일정 편성/예외 복구 | F07, F14 | F14는 캘린더 T9와 함께, F07은 별도 결함 수정 | 생성 전 날짜 확인·복구 후 상세 진입 |
| T7 설정 편집 | F09, F10, F12 | 결함 수정 유지, 추가 시각 정리는 후순위 | 조회 정렬/저장 분리·오류 위치 확인 |
| T8 탭/채널/목록 구성 | F11, F13, F17, 추가 메뉴 정리 | 알림→홈페이지→채용 순서 | 탭·저장·목록의 공통 구성과 장애 격리 |
| T9 캘린더 내부 정리 | 사용자 추가 범위, F01/F14 연결 | T0 다음, 메뉴 개선 첫 작업 | 읽기 쉬운 일정과 안정적인 날짜 탐색 |

PR은 메뉴와 검토 가능한 크기로 나눈다. `ops-task-workspace.tsx`를 건드리는 T1/T4는 동시에 수정하지 않는다. `makeup-request-workspace.tsx`는 T1 조회 오류 분리→T2 제출 오류 분리→T4 검색·표·정보 계층 정리 순서로 통합한다. 캘린더의 T1/T6/T9는 같은 변경 책임 아래 순차 통합한다. DB나 저장 payload를 바꾸는 T5/T7은 단순 시각 변경과 구분한다. 실제 일정은 담당자와 fixture 준비 수준에 따라 정하고, 근거 없는 완료일을 약속하지 않는다.

## 2. T0 — 현재 기준과 재현 고정

1. 작업 시작 시 원격 main·작업 HEAD·운영 배포를 다시 대조한다. 이번 audit 기준은 `b0f16bf5`, 로컬 HEAD는 `9f962dfc`였다. 기존 수정 문서와 다른 작업의 파일을 덮어쓰지 않는다.
2. 구현은 최신 main에서 `codex/` 브랜치의 독립 checkout으로 시작한다. 이번 계획 작성만으로 운영 적용을 수행하지 않는다.
3. 영향을 받는 실제 경로와 공통 소비자를 적는다. 정보 계층·강조 수준은 최근 `/admin/dashboard`, 목록 합성은 `/admin/students`와 `/admin/registration`, 편집은 `/admin/classes`, 설정은 `/admin/settings/schools`를 기준으로 삼는다. 대시보드의 카드 배치를 다른 메뉴에 그대로 복제하지 않는다. 공통 `DataTableWorkspaceToolbar`, `DataTableFilterPanel`, `DataTableRowActions`, `WorkspaceTabs`, `FormDialogContent`를 우선 사용한다.
4. 테스트용 합성 학생·수업·명단·일정으로 정상/0건/실패/지연/긴 이름을 준비한다. 운영 개인정보와 연락처를 fixture·PR에 복사하지 않는다.
5. 1440×900과 390×844, 같은 데이터·필터·테마·스크롤의 수정 전 화면을 남긴다. 본 audit의 1710px 운영 화면은 문제 증거이며 정밀한 전후 비교 baseline을 대신하지 않는다.

완료 조건: 재현 명령/경로, 초기 데이터, 예상 실패를 기록하고 실제로 재현했다. 오래된 문서나 source-only 추정을 그대로 실패 테스트로 굳히지 않는다.

## 3. T1 — 조회 상태와 복구

**파일:** `src/features/tasks/ops-task-workspace.tsx`, `src/features/makeup-requests/makeup-request-workspace.tsx`, `src/features/academic/timetable-workspace.tsx`, `src/features/academic/curriculum-workspace.tsx`, `src/features/operations/academic-calendar-workspace.tsx`. 관리 목록도 같은 패턴이 확인되면 `management-page.tsx`, `management-data-table.tsx`에 적용한다. 반복 피드백은 `src/components/ui/action-feedback.tsx` 및 공통 목록 구성을 먼저 검토한다.

- 수락된 데이터 없음+조회 중: 최종 배치를 보존하는 로딩.
- 수락된 데이터 없음+조회 실패: 작업 이름이 있는 한국어 오류와 재시도. ‘없음’/등록 유도/0건 단정 금지.
- 조회 성공+0건: 전체 빈 상태와 필터 결과 없음을 구분, 필요한 행동 하나.
- 수락된 데이터 있음+갱신/다른 조건 요청 중: 이전 행 유지, 현재 조건과 수락된 조건 차이를 표시. 데이터 내보내기는 실제 수락된 조건과 맞을 때만.
- 재조회 실패: 이전 결과와 시점/조건 유지, 재시도 위치·초점 유지. 무기한 ‘확인 중’ 표시를 실패 후 계속 쓰지 않는다.
- 알 수 없는 raw timeout/provider 문구는 화면용 오류와 내부 진단을 구분한다. 휴보강의 중복 오류 영역은 조회 범위별로 하나씩 정리한다.

| 검증 입력 | 기대 결과 |
|---|---|
| 최초 요청 timeout/503 | 정상 빈 결과 없이 오류+재시도만 표시, toolbar 유지 |
| 재시도 성공 0건 | 이때만 ‘없음’, 페이지 범위 0–0 |
| 재시도 성공 2건 | 오류 해제, 총2/실제2 일치 |
| 10행 성공→다른 필터 지연/실패 | 이전 행·페이지/스크롤 보존, 이전 조회 기준 식별 가능 |
| 조건 A→B→C 응답 역전 | 마지막으로 수락할 수 있는 요청만 반영 |
| 키보드 재시도/필터 | body로 초점 유실 없음, 중복 요청 제한, 상태 발표 |

관련 기존 보호는 `tests/ops-task-list-navigation.test.mjs`, `tests/numbered-pagination.test.mjs`, `tests/data-table-pagination.test.mjs` 및 각 feature의 조회 hook/서비스 테스트를 확인한다. 테스트가 실제 timeout과 렌더링 조합을 실행하는지 점검하고 문자열 존재 검사만 추가하지 않는다.

## 4. T2 — 편집 창의 완료·오류·초점

**파일:** `src/components/nav-user.tsx`, `src/components/ui/form-dialog.tsx`, `src/components/ui/dialog.tsx`, `src/features/makeup-requests/makeup-request-workspace.tsx`, `src/features/recruiting/recruiting-inbox.tsx`.

- 프로필: 공통 고정 header/footer, `min-h-0` 스크롤 body. 모바일 아바타는 전체 폼을 밀어내지 않도록 높이를 조정한다. 저장/닫기 순서·역할은 기존 공통 기준을 따른다.
- 프로필 검증: 비밀번호 길이/불일치/재인증 요구를 입력과 연결하고 첫 오류로 초점 이동. 값과 입력 상태 보존. 성공은 status, 실패는 alert.
- 휴보강: 조회 오류는 페이지, 제출 오류는 현재 dialog. 승인/반려/환불 등 각 작업의 실패 이유·메모·재시도를 그 dialog에 둔다.
- 채용: 삭제 성공 후 사라진 행 대신 유효한 목록 제어로 초점 복귀. 운영 삭제 재현 없이 mock으로 확인한다.

| 검증 입력 | 기대 결과 |
|---|---|
| 프로필 390×844/390×667, 200% 확대 | 모든 입력과 저장·닫기가 내부 스크롤로 보임, 페이지 바깥 넘침 없음 |
| 휴보강 submit 실패/권한 만료/충돌 | 열린 창 안에 원인 표시, 입력 보존, 중복 상신 없음 |
| 수정 후 취소/이탈 취소 | 기존 초안 보호 계약 유지 |
| 마지막 지원서 삭제(mock) | 오류 없는 빈 상태, 초점이 새로고침/유효 목록 제어에 있음 |

관련 테스트: `tests/dialog-opener-focus.test.mjs`, `tests/sidebar-focus-return.test.mjs`, `tests/makeup-draft-navigation.test.mjs`. 삭제 backend 테스트는 UI focus 증거를 대신하지 않는다. 공통 Dialog를 바꾸면 학생/수업 편집과 교재 문서 창도 확인한다.

## 5. T3 — 모바일 탐색과 현재 위치

**파일:** `src/components/nav-main.tsx`, `src/components/app-sidebar.tsx`, `src/components/ui/sidebar.tsx`.

- 수락된 route 이동에 맞춰 모바일 sheet 닫힘을 연결한다. 로고·일반 메뉴·설정 하위 메뉴·현재 화면 재선택을 포함한다.
- 미저장 입력 때문에 이동을 취소하면 초안과 원래 화면을 유지한다. 하위 메뉴 펼치기는 이동으로 취급하지 않는다.
- 부모의 확장/포함 상태와 leaf 현재 페이지를 구분한다. 연간표에서 캘린더 leaf를 현재 페이지로 표시하지 않는다.
- 단순 Escape는 원래 메뉴 버튼, 성공한 이동은 새 업무 화면으로 초점을 돌린다. desktop sidebar 접힘 설정은 유지한다.

검증: 실제 `NavMain`을 사용해 390px에서 메뉴 선택→sheet 닫힘→본문 조작을 확인한다. 기존 `tests/sidebar-focus-return.test.mjs`의 가짜 Link에만 닫기 callback을 넣어 통과시키지 않는다. `tests/admin-shell.test.mjs`의 retired route/빠른 이동 계약도 유지한다.

## 6. T4 — 전반·퇴원·휴보강·재시험의 정보 계층

**파일:** `src/features/tasks/ops-task-workspace.tsx`, `src/features/makeup-requests/makeup-request-workspace.tsx`, `src/components/data-table/`의 기존 검색·표 설정·행동 구성.

- 검색·필터·신규 신청·표 설정을 공통 toolbar에 모으고 검색 진입을 열 헤더/아이콘 안에 숨기지 않는다. 데스크톱은 검색과 핵심 필터를 바로 보여주고 모바일은 검색 접근을 유지한 채 공통 필터 패널을 사용한다.
- 전반/퇴원/휴보강 검색 범위를 독립 상태로 분리한다. 헤더 정렬은 정렬만 바꾼다. 검색 scope를 바꾸는 API가 필요하면 기존 페이지/서버 정렬 계약을 먼저 확인한다.
- 모바일 검색 버튼을 열었을 때 무엇을 찾을 수 있는지 명확하게 한다. 학생/이전 수업/이후 수업을 누락하지 않는다.
- 전반·퇴원 표는 현재 코드의 신청/처리 단계별로 학생, 관련 수업, 효력일, 상태, 담당자와 다음 행동의 우선순위를 먼저 정한다. 현재 단계에서 비어 있거나 판단에 쓰이지 않는 부가 열은 상세/표 설정에서 보존한다. 1440px 기본 보기에서 대상 학생과 다음 행동이 함께 보이게 하고 긴 수업명은 줄바꿈한다. 모든 열을 작게 축소해 맞추지 않는다.
- 전반 카드: 학생 식별명→이전/이후 수업→효력일/현재 단계→다음 행동. 긴 출발 수업 때문에 목적지가 숨지 않게 한다.
- 휴보강 표는 실제 상태별 필요한 열과 현재 가능한 행동을 정리한다. 신청 창은 대상 학생·원 수업·변경 일정·사유 순서, 처리 창은 신청 내용 확인·처리 판단·처리 행동 순서로 묶는다. 각 화면에서 같은 정보를 요약 카드와 폼에 반복하지 않는다. 승인/반려/환불 등 기존 조건과 초안은 보존하며 F03 오류는 해당 처리 영역 안에서 복구한다.
- 재시험 데스크톱: 학생·상태·응시예정·진행 중 점수·현재 가능한 주 행동을 우선한다. 교재/범위/이력은 기존 정보를 보존하면서 상세/표 설정으로 접근한다.
- 재시험의 외곽 틀은 공통 목록 면 하나로 정리하고 탭·필터·표를 각각 카드로 감싸지 않는다. 같은 상태를 반복하는 배지와 상시 강조를 줄인다. 필터는 목록 위, 시험 시작·점수 입력·후속 처리는 해당 학생 행에 둔다. 실제 위험/실패와 현재 선택의 의미는 유지한다.
- 실제 table/head/body/cell과 접근 가능한 열 설정을 사용한다. 사용자 열 폭/순서의 기존 저장값은 보존하고 명시적 기본값 복원에서 추천 구성을 적용한다.

검증 데이터: 학생 이름과 수업 이름이 다른 기록, 같은 접두사의 긴 수업명 40자, 대기/진행/합격보고/불합격/재재시험, 점수0/빈값/상한/저장 실패. 검색 중 날짜 정렬해도 검색 조건은 유지되고 학생과 현재 주 행동이 1440px에서 함께 보여야 한다. VoiceOver 표 관계와 키보드 열 설정은 별도 확인한다.

전반·퇴원·휴보강은 실제 단계/상태마다 0건·1건·다건을 비교한다. 단계 전환과 화면 폭 변경 후에도 검색·선택·점수/신청 초안이 유지되어야 한다. 기본 표와 사용자 저장 열 구성을 각각 검증하고, 행 선택 전후 검색·필터·첫 행의 위치가 움직이지 않아야 한다.

## 11. T9 — 캘린더 내부 정리와 조회 안정성

**첫 메뉴 작업.** 사용자가 추가한 정상 화면의 시각·배치 관찰과 최초 조회 실패 후 재시도 복구 사례를 반영한다. 이번 리뷰의 캡처 08은 실패 상태만 기록했으므로, 착수 시 정상·밀집 일정 화면을 별도로 확보해 비교한다.

**파일:** `src/features/operations/academic-calendar-workspace.tsx`, `src/app/admin/calendar/components/calendar.tsx`, `calendar-main.tsx`, `calendar-sidebar.tsx`, `date-picker.tsx`. 조회 안정성은 `src/features/operations/use-operations-workspace-data.ts`, `operations-read-service.js`와 실제 호출 RPC를 필요한 범위에서 추적한다. `/admin/calendar` 경로가 redirect여도 이 디렉터리의 Calendar 컴포넌트는 현재 학사 캘린더가 사용한다.

- **일정 셀:** 강한 전체 배경·상시 그림자·hover 이동을 줄이고 제목/시간/학교 등 식별 정보가 먼저 읽히게 한다. 일정 종류의 도메인 색 의미는 유지하고 선택·오늘·오류는 구분한다. 시간표·학교 연간 일정표의 표현을 함께 바꾸지 않는다.
- **긴 제목:** 단일/다일 일정의 배치와 겹침을 보존하면서 필요한 줄바꿈과 높이를 정한다. 월간 셀에 모두 담을 수 없는 제목도 클릭·키보드·모바일 상세에서 전체를 읽을 수 있게 한다. hover만 유일한 확인 방법으로 두지 않는다.
- **상단 제어:** 이전/오늘/다음과 기준 날짜, 검색·조건, 월간/목록 보기와 새 일정 행동을 역할별로 묶는다. 검색과 보기 전환을 서로 떨어진 외곽 틀에 두지 않고, 모바일에서는 현재 날짜와 주 행동을 유지하며 조건을 펼친다. 날짜 이동/필터/보기 변경 뒤에도 현재 조건과 초점을 알 수 있어야 한다.
- **조회 안정성:** 첫 조회 실패→동일 범위 재시도의 요청 범위·소요시간·오류 종류를 재현 환경에서 기록한다. 실패 원인을 특정하기 전에 고정 대기나 반복 자동 재시도를 추가하지 않는다. 마지막 성공 범위와 데이터를 보존하고 사용자 재시도는 중복 요청 없이 해당 범위를 다시 읽는다. 오류 표시(T1), 요청 역전 방어, 한 주 복구 후 상세 진입(T6/F14)을 함께 확인한다.

| 검증 입력 | 기대 결과 |
|---|---|
| 일정 0/1건, 하루 12건, 다일 일정, 제목 40자 | 종류 구분 유지, 제목 확인 가능, 겹침/더 보기/상세 연결 보존 |

관련 기존 테스트: `tests/academic-calendar-ui.test.mjs`, `tests/academic-calendar-range-interaction.test.mjs`, `tests/calendar-day-hydration.test.mjs`, `tests/event-form-draft-navigation.test.mjs`. 실제 동일 데이터의 전후 캡처로 색·제목·제어 배치를 확인한다. 조회 지연은 같은 조건에서 전후 측정하고, 원인 미확인 상태를 성능 개선 완료로 보고하지 않는다.

## 12. 완료 판정과 재검토 기준

각 PR은 다음을 구분해 기록한다.

1. **구현 근거:** 변경한 파일, 재사용한 공통 구성, 기존 권한/API/저장 설정 보존 여부.
2. **자동 검증:** 필요한 상태·서비스·회귀 테스트의 실행 명령과 실제 결과. 관련 없는 전체 suite 반복 대신 변경 범위에 맞춘다.
3. **브라우저:** 같은 fixture의 1440/390px 전후, keyboard/focus, 긴 내용, loading/empty/error, 다크/reduced motion 중 영향받는 상태. 표 선택 전후 툴바/첫 행 위치도 확인한다.
4. **디자인 계약:** shared token/component를 바꾸면 `DESIGN.md`와 영향받는 형제 화면을 함께 확인한다. feature CSS로 공통 token을 재정의하지 않는다.
5. **배포:** merge/CI, DB migration 적용, 배포 URL/commit, 운영 읽기 검증을 각각 별도 증거로 남긴다.
6. **실제 업무:** 데이터 저장·알림 provider/수신 확인은 배포와 구분한다. 리뷰용 fixture 성공으로 운영 저장/발송 완료를 선언하지 않는다.

검증 중 기본 권한·학생/수업 상태·기존 일정/교재·초안/저장 선호가 바뀌거나 작업 범위 밖 migration이 필요해지면 변경 범위를 다시 나눈다. 색·카드·요약 설명을 늘려 해결하려 하지 말고, 사용자가 현재 상태와 다음 행동을 알아볼 수 있는지를 재검토한다.
