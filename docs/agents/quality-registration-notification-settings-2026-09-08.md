### 함께 고친 실행 결함

- 방문 provider 요청의 `workflow_key` 누락으로 실제 카드 렌더 검증이 실패하던 경로를 수정했다.
- 방문 dispatch plan의 서비스 역할 호출과 실제 관리자 검증 조건을 맞췄다.
- 관리팀 legacy 전달에서 검증된 담당 원장 멘션이 provider에 전달되도록 연결했다.
- 방문/취소·관리팀·청강의 HTTP 408은 `delivery_unknown`으로 보존한다. 결과 불명확 상태를 확정 실패로 바꾸어 다시 보내지 않는다.
- 관리팀은 미리보기 이후 규칙·멘션·연결이 변경되면 최종 DB 외부 시도 단계에서도 차단한다.
- 청강 수신 강사는 등록 건 전체를 읽을 권한이 보장되지 않으므로 청강 카드에서만 앱 이동 버튼을 생략한다. 공용 provider의 본문·멘션·링크 검증과 다른 알림의 이동 버튼은 유지한다.
- 과거 OFF 요청, 이미 전달된 요청, 이전 처리 흔적이 있는 요청을 관리팀 미리보기에서 먼저 구분하며, 해당 이력 화면의 재발송 버튼은 숨긴다. 후속 개선에서는 처리 이력이 전혀 없는 이전 요청만 현재 내용으로 다시 확인하여 새 안내를 준비할 수 있다. 이전 요청·문구·영수증은 보존하며 자동으로 재생성하거나 발송하지 않는다. [구체적인 복구 계약](../operations/2026-09-08-registration-management-notification-preview.md)을 참조한다.
- 고객 이력과 설정의 새 RPC는 서비스 역할뿐 아니라 활성 관리자 여부도 확인한다. 정지·삭제 계정의 RPC 조회는 `42501`로 거부한다.
- 기존 고객 `check`에 15초 제한과 취소 신호를 연결했다. 조회 창·사용자·등록 건이 바뀌면 늦은 응답이 새 화면이나 다음 요청의 잠금을 바꾸지 못한다.

### 후속 개선: 미발송 요청 복구

현재 규칙·문구·멘션·연결과 과거 요청이 다르면, 읽기 전용 미리보기에서 복구 가능 여부를 계산한다. 모든 소유권 claim과 전달 이력이 없고 작업 큐도 처리된 적이 없을 때만 `현재 내용으로 새 안내 준비`를 허용한다. 이미 전송을 시작했거나 결과가 불명확하면 새 요청을 만들 수 없다.

`ensure_registration_workflow_notification_v4`는 사용자가 확인한 이전 요청 ID와 내용 지문을 다시 검증한다. 이전 원본은 별도 관계로 보관 처리하고 새 원본과 연결한다. 이전 원본·확인 기록·요청 영수증을 수정하거나 지우지 않는다. 같은 확인 키의 재시도는 최초 응답을 반환하며, 다른 관리자의 오래된 확인은 거부한다. 복구와 발송 시작·큐 처리에 같은 잠금 기준을 적용하여 이전 요청이 뒤늦게 전송되는 틈도 막는다.

화면에서는 보관된 이전 요청과 새 안내의 전달 기록을 다시 열어볼 수 있다. 응답 유실 후 확인 키를 재사용하고, 새 시도에서 이전 오류 표시를 초기화한다. 등록 사실에 저장 전 변경이 있으면 복구 미리보기와 전달을 차단한다.

설계 근거는 PostgreSQL의 [명시적 잠금과 잠금 순서](https://www.postgresql.org/docs/17/explicit-locking.html), Supabase의 [함수 권한](https://supabase.com/docs/guides/database/functions)이다. 새 내부 관계 테이블은 비공개 스키마에 두고 일반 사용자·서비스 역할의 직접 접근을 허용하지 않는다. 새로운 알림 공급자나 자동 발송 기술은 추가하지 않았다.

후속 최종 검증은 다음과 같다.

- 영향 범위 Node 49/49, 실제 UI timeout 재시도 회귀 포함. 최종 Next production build·타입 검사 통과. 전체 ESLint 오류 0개, 기존 파일 경고 5개. 마지막 변경 파일의 ESLint도 오류·경고 0개.
- 격리 DB 04차: 기준 parity/smoke 1,937개, 정렬된 전체 마이그레이션 적용, DB lint, 등록 알림 9개 pgTAP 파일 298/298, 최종 운영 계약 읽기 전용 검사 모두 통과.
- 실제 두 DB 연결의 경합 6/6: 서로 다른 관리자, 같은 확인 키 재시도, 복구와 이전 발송 claim의 두 가지 선후 관계, 큐 claim 선점, 같은 target 작업 재요청. DB 잠금 대기를 직접 관찰했고, 오래된 원본 6건 보존·중복 replacement 없음·큐 재요청 deadlock 0개·provider 호출 0회를 확인했다.
- 실제 앱 컴포넌트의 CUA 검증: 복구 취소, 확정, 이전/새 기록 연결, 전달 완료·결과 불명 재전송 차단, 상태 충돌, timeout 후 같은 확인 키 재사용과 경고 해소, 미저장 등록 정보 차단. 1280px와 390px에서 가로 넘침 없음.
- 기존 마이그레이션 68개와 앞선 신규 5개의 SHA를 유지했다. 복구 마이그레이션 `20260908062222`의 최종 SHA는 `89ef4c52e56f943823675a314b02764f8568fb9a73fc153bfafd02daf13d9c4a`이며 새 6개는 로컬 `candidate` 상태다. 이번 검증에서 만든 DB 컨테이너와 임시 작업공간은 정리했다.

### 릴리스 검토에서 보완한 사항

- 실제 방문 취소 목록의 공개 응답에 발송 카드 전용 `href`가 포함되어 엄격한 클라이언트 DTO 검증이 목록 전체를 거절하는 문제를 고쳤다. 공개 projection에서만 제거하고 private 미리보기·카드 링크·확인 지문을 유지한다. 격리 DB의 실제 목록을 실제 서비스 파서에 전달하는 별도 probe를 CI에 추가한다.
- 청강·취소의 조회와 전달에 15초 제한 및 취소 신호를 적용한다. 응답이 끝나지 않아도 모달 잠금이 풀리며, 전달은 결과 확인 상태가 된다. 새 조회에서 상태를 확인하기 전에는 재전송하지 않고, 같은 내용의 명시적 재확인은 기존 키를 유지한다.
- 설정 조회·원자적 저장도 인증 토큰 취득부터 응답 본문 읽기까지 제한 시간을 적용한다. 저장 응답이 끊기면 초안과 요청 키를 보존하여 결과를 다시 확인할 수 있다.
- 최초 설정 마이그레이션에 `lock_timeout=5s`, `statement_timeout=120s`를 추가하여 배포 중 무제한 잠금을 방지한다. 앞선 로컬 후보의 해시 기록과 구분해 설정/취소 두 파일의 릴리스 해시를 다시 고정했다. 이미 `main`에 있는 68개 마이그레이션은 수정하지 않았다.
- 새 등록 회귀 검사와 실제 DB probe를 PR CI에 연결했다. 배포 후 읽기 전용 검증은 SQL 문자열·주석과 실제 변경 명령을 구분하며, 전체 파일 해시·읽기 전용 트랜잭션·마지막 rollback 검사를 유지한다. 운영 배포 workflow의 명령·비밀값 범위·해시는 변경하지 않았다.

이 단계의 확정된 마이그레이션 6개는 manifest `final`로 전환했다. `final`은 검토 대상 파일의 내용 고정을 뜻하며 운영 DB 적용을 뜻하지 않는다. 릴리스 검증 증거는 `.codex-artifacts/registration-release-20260908/`에 별도로 기록한다.

### 범위와 해석

방문 취소는 과거 안내의 내용과 논리 채팅방 `google_chat.management`를 보존한다. 과거 실제 webhook/space 주소가 원래 이력에 없으므로 그 주소까지 고정했다는 뜻은 아니다. 고객 설정의 템플릿 검증 기록도 실시간 공급자 확인이나 특정 수신자의 도착 보장이 아니다. 새 관리팀 UI가 미리보기 확인을 거치며, 호환성을 위한 기존 명시적 v2 RPC는 그대로 유지된다.

고객 이력의 `발송 결과 확인`은 기존 접수 ID로 provider 결과를 확인해 해당 영수증을 갱신하는 동작이다. 단순 SELECT가 아니며, 입학신청서 접수가 확인되면 기존 계약에 따라 `admission_notice_sent`와 감사 기록도 반영한다. 새로운 메시지 발송이나 입학 실행을 시작하지 않는다. `SOLAPI 접수 완료`와 최종 `도착 확인`은 구분한다.

아래는 구현 전 감사와 제안 원문이다. 해당 절의 ‘현재’와 소스 줄 번호는 초기 감사 시점을 가리킨다.

등록 Google Chat의 기본 화면을 **방문상담 인계 / 관리팀 진행 공유** 두 묶음으로 정리한다. 개별 이벤트와 이력을 합치거나 삭제하는 것이 아니라, 업무 단위로 설정을 보여준다. 이전 흐름의 12개 규칙은 기본 화면에서 제외하고 읽기 전용 보관 영역으로 분리한다. 고객용 알림톡은 별도 탭에서 관리한다.

지금 필요한 일은 꺼진 16개 규칙을 일괄 활성화하는 것이 아니다. 실제 발송 경로와 연결되지 않은 설정을 먼저 구분하고, 현재 명시적 발송 동작에 필요한 설정만 운영자가 선택하게 해야 한다.

## 현재 상태와 의미

| 분류 | DB 규칙 수 | DB 설정 | 현재 화면 | 정리 방향 |
| --- | ---: | --- | --- | --- |
| 방문상담 | 5 | ON · 고정 | 5행 | 한 묶음. 예약/변경 문구와 이전 이벤트 호환을 구분 |
| 관리팀 진행 공유 | 4 | OFF | 4행 | 한 묶음. 상담 신청·상담 완료·대기 신청·등록 신청 |
| 이전 청강 자동 알림 | 7 | OFF | 7행 | 자동 생성·claim 경로 폐지. 일반 편집에서 제외 |
| 이전 등록 종료 처리 | 2 | OFF | 2행 | 등록 완료·문의 종료. 현행 등록 UI 발송 호출 없음 |
| 이전 예약 리마인드 | 3 | OFF | 이미 숨김 | 이전 설정 보관에 통합 |
| 합계 | 21 | ON 5 / OFF 16 | 18행 | 기본 업무 묶음 2개 + 이전 설정 12개 |

방문상담 5개가 ON이라는 사실은 다섯 상황 모두가 현재 발송된다는 뜻이 아니다. 현재 `ensure_registration_visit_notification_v1`은 예약 상태 `scheduled`만 허용한다. 최초 명시적 전송에서는 예약 이벤트, 이전에 준비된 방문 알림 원본이 있으면 변경 이벤트를 준비한다. 이 원본의 존재가 전송 성공을 뜻하지는 않는다. 교체·과목 제외는 현재 원본 검증의 호환 목록에 남아 있다. 취소는 원본 검증 목록에서도 제외되며, 취소 상태는 명시적 전송 준비를 통과하지 못한다. **취소 알림은 ON 표시와 실제 동작이 어긋나는 우선 수정 대상**이다.

운영 DB에서도 청강 자동 materialize 함수의 `55000 / registration_observation_chat_automatic_materialization_retired`, 빈 결과를 반환하는 claim 함수, 관련 자동 트리거 0개를 확인했다. `lightweight` 모듈은 코드에 남아 있지만 현재 앱 호출이 없고 DB enqueue는 0을 반환한다. 코드 파일이 존재한다는 이유로 현재 운영 기능으로 제시하지 않는다.

등록 dispatch flag는 ON이지만 phone/visit/solapi adapter flag는 OFF다. 방문상담에는 별도 명시적 발송 경로가 있으므로 이 flag 하나로 전체 방문상담 발송 상태를 판단할 수 없다. 과거 청강 전송 이력이 남아 있어도 현재 자동 경로가 살아 있다는 증거는 아니다.

## 무엇이 복잡함을 만드는가

1. **사용할 수 없는 설정이 일반 설정과 섞여 있다.** 청강 3시간 전 알림·종료 30분 뒤 피드백 요청 등 폐지된 자동 경로를 지금도 켤 수 있는 것처럼 보여준다.
2. **실제 발송 시점과 설명이 다르다.** “상담 완료 상태가 저장되었을 때”라고 쓰여 있지만 현재는 등록 상세의 별도 관리팀 알림 버튼이 발송을 시작한다. 진행상태 저장은 발송하지 않는다.
3. **저장 방식이 섞여 있다.** 규칙과 문구는 초안 후 하단 저장, 멘션은 클릭 즉시 별도 저장이다. 멘션만 바꾸면 하단은 여전히 “변경사항이 없습니다”라고 표시한다.
4. **편집기를 닫는 행위가 취소가 아니다.** 입력 즉시 부모 초안이 바뀌고, X·Escape·편집 완료는 모두 닫기만 한다. 다음 저장에 의도하지 않은 문구가 포함될 수 있다.
5. **같은 정보가 반복된다.** Google Chat 전용 표에 채널 열이 다시 있고, 과목팀·멘션 설명·고정 배지가 각 행에 반복된다. `구글챗 · 관리팀 / 구글챗`과 `관리팀 / Google Chat`처럼 이름도 섞인다.
6. **화면이 길고 좁다.** 운영 화면 390×844 점검에서 가로 넘침은 없지만 문서 높이는 5,515px, 규칙 패널 높이는 5,056px였다. 기본 데스크톱 폭에서도 표 내부 가로 스크롤로 이벤트 이름이 잘릴 수 있다. 설정을 찾아 비교하기 어렵다.
7. **연결의 범위가 모호하다.** 업무 아래 연결 탭에 전역 5개 Chat 연결이 표시된다. 실제 방 이름은 현재 DTO에 없고 역할 이름·마스킹 주소·과거 검증 시각만 있다. “연결됨”을 현재 메시지 수신 보장으로 읽으면 안 된다.

## 제안 화면

```text
등록 알림                                      수신 채팅방 관리

[직원 알림 · Google Chat]  [고객 안내 · 알림톡]

방문상담 인계          관리팀       설정 켜짐 · 고정       상세 보기
관리팀 진행 공유       관리팀       4개 단계 꺼짐          상세 보기

이전 설정 12개 보기
```

메인 목록에는 알림 목적·받는 방·현재 설정·상세 진입만 둔다. 채널·트리거 설명·변수·멘션은 해당 상세에서 한 번만 보여준다. 두 묶음을 만드는 것을 전체 ON/OFF 스위치 추가로 해석하지 않는다. 특히 방문상담의 기존 고정 전달 정책은 일반 스위치로 바꾸지 않는다.

상세에서는 상황을 선택한 뒤 **발송 시점 → 받는 방과 담당자 → 실제 문구 미리보기**를 보여준다. “설정 켜짐”, “발송 방식: 직접 보내기”, “이전 경로용”, “연결되지 않은 동작”을 서로 구분한다. 과목별 진행 공유 버튼에는 “영어 진행상태 공유”처럼 대상 과목을 표시한다.

`?workflow=registration&section=rules&group=visit`처럼 선택 상태를 URL에 보존한다. 키보드로 설정 버튼을 구분할 수 있도록 “방문상담 인계 상세 보기”와 같이 접근 이름을 지정한다. 390px에서는 별도 중첩 카드 대신 같은 두 업무 행을 세로로 배치한다.

| 청강 피드백 | 후속 기능으로 제안 | 선생님 피드백 요청은 Google Chat에서 명시적으로 전달. 폐지된 폼/RPC를 되살리기 전에 Chat 답변 또는 신규 입력 방식 중 실제 운영 방식을 결정 |

고객 탭의 상태는 단순 ON/OFF보다 `준비됨 / 설정 필요 / 접수 / 전달 완료 / 결과 확인 필요`처럼 실제 의미에 맞춘다. 단, “준비됨”은 현재 템플릿·수신자·권한 검사 결과가 있을 때만 표시한다. 자동 리마인드와 과거 묶음 메시지 종류가 타입에 남아 있다는 이유로 신규 운영 메뉴에 포함하지 않는다. 취소된 등록건도 과거 접수 기록의 전달 결과를 조회할 수 있어야 한다.

## 저장과 문구 개선

- 편집기는 별도 로컬 초안을 갖고 `취소` / `변경사항에 반영`을 제공한다. X·Escape는 편집기를 열기 전 값으로 돌아간다. 페이지 최종 저장 전 변경한 규칙과 문구를 함께 검토한다.
- 멘션을 즉시 저장하는 현재 방식은 단기적으로 상세에 옮겨 저장 시점을 명시한다. 최종적으로는 규칙·멘션·문구를 **하나의 서버 트랜잭션**에서 각 revision과 idempotency를 검증해 저장한다. 두 API를 순차 호출하고 한 번에 저장된 것처럼 표시하지 않는다.
- 문구의 기본 정보는 학생·과목·일정·장소·담당자·다음 행동이다. “관리팀이 확인하고 있어요”처럼 확인하지 않은 진행 사실을 기본값으로 쓰지 않는다. 변경 안내는 이전/새 일정, 취소 안내는 취소된 예약을 구체적으로 표시한다.
- 실제 Google Chat 방 이름을 확인할 수 있도록 연결 메타데이터를 보완한다. 현재 역할→연결 매핑을 임의의 방 선택기로 바꾸지 않는다. Webhook 교체와 테스트 전송은 전역 연결 관리에 둔다.

## 구현 순서와 완료 기준

1. **설정과 실행 가능성 일치.** 서버 설정 목록에 현행/이전 흐름 구분을 추가하고 UI뿐 아니라 편집 요청에서도 이전 자동 규칙 재활성화를 막는다. 기존 규칙 ID·템플릿·전송 이력은 보존한다. 방문 취소의 ON 표시와 미연결 상태를 바로잡는다.
2. **두 묶음의 설정 UI.** 반복 열 제거, 수신 방·직접 발송 시점 표시, 별도 편집 취소, URL 상태 보존, 이벤트가 포함된 접근 이름. 기본 상태와 오류·저장 중·긴 문구를 데스크톱/390px/키보드에서 확인한다.
3. **운영 설정 적용.** 관리팀 진행 공유 네 종류를 실제 수신 방·미리보기로 검토한 후 필요한 종류만 활성화한다. 기존 사실 편집이 발송을 일으키지 않는지, 중복 클릭과 실패 재시도가 중복 전달을 만들지 않는지 검사한다.
4. **필요한 동작 보완.** 방문 취소 전달을 먼저, 청강 담당 전달·피드백 요청과 취소 등록건의 과거 알림톡 조회를 다음으로 구현한다. 자동 리마인드를 재활성화하지 않는다.

설정 정리 성공은 행 수만 줄어든 것이 아니다. 운영자가 두 묶음에서 수신 방과 발송 시점을 알 수 있고, 저장 결과가 문구와 멘션에 일관되며, 화면에서 허용된 동작이 실제 발송 경로와 맞아야 한다. 배포·설정 활성화·실제 공급자 결과는 각각 검증한다.
