# Personal read connection candidate

Local candidate only; no production SQL, provider call, real key operation, merge or deployment is authorized.

## Chosen flow and approval scope

Keep administrator-issued credentials and their existing live administrator-issuer checks unchanged. Add `issuer_kind=self_teacher` only for keys whose issuer and owner both equal the authenticated actor. The existing administrator default and immutable identity trigger prevent converting old keys. A verified teacher uses Settings → API → Connection keys to select explicit current classes and shared academic schools, review expiry, issue once, then enter the secret into their own agent's secure input. The UI never copies, sends, stores or logs that secret. All current owner, assignment, school, expiry and rate checks still run on the three existing GETs.

An administrator-only alternative would require an administrator provisioning and handing a teacher a key; it would not provide self-service issuance, and keys would continue to stop if that administrator loses eligibility. This candidate deliberately implements one complete self-service teacher flow. Staff/viewer/assistant and fallback roles receive no new UI or issuance permission. Loss of teacher role blocks both lifecycle and reads; administrator recovery of old records remains an operational task outside this UI. Shared school selection does not imply student-school membership; the underlying teacher calendar read is already shared, and the key narrows it to explicit school UUIDs.

Production approval must name: one issuer-kind column/check plus updated identity trigger on the private credential table; a private RLS operation ledger/index; two private helpers; the strictly anchored issuer branch update to the service-only read function; and execute permission on `agent_personal_connection_v1(text,jsonb)` solely for `authenticated`. There is no new table read grant, service-role issuance, business write scope, auth-provider change, Chat/MakeEdu integration or migration of old keys. Source SQL is `personal-connection-lifecycle.sql`, intentionally outside ordered migrations until separately approved and finalized for installation.

## Lifecycle contracts

- `snapshot` returns only the caller's credential metadata and 10/15/20-row pagination. Pending request reconciliation uses the same per-owner advisory lock as mutations. An absent request is closed with a failed tombstone, so a delayed original request cannot mint a key afterward.
- `targets` performs literal name search with 10/15/20-row pagination and total from one statement snapshot. Selections persist across pages and are capped at 50 per resource type; no first-50 catalog truncation exists.
- `issue` derives scopes from explicit grants; it never accepts owner, issuer or arbitrary scopes. It locks current account/profile/catalog/class/assignment/school authority, limits five active keys and ten issues/day, and stores only a SHA-256 digest. A retry with the same ID and input returns metadata plus null secret; changed intent conflicts. No automatic transport retry occurs.
- `revoke` locks the exact own credential. The existing read function holds that row through authorization/projection; whichever transaction acquires it first completes first, and a later read fails after revocation. A currently running authorized read can complete before a waiting revoke commits.
- Only request metadata persists in sessionStorage: `{requestId, kind}` for issue/permissions recovery and an independent `{requestId, credentialId}` journal for restrictive revoke. Account switch/unmount discards the in-memory secret and late replies. Loss of sessionStorage causes fail-closed errors; recovery of a completed issue returns its exact metadata and a revoke action, never its secret.
- The existing API availability flag blocks new teacher issuance in the UI while preserving own list, recovery and revoke. The flag gates the three HTTP reads; it is not a database authorization switch and cannot stop direct authenticated lifecycle RPC calls. Database containment requires the separately approved execute revocation below. It does not remove previously granted keys.
- One-day default, 1/7/30-day UI choices, 30-day server maximum, explicit confirmation, and no empty-as-all grants. No secret renewal/edit-in-place.

## Installation and recovery boundary

This is a transaction-wrapped one-time proposal. It has a five-second lock timeout and strict source anchor: unknown read-function source aborts installation. It is not an automatically rerunnable migration. Before an approved rollout, capture the then-current main/read-function source, promote through the repository migration/preflight process, install SQL first, verify ACL and all three GETs with a separately approved test key, then release the UI. Do not deploy UI alone or merge while SQL is absent. Repeating the exact proposal must fail atomically without changing the installed state.

Emergency containment requires separate production approval: revoke execute on the new lifecycle RPC to stop issuance, revoke only self_teacher rows to stop those reads, and revert teacher UI navigation. Existing administrator rows are not modified by that containment. Do not drop credential history/operation tombstones while delayed requests or audit needs remain. Restoring the old read-function issuer branch rejects self keys; preserve their rows and hashes for audit. No rollback SQL is executed by this candidate.

## Exact application and rollback scope

The approved installation would alter `dashboard_private.agent_personal_dashboard_credentials` (`issuer_kind`, its value check and `agent_personal_self_identity`), replace `dashboard_private.agent_personal_dashboard_identity_v1()`, create `dashboard_private.agent_personal_connection_operations` plus `agent_personal_connection_operation_owner_time`, create the private class-eligibility and metadata helpers, patch `public.agent_personal_dashboard_read_v1(text,text,jsonb)`, and create `public.agent_personal_connection_v1(text,jsonb)` owned by `postgres`. RLS is enabled on the new ledger with no direct policies or grants; only the security-definer entrypoint accesses it. The lifecycle entrypoint grants EXECUTE only to `authenticated`, with PUBLIC/anon/service_role explicitly revoked.

Before any production installation, approval must identify the exact candidate SHA/SQL digest, captured live function definitions/ACL/owners, and expected schema/migration state. Source-anchor drift aborts rather than improvising a patch. The transaction commits all candidate objects together or rolls them back; a failed installation must be checked against the captured catalog before retrying. Existing administrator credentials are classified by the default, never reissued or transformed to self keys.

After a successful installation, approved containment has three ordered phases: (1) revoke EXECUTE on the lifecycle entrypoint from `authenticated` and commit that permission change; (2) drain all preexisting lifecycle transactions, including idle transactions with uncommitted results, or terminate the identified sessions under separate operational approval, and verify they have ended; (3) in a new transaction mark only unrevoked `issuer_kind='self_teacher'` credentials revoked, commit, then verify no active self keys remain and a fresh authenticated lifecycle call is denied. Do not combine permission revocation and the final credential sweep without the drain barrier: an earlier issue can otherwise commit a credential that the sweep could not see. If the relevant old transactions cannot be identified or proven drained, containment is incomplete; pause ingress and obtain a separately approved database-session drain before proceeding. Preserve every administrator row and operation tombstone. Already authorized in-flight reads may finish before the credential row lock is obtained. Reverting the UI to the captured pre-candidate main removes teacher issuance navigation; it does not revoke database access by itself. Restoring the captured old read function is optional defense in depth after self-key containment and must restore its captured owner/ACL as well. Keep the added schema and immutable identity enforcement for audit; do not drop the column, helpers or ledger as an emergency rollback. Physical cleanup is a separate reviewed migration after outstanding requests and retention obligations are resolved. No production containment, credential update, ACL change or rollback has been executed.

## Feature permissions extension (local, not installed)

The complete external operation inventory is `src/features/agent-api/feature-registry.json`: 21 versioned HTTP operations, with exactly three personal read operations enabled. Four additional internal category markers explain student, payment, textbook and class lifecycle exclusions; they are not an exhaustive inventory of private RPCs. UI, OpenAPI annotations, server route checks and the generated private SQL policy all consume this registry. Contract tests fail on missing/extra OpenAPI operations or stale generated policy. Existing business credentials retain their separate scope model and administrator checks. Personal-default-deny metadata does not redefine business credential permissions.

Use `node scripts/generate-personal-feature-permissions.mjs --check` to detect drift. Generation uses the immutable original lifecycle proposal plus `scripts/fixtures/personal-feature-permissions.template.sql`; do not hand-edit its generated output. Installation order is lifecycle SQL, then `personal-feature-permissions.sql`, followed by protocol-compatible UI. This second proposal is intentionally outside migrations. A missing or old `permissionVersion` fails closed even for an empty inventory.

A new personal key starts with no implicit permissions and requires explicit choices. The server intersects its stored feature IDs with immutable original scopes/targets, current teacher identity/account status, current assignment and current school access. Revoking a current assignment or owner role therefore invalidates corresponding reads even if a checkbox was previously selected. Unsupported write/internal features have no active personal checkbox. Updating features never widens original class/school UUID bounds. All three may be unchecked to pause the key. Newly added registry entries do not grant existing keys access.

The extra SQL scope is: add `feature_ids` (empty default) and `feature_revision` with checks to the private credential table; add `permissions` operation kind and before/after feature arrays plus applied revision to the private ledger; create the postgres-owned private policy helper with all client EXECUTE revoked; replace metadata/lifecycle helpers; add an exact feature gate inside the existing service-only read function while its credential row lock is held. A frozen one-time backfill maps only the original three reads from existing personal credential scopes (including administrator-issued personal keys); it never derives grants from a future registry. No business credential, student row, contact field, auth provider or delivery permission is altered.

Permission saves require the expected revision and use the same owner advisory lock and credential row lock. Stale competing intent fails `55000`; identical request replay returns the original audit plus current credential metadata without reverting later changes. Clearing a feature blocks a later read (`42501`); an already authorized transaction may complete before the save obtains its lock. Cancellation/rollback leaves no revision or ledger entry. Recovery of an absent request writes a durable failed tombstone before allowing new mutable intent. Mutation and failed-recovery budgets are separate (100/day each); restrictive whole-key revoke remains available even when both are exhausted.

If pending recovery fails, the UI separately validates a read-only inventory while preserving that request ID. Issue and permission changes stay blocked. A distinct revoke journal allows explicit same-ID recovery of a lost revoke response without discarding or overwriting the original permission request. Pending data contains no secret or grants. One-time display still requires the user to enter the key into their own agent's secure input; no clipboard/send integration exists.

Production approval must cover both exact SQL digests, the frozen backfill, all currently eligible teachers (no pilot allowlist), new mutable feature fields and audit retention. Recheck current production definitions/ACL/owners and column/function collisions specifically for the new proposal; old lifecycle-only compatibility evidence does not cover it. The existing three-phase containment (EXECUTE revoke and commit, drain all earlier lifecycle transactions, final self-teacher revoke and verification) remains required. Reverting the feature read gate alone would restore broader original scopes for existing keys and is not a safe containment procedure.
