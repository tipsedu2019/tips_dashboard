# 직접입력 기간 초안의 잘못된 조회 방지

## 운영 재현

PR #77의 날짜 입력 지연 로딩을 운영 검증하는 중 발견했다. 그 PR은 코드 로딩 시점만 바꾸었으며 이 필터 매핑은 기존 main에서도 동일했다.

퇴원 목록에서 `직접입력`을 선택하면 날짜를 고르기 전에 아래 조건이 통계 RPC로 전송됐다.

```json
{"p_type":"withdrawal","p_filters":{"taskType":"withdrawal","search":"","statuses":[],"view":"applicant","subject":null,"teacher":null,"period":"custom","dateFrom":null,"dateTo":null,"filterColumn":null,"sortColumn":null,"sortDirection":null}}
```

운영 응답: HTTP 400, SQLSTATE `22023`, `ops_task_filters_invalid`. 번호 목록 서비스도 완성되지 않은 범위를 로컬에서 거부해 오류가 표시됐다. 전반과 단어 재시험도 같은 매핑을 사용한다.

## 수정

- UI의 기간 입력 초안과 API에 적용한 조건을 분리한다.
- 날짜 두 개가 유효하고 시작일이 종료일보다 늦지 않을 때만 새 조건을 목록/통계 양쪽에 적용한다.
- 미완성·역순·존재하지 않는 날짜는 마지막 정상 조건과 같은 객체를 유지한다. 따라서 추가 RPC와 불필요한 통계 취소/재시작도 생기지 않는다.
- 정상 조건이 없는 첫 진입의 잘못된 기간은 전체 기간으로 조회하고, 사용자/역할/경로/업무 종류/목록 탭이 바뀌면 이전 조건을 재사용하지 않는다.
- 두 날짜가 잘못된 경우 입력 옆에 오류를 표시한다. 날짜 선택, 검색창, 공용 입력 스타일, 권한과 API의 엄격한 유효성 검사는 유지한다.

## 검증

실제 workspace와 실제 read service를 연결한 회귀 테스트에서 퇴원/전반/단어 재시험 각각 다음을 확인한다.

1. 직접입력 선택, 시작일만 선택, 역순 날짜: 추가 목록/통계 RPC 0건.
2. 유효한 범위 완성: 목록/통계 RPC 각 1건, 동일 범위, 1페이지.
3. 역순 입력 오류 노출 및 정상 범위로 수정 시 해제.
4. 이전 오늘 조건 유지, 사용자 변경 시 초기화, 불가능한 날짜/0000년 차단, 윤년 날짜 허용.
5. 미완성 기간에서 다른 탭으로 이동하면 새 탭의 목록/통계를 조회하며 이전 탭의 결과를 새 결과로 유지하지 않는다.

SQL은 변경하지 않는다. 기존 엄격한 계약은 `ops_task_page_reads_test.sql`과 `ops_task_numbered_pages_test.sql`의 `22023` 회귀 검사에 남긴다. 운영에 비즈니스 저장/발송을 수행하지 않는다. 배포와 운영 결과는 release-verification.md에 따로 기록한다.

최종 로컬 검사: 관련 테스트 240개, production build/타입 검사, 변경 파일 ESLint 통과.
