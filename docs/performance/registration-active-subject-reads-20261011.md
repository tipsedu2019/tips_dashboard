# 등록 상세의 비활성 과목 청강 보조 조회

## 범위와 측정의 구분

기준 main은 `372c6a9930f0fe673433cbce90bb586ff9b33ead`다. PR135의 청강 deep-link editor preload와 독립된 변경이다. SQL, RPC 인자/권한, 청강 판정, 수강 저장, 승인, 정산, 발송 또는 기존 오류 진단은 변경하지 않는다.

2026-10-11 운영 관찰에는 완료 목록의 `list_ops_task_numbered_page_v1` 4.587초, `classes` 4.393초, `get_ops_task_list_stats_v1` 4.345초가 기록됐다. 일반 상세 재방문의 manager RPC 3건은 각각 약 2.55초였으나 요청 인자는 수집되지 않았다. 이 숫자는 한 번의 운영 관찰이며 아래 합성 검증의 전후 시간이나 이번 변경의 효과가 아니다.

## 호출 경로 확인

- 완료 목록은 `view: completed`, 빈 statuses, 현재 검색어/페이지로 번호 페이지 hook → numbered service → `list_ops_task_numbered_page_v1` 1회를 시작한다. 이전 범위 요청을 취소하며 재시도는 꺼져 있고 8초 제한이 있다. 범위 밖 페이지 보정의 정상 추가 조회를 제외하면 코드에서 중복 호출을 찾지 못했다.
- 통계 RPC와 runtime 보강은 독립적으로 실행된다. 완료 목록의 linked label 보강은 전체 선택정보 5종(profiles/classes/textbooks/teacher_catalogs/academic_schools)을 병렬로 읽는다. 목록 수업명에 필요한 classes와 상세 선택정보의 분리는 추가 후보지만 이 PR은 해당 캐시/오류 경계를 바꾸지 않는다.
- 상세의 활성 청강 패널은 `(활성 과목, attemptLimit 20)`을 읽는다. 수강 시작일 편집기는 `loadRegistrationEnrollmentStartObservation` → `(그 과목, attemptLimit 1)` → 결정 청강이 있으면 feedback을 읽는다. 모든 과목 편집기가 숨겨진 채 마운트되어 두 과목에서는 `(A,20)+(A,1)+(B,1)`이 가능하다. 이는 동일 인자 중복과 다르며 운영 3건이 이 구성인지는 미확정이다.
- 완료 목록 SQL에는 이미 custom plan 및 narrow key 개선이 적용되어 있다. 이번 소스 분석으로 서버 쿼리 4.587초의 실행 단계별 원인을 확정할 수 없다. 클라이언트의 응답시간만으로 DB 실행, 네트워크, 인증 또는 자원 대기를 분리할 수도 없다.

## 변경

과목 선택 상태를 기존 수강 편집기에 전달하고, 비활성 과목의 청강 보조 읽기를 첫 선택 시점으로 미룬다. 양쪽 편집기는 계속 마운트되므로 초안과 dirty 상태가 유지된다. 기존 owner token을 통해 숨긴 뒤 늦게 도착한 응답을 무시한다. 완료된 읽기는 과목 ID와 피드백 버전이 그대로이면 재사용한다. 피드백 변경은 다음 활성화에서 갱신하며 권한 상실은 결과 재사용을 무효화한다.

두 과목을 열고 첫 과목만 사용하는 경우 코드 경로상 manager 호출은 3→2다. 두 번째 과목도 사용하면 필요한 보조 조회가 그 시점에 실행되므로 총 요청을 영구 제거하는 것은 아니다. 활성 청강 패널의 기존 요청과 취소/갱신 정책은 유지한다. 개별 RPC가 더 빨라진다는 주장은 하지 않는다.

## 로컬 합성 재현

`tests/registration-track-workspace.test.mjs`의 새 4개 테스트는 실제 TSX를 로드하고 저장소의 기존 hook harness와 합성 서비스 경계를 사용한다.

1. 숨은 상태에서 보조 조회가 0회인지, 선택 후 1회인지, 완료 후 재선택은 추가 조회가 없는지, 피드백 변경/권한 복원은 갱신하는지 확인한다.
2. 선택 해제 후 늦은 결과가 수강 시작일을 바꾸지 않는지, 재선택에서 미완료 요청을 다시 읽더라도 사용자가 선택한 정규 수업 초안이 유지되는지 확인한다.
3. 실제 부모 컴포넌트가 두 과목 편집기를 모두 유지하면서 선택 상태만 다르게 전달하는지 확인한다.

동일한 새 테스트를 기준 소스에 연결하면 4개 모두 실패하며 수정 소스에서는 4개 모두 통과한다. 관련 workspace/service/class-selection/observation 회귀는 367개 통과, skip 0이다. 이 테스트는 React hook의 격리 검증이며 실제 Chrome 렌더링, 운영 데이터, 네트워크 응답시간 또는 DB 실행계획의 증거를 대신하지 않는다. 전체 필수 검사와 독립 리뷰 결과는 PR handoff의 정확한 SHA에 연결한다.

실패한 조회의 재선택 재시도와 권한 상실 중 도착한 응답 차단도 별도로 확인한다.

## 남은 관찰

완료 목록의 4.587초 원인을 더 좁히려면 운영 변경 없이 한 번의 정상 읽기에서 호출 시작 이유(초기 진입/필터 변경/페이지 보정), RPC 이름, 비식별 필터 종류/페이지/크기, TTFB와 전체 응답시간을 함께 확인해야 한다. manager 요청은 실제 식별자 대신 같은 세션 안의 과목 A/B와 attemptLimit만 기록하면 동일 요청인지 다른 용도인지 구분할 수 있다. 실제 학생값, 원문 payload, URL 식별자, 세션/토큰을 로그에 추가하지 않는다. 서버 실행계획이나 대기 분석이 필요하면 별도 승인 범위로 남기며 이번 작업에서 운영 SQL·통계 권한·부하 검사를 실행하지 않는다.
